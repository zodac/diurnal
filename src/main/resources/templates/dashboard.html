{! ONE grid holds all four panels, placed EXPLICITLY into a 2x2 arrangement at lg+: row 1: calendar (cols 1-2) | day logger (col 3) row 2: stats summary (1-2) | note box (col 3) So the summary is exactly the calendar's width, the note sits in the day logger's column, and — the point of the explicit row-start — the summary and the note share row 2, with their TOPS level. Letting the note hug the logger instead (a nested flex column spanning both rows) left it floating well above the summary whenever the logger was short, which is not "alongside". DOM order stays calendar, logger, note, summary, which is exactly the required order once the grid collapses to one column on a narrow screen — so no order-* utilities are needed, and the explicit placements are all `lg:`-prefixed. Grid items are left to STRETCH (no items-start): that is what makes the day logger fill row 1, so the note still sits directly beneath it however few actions the day has. Without it a short logger left the note floating with a gap above it. The stats-summary WRAPPER stretches too, but the card inside is a block at its natural height, so a one-action summary still reads as pinned to the top of its row. `dir="ltr"` pins this 2x2 ARRANGEMENT (which panel sits in which quadrant) regardless of language - a deliberate product decision (asked of the user, not inferred): this is the app's own workspace layout, not reading content, so it does not mirror the way a translated sentence does. Each panel below re-asserts the PAGE's real direction (`language:dir`), so everything INSIDE a panel - including the calendar's own day grid, which is a separate, deliberate decision to keep mirroring (see the weekday-header note below) - behaves exactly as it did before; only the four panels' OUTER positions are frozen. See .claude/UI_PATTERNS.md section 7. !}
{! min-w-0: grid items default to min-width:auto, which would let the calendar grid's intrinsic width blow the column past the viewport on mobile. Allowing the item to shrink lets the calendar size down to fit the narrow screen. dir re-asserted (see the note on the outer grid above). !}

{! The note box. Deliberately NOT a partial and NOT an HTMX swap target: it is rendered exactly once, and changing the selected day only rewrites the textarea's value from dashboard.js's client-side cache. That is what makes the drag-resized dimensions durable across a date change with no re-application — nothing inside #note-panel is ever replaced. It is seeded with the initially selected day's note (data-note-date / the textarea's content) so opening the dashboard costs no extra request, exactly as #stats-summary seeds its own cache. Unlike the day logger, this stays live for a FUTURE date — a note may be written for any day (see NoteService). !}

{msg:noteHeading}

{! No `maxlength`, deliberately — as for every other free-text input in the app (the rule was first written here, and the other fields have since been brought into line; only the two numeric fields, whose digits are one UTF-16 unit each, still carry one). The attribute counts UTF-16 units, so against a 10,000-character bound it would cut a note of emoji off at five thousand with no explanation. The counter below measures CODE POINTS instead, exactly as the server does, and over-typing is allowed so the user can see how far over they are and edit back down; Save is what refuses. !} {! dir="auto" (not a fixed dir="rtl" inherited from #note-panel): the note's OWN text is arbitrary user content that may be written in either direction regardless of the viewer's own language - the same bug shape the notes-list snippet has (see partials/notes-list.html's own comment), but this is an EDITABLE control, where the browser's native per-field direction detection (caret placement, arrow-key navigation included) is the right mechanism, not a CSS-only unicode-bidi rule. Without it, an all-English note's trailing punctuation visually migrates to the front of the sentence while the page is RTL. !} {! The editor is the textarea PLUS a mirror layer behind it. The mirror holds the same text with the same metrics, drawn transparent, and paints a tinted pill behind every [[name]] token that names a file this day actually holds - which is what makes an embedded attachment look distinct from the prose without the box having to stop being a plain textarea. Nothing is drawn on TOP of the textarea, so typing, selecting, the caret and the character counter are all untouched; the hover card is placed by hit-testing the mirror's own pill rectangles (note.js). !}

{! The upload's own progress, driven by XMLHttpRequest.upload.onprogress. A determinate bar rather than a spinner: the size is known before the request starts, so how far along it is can be told honestly. !} {! The bar and its cancel button are one row: an upload large enough to be worth a progress bar is large enough to be worth abandoning, and the control belongs beside the thing it stops rather than in the status line at the top of the card. The button aborts the XHR (note.js), which is what actually stops the bytes - nothing is stored for a request that never completed. !}
{! Clear empties the box but does NOT write: it leaves the emptied note for the user to Save (or Undo), so no destructive write ever happens on a single click. It is hidden unless the STORED note is non-empty, since there is nothing to clear otherwise. !} {! flex-wrap, and a counter that may shrink: with the character count switched on, a narrow note panel (a small window, or a box the user has dragged narrow) used to push Save off the end of the row rather than wrapping. The counter gives way first (min-w-0), and the button group wraps to its own line before anything is lost. !}
{! Shown only while a day is selected and the box is typeable — a count against a disabled, empty box is noise. Muted under the limit, red over it. Always RENDERED, even for a user who has turned the counter off in Settings: the element is what `aria-describedby` above points at, and note.js reveals it anyway while a note is over its bound, where it is the only explanation for Save going inert. The preference is therefore a condition on `hidden`, not on the markup. !}
{! The file picker is the same upload the drop zone performs, for anyone not dragging - a keyboard user, a touch device, or a browser with no drag support. `accept` is only a hint to the picker (a dropped file ignores it entirely), so the server's own extension check is what actually decides; it is omitted altogether when the deployment accepts everything. !} {! An ICON button, where the three beside it are words: the row already carries the counter and three controls, and the note panel is one grid column wide - a fourth worded button pushes Save off the end of it at the default width. The glyph says "attach" as well as the word does, and the accessible name plus the hover tooltip carry the wording for everyone else. !} {! Ctrl+S saves the note (note.js), and a shortcut nothing on screen mentions is a shortcut nobody finds - so the button doing the same thing carries the hint. `group relative` is what the shared bubble anchors to, exactly as on the Attach button above. It opens only while Save is LIVE, and needs no rule of its own to do so: `.note-btn-primary:disabled` already sets `pointer-events: none`, so `:hover` cannot match on an inert button - and a bubble offering a keystroke that would do nothing is worse than no bubble. `align='right'` because this is the row's trailing button: the bubble anchors to that edge and grows inward, so it can never widen the card. !}
{! Three drag handles: the right edge, the bottom edge and the corner. Native `resize: both` gives only a corner grip and cannot do the edges, so these are driven by the Pointer Events handler in dashboard.js (the same approach the settings stats picker uses). Decorative, so hidden from assistive tech — the box is fully usable at its default size, and the textarea scrolls. !} {! ONE hover card, reused for whichever attachment the pointer is over, rather than one per token: the tokens live inside a text layer that is rebuilt on every keystroke, so a card rendered among them would be destroyed mid-interaction. It is positioned by note.js against the pill it belongs to. The download link's href and the preview's src are set from the server-supplied URL on the attachment itself - never built here - so a sub-path deployment keeps its prefix. !} {! Two states, told apart by their OUTLINE. Hovering a pill opens a transient card, drawn with a dashed border: it follows the pointer from pill to pill and closes when the pointer leaves. CLICKING one pins it - solid border, and a close button, because a card that no longer answers to the pointer needs a way out that is not "guess". note.js owns the flag; the class is the whole of the styling difference. !}
{! The thumbnail opens the file full size in a new tab, which is the only way to see it at its own size: the card is a few rem tall by design (it floats inside a note box of --note-default-h, so anything larger covers the writing it is anchored in). rel="noopener" because the target is a user-supplied file - the tab it opens must not get a handle on this one. The href is set beside the src in note.js, from the URL the server put on the attachment. !} {! A sound file gets the browser's own player instead of a thumbnail. `preload="none"` is deliberate: this endpoint serves the whole file in one response (an attachment is sealed as a single blob, so there are no range requests to satisfy), and hovering a pill must not pull a megabyte down for a clip nobody plays. It is NOT wrapped in the "open full size" link the thumbnail uses - a link around the controls would swallow every click meant for play or the scrubber. note.js pauses it whenever the card closes. !}
{! No js-digits: that pass transcodes ASCII digits on an HTMX swap, and nothing swaps this card - note.js formats the figure with toLocaleString when it writes it, which does the same job at the one moment it is needed. !}
