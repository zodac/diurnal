{! The notes page's attachments data table (header + rows + pagination). Rendered on the full page (inside #note-attachment-list) and returned wholesale by GET /internal/note-attachments/list for HTMX swaps. Params: page (PaginatedAttachments), searching (true when a term is narrowing the list). Unlike the notes table above it, this table's state is NOT in the URL: its search box and its pagination links both swap over HTMX only, and the page's own ?q=/?page= belong to the notes half. That is why the footer is given pageUrl='' (so a link's href is "#", the same fallback the dashboard's day panel uses) and searchSource, which is what carries the live term into every page request (the delegated htmx:configRequest listener in app.js). `searching` is passed in rather than derived from a query suffix for the same reason - there is no suffix to read. Both names are marked up the way a note snippet is (NoteSearch.marked), and for the same reason: the mark is what shows WHY this row is in the result. They differ in that a filename needs no window - it is short and shown whole - so every occurrence is marked rather than one window's worth. The runs are a LIST, not a marked-up string, so Qute still escapes every character of a user-supplied name on the way out; never render one with .raw. TWO name columns, and they are different things. `name` is the display name the day's note embeds the file by, which a rename rewrites; `fileName` is what the file was uploaded as, which nothing rewrites. They read identically until someone renames a file - that is not redundancy to tidy away, it is what makes a renamed one legible beside the rest. The search box matches EITHER (NoteAttachmentService.searchPage), so whichever one the reader half-remembers finds the row. !}

The link opens in a new tab rather than navigating: an image renders and anything else downloads, and either way losing the notes page to do it would be the wrong trade. !} {!
