# Internationalisation (i18n) & Localisation (l10n)

Diurnal's UI is available in a choice of languages, each with real translated text, locale-aware date/number
formatting, and — for Arabic — a mirrored right-to-left layout. This file documents **how the finished feature
works**: the architecture, what is and isn't translated, the translation content itself, the test coverage, and
how to extend any of it. It is a reference doc, not a changelog — read the section you need, not the whole file.

## Language resolution

The offered languages are the constants of **`user/Language`** — a plain enum (not `PreviewOption`; the Settings
picker is an autonym-labelled dropdown, since a flag/thumbnail picker is a poor fit for a language that
spans many countries — see "The Settings language picker" below). Today: `ENGLISH_GB` (`en-GB`, the default), `ENGLISH_US` (`en-US`), `SPANISH` (`es-ES`),
`ARABIC` (`ar-SA`), `JAPANESE` (`ja-JP`). Every offered language is **region-qualified** — never a bare `en`/`es`/
`ar`/`ja` — so `Language.locale()` carries the region needed for correct date/number formatting, and a translator
is never left guessing which regional convention applies.

Two independent negotiation paths, because a request either has a signed-in user or it doesn't:

- **Logged-out pages** (login, register, the first-run setup wizard, 403/404 error pages) re-negotiate from the
  request's **`Accept-Language`** header on **every request** — `Language.fromAcceptLanguageHeader(String)`.
  There is no cookie and nothing is persisted; this was a deliberate design decision, not an oversight. Resolution
  falls back in two stages: an exact/regional match via `Locale.lookupTag`, then `Language.BASE_LANGUAGE_FALLBACK`
  for a header naming an offered *base* language but an uncarried region (e.g. `es-MX` still resolves to
  `SPANISH`, `ar-EG` still resolves to `ARABIC`) — a header naming no offered language at all, or missing/blank/
  unparseable, falls all the way to `Language.DEFAULT` (`en-GB`).
  Because those pages are genuinely content-negotiated, every HTML response carries **`Vary: Accept-Language`**
  (`quarkus.http.filter.html-pages.header.Vary` in `application.properties`, alongside the `Cache-Control:
  no-store` that already stops any cache keeping the page) — the header that stops a shared cache handing a stored Spanish
  `/login` to an Arabic-speaking client. It is set for every HTML path rather than just the logged-out ones: a
  signed-in page ignores `Accept-Language`, so declaring the dependency there is redundant but never wrong.
- **Logged-in pages** read the persisted **`User.language`** column directly, via `Language.fromValue(String)`,
  and ignore `Accept-Language` entirely. A new account's `language` defaults to `en-GB` regardless of the
  registering request's header (the header is only consulted for the pre-registration page *render*, never
  written onto the new row); a signed-in user changes it from Settings, which round-trips through
  `PATCH /api/v1/users/me`'s `preferences.language` field like any other preference.

`quarkus.default-locale`/`quarkus.locales` in `application.properties` list the same set for Quarkus's own
build-time validation of every `.properties` file — kept in sync with the `Language` enum by convention (a new
language needs both), not derived from one automatically.

## The Settings language picker

**The one Settings dropdown with a filter box.** Nothing can be placed inside a native `<select>`'s popup — the
browser owns that surface — so offering one meant owning the listbox: a button plus a `role="listbox"` panel
(`partials/combo-field.html`, the `.combo-*` block in `app.css`, `wireCombo()` at the top of `settings.js`). Every
Settings dropdown is now that same control, since a page with two kinds of dropdown is worse than a page with one;
`search=true` on this row is the only difference between them. The **field** is still an
`<input type="hidden" id="language" name="language">` carrying the same `hx-patch` the `<select>` did, so the save
path — and `settings.js`'s reload-once-saved handler, which reads `#language` and listens for its
`htmx:afterRequest` — never had to learn the control's new shape.

Each option is worded by `partials/language-option-label.html`, used for both the closed button and the list so the
two can never disagree: the **autonym** (`Language.label()` — "Español", the only name a user can find before the
UI has switched), plus, when the autonym does not already say it, the language's **English name** in brackets
(`Language.englishLabel()` — "Español (Spanish)", but plain "English (UK)"). That English name is CLDR data
(`Locale#getDisplayLanguage(Locale.ENGLISH)`), resolved once per constant exactly like the date patterns above, so a
newly-added language gets its second name for free and `LanguageTest` pins the resolved value. It is deliberately
English rather than the viewer's own language: it is the second name a language is universally listed under, and
translating every offered language's name into every other offered language would be 25 bundle entries today,
growing quadratically, for a search alias.

**The list is ordered by `Language.pickerOrder()`** — alphabetically on the English name, with the autonym
breaking the "English (UK)"/"English (US)" tie — so Arabic leads a list whose default language is English. English is
the one ordering every viewer can be given: there is no sequence that is alphabetical in five alphabets at once, and
sorting by autonym would reshuffle the list per script. Sorting rather than relying on the enum's declaration order
is deliberate — it is a rule a newly-added constant obeys on its own, and it leaves the declaration order meaning
nothing a user sees.

**The filter matches either name** (the two are one `data-search` string per option), case- and accent-insensitively
— `settings.js` folds both sides with NFD-then-strip-marks, so "espanol" reaches "Español" from a keyboard with no
`ñ`. A script the user cannot type is therefore always reachable by its English name, which is the point of the
box; it is a shortcut, never a gate, since every open starts unfiltered.

**Bidi**: each half of a label is its own `<bdi>` (`unicode-bidi: isolate` + `dir="auto"`) with its own `lang`, so a
mixed-script pair like "العربية (Arabic)" is laid out on the autonym's own terms while the line's base direction
stays the page's — verified in a real browser under both `dir`s (see `UI_PATTERNS.md` §7 on why a DOM-text dump
cannot check this). The widget's offsets are all logical properties and it contains no competing `ltr:`/`rtl:`
Tailwind pair, so it is clear of the nested-`dir` trap that `.app-tooltip-center` documents.

## Message bundles (`AppMessages`)

All translatable UI text lives in **`web/AppMessages`**, a single **unqualified** `@MessageBundle` interface —
deliberately unqualified (bundle name defaults to the literal string `"msg"`) rather than named after the
interface, which is why a translated sibling file is `msg_<locale>.properties`, not `messages_<locale>.properties`
or `AppMessages_<locale>.properties` — a real bug shipped once from assuming otherwise: a wrongly-named file
compiles, deploys and registers with CDI without error, Quarkus simply never associates it with any locale, and
the "translated" language silently renders English with no warning anywhere.

English content lives **inline**, as each method's `@Message("...")` default value — there is no separate English
`.properties` file, and `quarkus.default-locale=en-GB` means Quarkus **never even consults** a properties file for
that locale, even if one existed with different content. Every other offered language is a sibling
`src/main/resources/messages/msg_<locale>.properties`, one `methodName=translated text` line per bundle entry.

**A missing key falls back to the English default**, silently, per key (not per file) — confirmed by
`AppMessagesIT` and relied on deliberately in one place (see "Known limitations"). This is also why
`AppMessageCoverageTest` exists: it reflects over `AppMessages` and asserts each offered non-default locale's file
carries **exactly** the bundle's full key set — no missing key (an invisible English fallback) and no orphaned key
(a typo, or a stale entry for a since-removed method). **The locales it checks are derived from `Language.values()`,
not listed in the test** — a hardcoded list is a guard that silently stops watching the moment a language is added,
which is the one case it exists for.

That test additionally pins **placeholder parity**: every translated value must still reference each `{name}` its
English default uses (either bare, or as the base of a derived call like Arabic's `{count.arabicPluralCategory}`).
A *dropped* placeholder is the invisible half of this failure mode — Qute renders the sentence without it, so the
value just vanishes from that one language ("please try again in  seconds"), with no build error and no exception.
The reverse (a name the method never declared) throws at render, which `AppMessagesIT`'s every-method pass covers.

**The one rule every contributor needs: a locale is resolved per `TemplateInstance`, not implicitly, and a direct
Java call to an injected `AppMessages` bean always returns the English default**, regardless of the caller's own
`user.language`. Only a literal `{msg:...}` expression at a template render site, on a `TemplateInstance` that had
`.setAttribute(MessageBundles.ATTRIBUTE_LOCALE, someLocale)` called on it, resolves per-locale. Every page-rendering
`*WebResource` and every HTMX-fragment-rendering `*InternalResource` sets that attribute. Practically,
this means anything that isn't a literal `{msg:...}` call at a template call site — an enum's own `label()`, a
Java-computed compound string, a sealed result type's message — **cannot** resolve translated text by calling
`AppMessages` from Java; see "Adding a translatable string" below for the fix pattern this forces.

`/api/v1/*` JSON responses are **always English** — there is no `TemplateInstance` in flight for a JSON body, so
this isn't a gap to close, it's the shape of the mechanism. Where a sealed result type has both a web and an API
surface (e.g. `PasswordRejection`, `ProfileRejection`, `RegistrationError`), the API resource calls a plain static
English-producing method directly and the web resource instead resolves a translated sentence through a small
dedicated partial — both call the exact same underlying service, only the *rendering* differs. This split is
marked explicitly in each such class's own Javadoc (e.g. `PasswordChangeService.CURRENT_PASSWORD_ERROR`'s
comment), so it reads as policy, not as an inconsistency.

**A translated response body is text for a human, never a value to branch on.** The web surface returns a
*translated* sentence, so any client that reads one back — to decide which step to show, which field to highlight,
what went wrong — is really branching on English and quietly stops working in every other language. This shipped
once: `settings.js` matched the password-change 422 against `/current password/i` to decide whether to send the user
back to step 1 of the flow, which no non-English user ever hit. The fix, and the pattern for anything like it, is a
**machine-readable discriminator beside the body** — `SettingsWebResource` sends `X-Password-Error: current`,
alongside the existing `X-Lockout-Retry-After`. Same rule for a client-side *literal*: the handful of strings the
scripts compose come from `layout.html`'s `data-i18n-*` bootstrap into `window.Diurnal.i18n`, never from a quoted
string in a `.js` file. Login and register make that load-bearing rather than cosmetic — they are the two pages
whose language is negotiated per request, so a hardcoded literal there is English for every visitor who needed
otherwise (the lockout countdown banner was exactly that).

Where such a bootstrapped string has to wrap around an ELEMENT rather than a plain value — the lockout banner's live
`m:ss` clock — the message carries a `%CLOCK%`-style placeholder that the script swaps for the element, because a
`data-*` attribute can only hold text. That placeholder is not cosmetic either: the clock does not sit at the end of
the sentence in every language (Japanese puts it mid-sentence), so a "lead text plus appended element" split cannot
be worded correctly for all of them.

## Locale-aware formatting

**Dates**: `Language.locale()` feeds `DateTimeFormatter.ofLocalizedDate(FormatStyle...)` for full/long dates —
this localizes field *order* as well as vocabulary (`en-US` reorders to month-first with zero extra code, since
the `Locale` already carries the region). Two shapes no `FormatStyle` covers — `Language.dayMonthPattern()` (day +
abbreviated month, no year) and `Language.monthYearPattern()` (month + year, no day) — come from a **CLDR
skeleton** instead: `DateTimeFormatterBuilder.getLocalizedDateTimePattern("MMMd"/"yMMMM", IsoChronology.INSTANCE,
locale)`, which asks for a set of *fields* and lets CLDR choose the language's own order, separators and literals
(Japanese's `"M月d日"`/`"y年M月"`, Spanish's `"MMMM 'de' y"`, `en-US`'s `"MMM d"`). Both are resolved **once per
enum constant** in the constructor, not per call — the value is constant for a language and the lookup is ~700 ns.
This replaced an exhaustive switch of hand-written patterns, one arm per language per shape; CLDR returns exactly
what every arm said (bar `y` for the arms' `yyyy`, which renders identically for any four-digit year), so **a new
offered language needs no pattern work at all** and cannot be handed a wrong pattern by hand. The trade is that
`src/main` no longer states what any language's date shape is, so `LanguageTest` pins both the resolved pattern
and its rendered output per language — a CLDR revision arriving with a JDK upgrade fails there rather than quietly
reshaping every date on the Stats page.

> This does **not** need ICU4J — `getLocalizedDateTimePattern`'s skeleton overload is JDK (Java 19+), reading the
> same `jdk.localedata` CLDR the app already depends on and jlinks in (see "Fonts"). ICU4J was audited for this
> and the rest of the i18n surface; the only things it could remove that the JDK cannot are `ArabicPlural` and
> `Language.BASE_LANGUAGE_FALLBACK` (see "Known limitations"), which is not worth ~14 MB and a second CLDR copy
> today.

**The day a week starts on is a *user setting defaulted from the locale*, not a locale default** (`user/WeekStart`,
Settings > Preferences > "Week starts on"; stored in `users.week_start`, `NULL` = follow the language). The dashboard
calendar was fixed at Sunday-first in every language, which matched neither `en-GB`/`es-ES` convention nor the default
language's own — and the fix was deliberately **not** to make `WeekFields.of(locale).getFirstDayOfWeek()` *the* answer,
but to make it the **default** answer a user can override, because which day their week starts on is a habit a language
only predicts. All seven days are offered even though CLDR only ever returns three (Monday/Saturday/Sunday), precisely
because the override exists for the person the convention does not describe. `NULL` means there is no sentinel day to
interpret and nothing needed backfilling. `DayLabels#weekdayAbbreviations(locale, firstDay)` words the columns from the
locale and rotates them around the resolved day; the grid itself is offset by that same resolved day, handed to
`dashboard.js` as `data-week-start` in the browser's own `Date#getDay()` numbering (`WeekStart#browserIndex`), so the
header and the cells cannot drift apart. Each option's LABEL is CLDR data (`DayOfWeek#getDisplayName`), so only the
picker's `Automatic ({day})` wrapper is a bundle entry.

**Digit glyphs are a separate axis from vocabulary and field order.** `DateTimeFormatter#withLocale` alone does
*not* switch numbering systems, only weekday/month names — a date formatter must additionally chain
**`Language#localizeNumerals(DateTimeFormatter)`** (`.withDecimalStyle(DecimalStyle.of(locale()))`) to render
Arabic-Indic digits under `ar-SA`. A hand-built string that never passes through a formatter at all (e.g. the
timezone picker's `"UTC+5:30"`) instead runs through **`Language#localizeDigits(String)`**, which transcodes each
plain ASCII digit to the language's own zero-digit-relative glyph. On the client, the same job is done by the
shared **`.js-digits`** CSS marker class (paired with **`.js-phrase`**, see "Right-to-left support" below) —
applied unconditionally on every element that might ever hold a rendered number (banners, tooltips, stat tiles,
pagination, the frequency chart, the calendar). `.js-digits` transcodes whatever ASCII digits it finds in the
final rendered text regardless of whether they came from a literal or a substituted `@Message` parameter — which
matters because Qute's default `{param}` interpolation for a numeric `@Message` argument is plain
`Integer`/`Long#toString()`, with no locale awareness of its own. `HtmxResponses.conflictBanner` was the one
hand-built banner factory missing this pairing (it hardcoded `<div class="banner banner-error">` rather than
mirroring `partials/banner.html`'s markup exactly); `register.html`'s missing-fields banner is the other hand-built
copy and now carries it too (its body is a `<ul>`, so it cannot go through the partial).

**The two classes are not interchangeable, and where each goes is decided by its mechanism, not by taste.**
`.js-digits` is a JS pass that WALKS an element's descendants, so one marker on a list or a wrapper covers every row
generated inside it. `.js-phrase` is `unicode-bidi`, which is **not inherited** and governs only the inline content
of the element carrying it — so it must sit on the element that actually holds the sentence, and putting it on a
block-level ancestor whose children are block boxes does nothing at all. `partials/password-constraints.html` is the
worked example of the split (`.js-digits` on the `<ul>`, `.js-phrase` on each row's text `<span>`).

**A `#rrggbb` colour is exempt from digit localization**, in `Diurnal.localizeDigits` itself: it is a technical
token in the same category as an IANA zone id or a CSV header, and transcoding one yields `#١٦a٣٤a` — not a colour,
not copy-pasteable, and wrong in the two messages (`profileInvalidNoteColour`, `importInvalidColour`) whose whole
job is to show what a valid colour looks like. Digits elsewhere in the same sentence still localize. The guard lives
in the JS pass rather than in `Language#localizeDigits` because the JS pass is the one applied to arbitrary
translated messages; the Java one is only ever handed the timezone picker's own `"UTC+5:30"`.

**A raw `textContent =`/`innerHTML =` write bypasses every DOM pass**, because they are registered on
`htmx:afterSwap` — and `.js-digits` cannot be retro-fitted to such an element either, since `localizeDigitsIn` marks
what it has walked (`data-digits-done`) and never walks it twice. So these paths localize the STRING before writing
it: `Diurnal.bannerHtml` does, and so does `settings.js`'s `flashStatus`, which is where every Settings preference
rejection lands (several quote their own bound — "between 2 and 50 characters"). The bidi half still comes from a
class, since `.js-phrase` is CSS-only and survives the write (`partials/card-header.html`).

**Pluralisation** is expressed **inside a single `@Message` value**, as a `{#if}`/`{#else if}` chain — since a
`@Message` value is itself a small Qute template, no second grammar or bundle format is needed for CLDR-style
plural branching. English/Spanish use a plain `{#if count == 1}...{#else}...{/if}`; Japanese needs no branching at
all (nouns don't inflect) but keeps the same `{#if}` shape so every locale's file supplies what the method
declares; Arabic needs the full six-category CLDR grammar (`zero`/`one`/`two`/`few`/`many`/`other`), resolved by
**`web/ArabicPlural#arabicPluralCategory`** — a pure static `@TemplateExtension`, callable as
`{count.arabicPluralCategory}` directly inside a translated `@Message` value (Qute's expression language has no
modulo/range operators, so this can't be computed inline, and a Java-side caller can't be locale-aware per the
rule above). `ICU4J` was evaluated twice for this and rejected both times: its `MessageFormat` plural syntax uses
a second `{}` grammar that collides with Qute's own, and would need a second resource-bundle format per language.
One narrow, unimplemented follow-up remains: `ICU4J`'s `PluralRules.select()` could replace just `ArabicPlural`'s
hand-rolled boundary arithmetic while still feeding the same `{#if}` branching — optional, not a live gap.

**Decimal formatting** (`SubjectStatsExtensions.formatDecimal`) uses `NumberFormat.getNumberInstance(locale)` with
grouping off and rounding pinned to `HALF_UP` (not `NumberFormat`'s default `HALF_EVEN`, so `2.5` at zero decimal
places always reads `"3"`, consistently across languages).

**Collation**: locale-dependent lists sort via `java.text.Collator.getInstance(locale)`, applied in Java over an
already-fetched list rather than as a database `ORDER BY` (which has no access to the viewing user's locale) —
`LogsApiResource`'s day-events endpoint, `ActionsInternalResource.getActions` (shared by the `/actions` page and
`GET /api/v1/actions`) and `LogWebResource`'s day panel all do this. That last one is worth knowing as a shape: it
sorts by count and only *ties* on the name, and the tie-break used to be left implicit — a stable sort over the
DB's `order by name asc`, which is code-point order, so it put every accented or non-Latin name after every
plain-ASCII one and disagreed with the `/actions` page about the same two names on the same screen. **An implicit
tie-break inherited from a database ordering is still a text ordering**; make it explicit and collate it. The
month back-fill builds one `Collator` for the whole loop rather than one per day. Not every list needs any of this:
the admin users table sorts by `createdAt` (not a text field), and `Role`'s two-value ordering deliberately stays
plain `String#compareTo` (the two values collate identically either way).

## Right-to-left support

`Language.dir()` is an **exhaustive switch** (not a ternary) returning `"rtl"` for `ARABIC` and `"ltr"` for
everything else — exhaustive so a future RTL language addition that forgets this method fails the **build**,
never silently defaults to `"ltr"` at runtime. Wired into `<html dir="{language:dir(language)}">` via
`LanguageExtensions` (`@TemplateExtension(namespace = "language")`).

**App chrome deliberately stays fixed-position regardless of language.** The navbar, Settings' two-column layout
and the dashboard's panel grid all pin `dir="ltr"` on their *structural* container, with `dir="{language:
dir(language)}"` re-asserted on every child region so content inside still fully localizes (RTL alignment,
mirrored in-card controls, phrase direction, digit glyphs) — a deliberate choice of positional consistency
("muscle memory" for chrome a user builds habits around) over full mirroring, asked of the user directly rather
than assumed. The calendar's own internal day-grid is explicitly excluded from this pinning and does mirror.
Calendar-toolbar navigation glyphs (the «‹›» chevrons) are a further, separate exception: by explicit request they
never mirror regardless of language, unlike the Stats page's frequency-chart prev/next glyphs, which do.

CSS Grid and Flexbox mirror for free (`grid-column-start`/flex `justify-content`/order are relative to the writing
direction's start line, not physically left-to-right) — the dashboard's outer grid, the calendar's internal grid
and the toolbar needed zero JS/template changes for this. The general convention for anything else is **logical
properties**: `ms-*`/`me-*`/`ps-*`/`pe-*`/`start-*`/`end-*` in Tailwind, `margin-inline-*`/`padding-inline-*`/
`inset-inline-*`/`text-align: start` in handwritten CSS (see `UI_PATTERNS.md` §7) — a physical-direction utility
or property anywhere in a template or `app.css` is a bug, not a style nit.

**One CSS gotcha worth knowing**: Tailwind's `ltr:`/`rtl:` variants compile to `:where(:dir(X),[dir=X],[dir=X] *)`
— the `[dir=X] *` clause matches *any* ancestor carrying that attribute, not the nearest one, unlike native
`:dir()` (which resolves nearest-ancestor, like normal inheritance). Once chrome containers pin `dir="ltr"` with
no `dir="rtl"` reassertion inside them, a competing `ltr:`/`rtl:` pair on the same element can have **both halves
match simultaneously**, with CSS source order silently picking the wrong one. The fix, used wherever this bites
(`.app-tooltip-center`, `.toggle-thumb`), is a handwritten class using the native `:dir()` pseudo-class directly.

**Bidi isolation for embedded technical values**, three techniques depending on shape:

- `.js-digits`/`.js-num`/`.js-num-input` — `unicode-bidi: isolate`, protects a bare number from reordering
  relative to its surroundings (the same semantics as `<bdi>`).
- `.js-phrase` — `unicode-bidi: plaintext`, for a phrase mixing translated words with an embedded number/date;
  resolves the phrase's own base direction from its first *strongly*-directional character, self-adapting per
  phrase with no code change once content is translated. A phrase that is **only** a bare localized number (no
  accompanying word — e.g. a stat tile showing just `"٢٠٢٦"`) has nothing strongly-directional to find and falls
  back to LTR even on an Arabic page; `.js-phrase:dir(rtl)`/`:dir(ltr)` force `text-align` explicitly for this
  case, keyed on the ambient page language via `:dir()` rather than guessed from the element's own content.
- Literal Unicode bidi-isolate control characters (LRI `U+2066` / PDI `U+2069`), wrapped directly around a value
  inside a Java-built string, for the one case CSS can't reach: a plain-text `<option>` element, which accepts no
  markup at all (`UserSettings#offsetParen`, the timezone picker's UTC-offset parenthetical).

`dir="auto"` (browser-derived direction, not a CSS class) is used on exactly one element today: the note-writing
`<textarea>` (`#note-input`) — appropriate there because it's an *editable* field of unknown-in-advance direction,
and the browser's own mechanism also gets caret placement and arrow-key navigation right, which no CSS technique
can. It is **not** applied to other places a user's own free text is displayed read-only (an action name in
`partials/action-row.html`, a day-panel row, an admin user row, the navbar display name, a stat's custom label) —
this was planned in `TEXT_INPUT.md`'s original bidi-decision notes but never carried out; see "Known limitations."

## Fonts

Nova/Standard/OpenDyslexic (the `Font` setting's three options) are all Latin-only. **Noto Sans Arabic** and
**Noto Sans JP** (Google Noto project, SIL Open Font Licence) are appended to the *end* of every `--font-body`/
`--font-display` CSS stack (`:root`, `.font-nova`, `.font-dyslexic`) as a script-coverage fallback — **not** a
fourth `Font` picker option, and **not** gated behind the account's UI `language`, since a day note is free text
that may be typed in any script independent of the viewer's own language preference (the same principle
`NOTES.md` states for translation). `unicode-range` already makes the browser's fetch conditional on a character
actually needing the font, so no separate gating mechanism was needed on top of it.

Both are subsetted from upstream variable fonts (not shipped whole — the raw Japanese file alone is ~9.5 MB):
Arabic to Google's own curated Arabic-script glyph set, Japanese to the JIS X 0208 "common-use kanji + kana"
cutoff — total served payload for both scripts, both weights, is ~2.3 MB, trivial against the image's own size. A
rare kanji outside that cutoff falls through to the OS's own CJK fallback. Generation is scripted and reproducible
via `scripts/generate-noto-fonts.py`; master files live in `assets/NotoSansArabic/`/`assets/NotoSansJP/` (each
with its own `OFL.txt`), served `woff2` under `src/main/resources/META-INF/resources/fonts/`.

The Dockerfile's jlink build also trims to a `--include-locales=en,es,ar,ja` custom JRE, but must keep the
**`jdk.localedata`** module — despite the name suggesting "extra," CLDR-backed `java.time`/`java.text` calls
(weekday/month names, timezone display names) silently fall back to English/Latin data without it, in the
packaged runtime only (never in `quarkus:dev`/`mvn test`, both of which run a full non-jlink-ed JDK). A permanent
regression test lives in the deployment-smoke tier (`tests/smoke/smoke.spec.ts`).

## What is and isn't translated

**Never translated, no exceptions**: brand and product names ("Diurnal", "GitHub", "Nova", "OpenDyslexic"), a
`#rrggbb` colour value, and a user's own data — action names, display names, custom stat labels, and note content
(per `NOTES.md`'s own boundary: a note is the user's own words, and translating it would need to be a deliberate,
separately-decided, user-initiated action in some future feature, never an automatic side effect of a language
setting). The complete, closed list of user-supplied fields this covers is the `text/TextFields` catalogue:
`ACTION_NAME`, `DISPLAY_NAME`, `STAT_NAME` (the catalogue's own *default* label for a stat is translated; a user's
rename of it never is), `EMAIL`, `PASSWORD`, `NOTE`.

**The one name that looks like user data and isn't** is the notes `StatSubject`'s. Every other stats subject is an
action, so its name is the user's own text; the notes subject is app chrome sitting in the same list, and its name
is translated (`AppMessages#statSubjectNotes`) at each of the five places it renders — the stats cards, the
dashboard summary, the chart legend, the chart's compare picker, and the bar tooltip. The record still carries the
English `name()` for the API. See "The template-side-switch rule" for the `.or()` shape this needs.

**"OIDC" and "API"** are spelled out phonetically in non-Latin-script languages (`ar-SA`, `ja-JP` — e.g. OIDC →
"أو آي دي سي" / "オーアイディーシー") rather than kept as bare Latin letters, matching how Arabic/Japanese
technical writing conventionally handles initialisms like USB/PDF/CD: an initialism carries meaning (spoken
letter names) genuinely inaccessible in a different script, unlike a brand name, which carries none to translate.
`es-ES` (Latin script, already directly readable) is unaffected. **"UTC" is the one exception kept as literal
Latin letters everywhere** — it's tied to a formal ISO 8601 offset notation ("UTC+03:00"), not merely spoken
jargon, matching the convention Windows/Google/Apple all follow even in fully-localized timezone pickers.

**IANA timezone ids** (`Europe/London`, `Pacific/Auckland`, …) are always **submitted and stored** as the raw id,
in every language — only the visible Settings label changes. `en-GB`/`en-US` show the bare id (it *is* the
`@Message` default text); `es-ES`/`ar-SA`/`ja-JP` show a **segment-mapped translation** — each path segment
translated independently and rejoined with the id's own `/` (e.g. `Pacific/Auckland` → `es-ES` "Pacífico/Auckland",
`ar-SA` "باسيفيك/أوكلاند") — rather than a CLDR metazone display name or a natural "City, Country" phrase, both of
which were tried and rejected (a metazone name isn't always the translated CITY, and English losing its own
readable id in an earlier design was a regression nobody wanted).

**CSV filenames and column headers** in the data export/import (`actions.csv`/`logs.csv`/`notes.csv`, `name`/
`colour`/`date`/`action`/`count`/`content`) are a fixed, never-translated cross-language file-format contract —
otherwise round-tripping an export between two accounts on different UI languages would break. A filename is
therefore set apart visually instead of being translated - **bold**, both where it LEADS an import-refusal row and
where it is named INSIDE the sentence (`importMissingMember`/`importUnknownAction` carry
`<strong>...</strong>` in the `@Message` value itself, since the name does not fall at the same point in the sentence
in every language). A **header row** (`importEmptyFile`/`importWrongHeader`) is set in `<code>` chips instead
(`.import-problems code`): it is a list rather than one word, and bold alone leaves `name` reading as more words of
the sentence rather than as an exact column name the file has to carry.

**One chip per column NAME, never one around the whole list** — the commas separating them are ordinary sentence
punctuation and stay outside the chips, so a chip marks exactly where one name starts and stops. Unlike the bolded
filename, that markup is composed in Java (`TransferInternalResource.chippedColumns`) and substituted in as a single
value, because the number of names is a property of the member rather than of the language: writing the chips into
each `@Message` value would ask every translator to keep a per-member chip count in step with `TransferFiles`. The
separator stays an **ASCII comma in every language** (not `،`/`、`) for the same reason the names themselves are never
translated — chips and commas together spell the literal header row the file has to carry.

Those four arms of `partials/import-reason.html` — and the finished reason in `partials/import-panel.html` — are
therefore rendered with `.raw`, since Qute escapes the *result* of a `{msg:...}` expression like any other value and
would otherwise print the tags. **`.raw` switches off the escaping of everything the entry rendered, its parameters
included** (a message bundle's own template has no content type, so Qute never escaped them on the way in either) —
so a raw entry may embed only fixed text, or text escaped by hand with `web/HtmlEscaping`'s `{value.escapeHtml}`
extension, as `importUnknownAction`'s uploaded action name is.

**The Swagger UI** (the admin-only `/admin/api-docs` page) is a third-party asset and stays untranslated — an
accepted scope boundary, not a gap being tracked.

**Rejection messages are one whole, atomic sentence per (field, failure-shape) pair**, never a
`{fieldLabel} {requirement}` substitution — word order isn't universal, and a substitution can reorder words but
can't fix grammatical *agreement* (e.g. a Spanish article/adjective must agree in number with its noun), which
needs the whole sentence to vary. `partials/text-failure-message.html` is the shared partial for this shape,
switching on `field.key` then `shapeKey`.

**Every rejection is therefore worded twice**, and the Java wording is marked `@NotUiFacing` (`http/NotUiFacing`) —
`TextOutcomeExtensions.message`, `TextFieldExtensions.lengthMessage`, `ImportService.message`,
`ProfileService.message`, `RegistrationService.message`/`label`, `PasswordChangeService.message` and the three
`UserSettings.*_MESSAGE` constants. That text goes to an `/api/v1` body or a log, never to a page, which is why it
is hardcoded English with a concatenated plural `"s"` and no bundle lookup: what it says is free, because the
language setting does not govern it. **A web or internal surface must never call one** — it renders the partial (or
its own `msg:` entry) instead. `NotUiFacingTest` fails if a `*WebResource`/`*InternalResource` references an
annotated member, if one is also a Qute `@TemplateExtension`, or if the marker lands on a `private` member (the
constraint is about reach from another class, and a surface often sits in the *same package* as the service it
calls, so package-private still needs marking). Before it existed, a stray English sentence in a translated page
was caught by nobody: nothing throws, and only a reader of that language would see it.

**The same rule applies to any sentence, not just a rejection**, and two places had drifted from it:

- The registration form's missing-fields banner was `{msg:missingFieldsPrefix} {msg:missingFieldWord(n)}:`, joined
  by the template. Japanese is verb-final and has no "prefix" for a bare noun to follow, so its only workable
  translation of the prefix was the *whole* sentence — after which the noun was still appended to it, rendering
  「次の項目を入力してください 項目:」. Now one `missingFieldsIntro(count)` carrying the complete sentence per plural
  branch.
- The per-section page-size controls read `{msg:fewerItemsPerPageFor(section)}`, splicing `PageSection`'s English
  label into a translated frame — half-translated in every non-English language, and unfixable for a language whose
  preposition contracts onto the following noun (Arabic's لـ). Those three entries are gone: the visible row label
  IS the input's accessible name (a plain `<label for>`, which an `aria-label` was overriding), and the ± buttons
  take their section context from a `role="group"` labelled by that same label, so they can reuse the general row's
  existing generic captions.

**A substitution is still correct where the argument is genuinely a NAME** — `showFrequencyGraphFor(subjectName)`,
`stopComparing(subjectName)`, `duplicateActionName(name)` all interpolate the user's own action name, which has no
translated form and no agreement to satisfy.

## Translation content

Each offered language beyond English picked its own register once and applies it consistently: Spanish uses
informal **tú** throughout (matching consumer-SaaS convention over formal *usted*); Arabic uses Modern Standard
Arabic with masculine-default second-person address (matching the near-universal convention in Arabic software
UI, since Arabic has no true gender-neutral option); Japanese uses polite ***teineigo*** (です/ます) for sentences
and plain noun form for short button/label text, both coexisting by entry kind rather than one rule applied
uniformly. Domain vocabulary (streak, gap, action, dashboard, …) was picked once per language and reused
everywhere rather than translated key-by-key, so the same concept always reads the same way.

`msg_en-US.properties` is a **full duplicate** of the bundle's key set (currently ~390 keys), not a sparse
spelling-only diff — a deliberate reversal from an earlier, smaller design, made specifically so CrowdIn/Weblate
tooling (below) has a complete file to manage. It differs from the `en-GB` default only in American spelling
(`colour`→`color`, `authorised`→`authorized`, and similar) and a small number of genuinely different American
phrasings; everything else is generated by joining those overrides onto the English export.

## Translation tooling

**`scripts/generate-source-messages.sh`** (+ `scripts/GenerateSourceMessages.java`) reflects over the compiled
`AppMessages` class — not a source-text parse, which sidesteps multi-line concatenated `@Message` values — and
writes sorted `key=value` lines to **`translations/msg_en-GB.properties`**. This file is a **one-way export**,
never read by the running application; re-run the script after any English wording change, before syncing to a
translation platform.

**`../crowdin.yml`** is a starter config (properties-file mapping, the export file as
source, `src/main/resources/messages/msg_%locale%.properties` as each translated target) for CrowdIn/Weblate.
**No live project is wired up** — no `project_id`/token exist yet, so a new/updated translation still lands as a
hand-authored `msg_<locale>.properties` file exactly like the four that exist today; the tooling exists to make
that easier to set up later, not to automate it now.

**`web/AppMessageCoverageTest`** is the completeness guard: it reflects over `AppMessages` for the bundle's full
key set and asserts each offered non-default locale's `.properties` file carries exactly that set. It reads each
file via an explicit UTF-8 `InputStreamReader` (not the `Properties.load(InputStream)` overload, which defaults to
ISO-8859-1 and would corrupt non-Latin content) — added after a real gap (`es-ES` missing 14 timezone keys)
shipped unnoticed once, to make that class of mistake fail the build instead.

**That same test also pins the export itself** (keys *and* values, against the `@Message` annotations it was
generated from). Nothing in the running app reads `translations/msg_en-GB.properties`, which is exactly why it goes
stale unnoticed — it had already drifted a key behind. A key missing *there* is a string a translation platform
never offers anyone, which is how a language quietly ends up rendering English for it. If that test fails, the fix
is to re-run `scripts/generate-source-messages.sh`, not to hand-edit the file.

## Test coverage

- **`tests/ui/i18n.spec.ts`** — a smoke-level pass per offered language (not full parallel suites): for each of
  `en-GB`/`en-US`/`es-ES`/`ar-SA`/`ja-JP`, one case per negotiation path — a logged-out `/login` render (via
  `test.use({ locale })`, asserting `<html lang>`/`<html dir>` and the `signIn` message) and a logged-in dashboard
  render (register + login + set the language preference, asserting the same attributes plus the translated nav
  label). Excluded from the suite's mobile-viewport duplicate pass (behaviour/text assertions, not geometry).
- **`playwright.config.ts`** pins `locale: "en-GB"` explicitly for the rest of the E2E suite, so its many
  literal-English assertions pass on purpose rather than by accident of an unpinned browser default; `fixtures.ts`
  additionally forces the persisted `User.language` to `"en-GB"` post-login for the same reason (a logged-in page
  ignores `Accept-Language`, so the header pin alone isn't enough).
- **`tests/smoke/smoke.spec.ts`** carries a permanent regression test against the packaged Docker image: sets a
  test account's language to `ar-SA` and asserts the dashboard weekday header and the timezone picker both render
  real Arabic CLDR text, never an English/Latin fallback — the `jdk.localedata` jlink-module class of bug (see
  "Fonts") is invisible everywhere except a real built image, so this is the one tier that can catch it.
- **`AppMessagesIT`** renders real content per locale (including a worked pluralisation example), and includes a
  reflection-driven test that renders **every** bundle method with dummy arguments against every translated
  locale, asserting nothing throws — a stray unbalanced `{#if}` or a typo-ed parameter name in a 380+-line
  properties file is exactly the class of mistake a build does not catch, only a real render does.
- **`web/TemplateSwitchCoverageTest`** guards the "third bucket" enums whose translated word is resolved by a
  template `{#switch}` (`PageSection`, `IpLockoutStatus`): it reads the template source and asserts an arm exists
  per constant. A `{#switch}` with no matching arm renders nothing at all, silently — see "The template-side-switch
  rule".
- **Text-expansion / visual QA is manual, not automated** — real Playwright screenshots (desktop and a 390px
  mobile viewport) taken across the Actions table, calendar toolbar and full Settings page per language, reviewed
  by eye rather than asserted on. Right-to-left mirroring and the preview-tile pickers held up cleanly at both
  sizes across every language checked; the one place translated captions visibly truncate (the Settings "Action
  stats" picker row, at the 390px width) already truncates in English too and is already mitigated by its own
  long-press/hover tooltip, so this is an accepted, pre-existing tradeoff rather than a translation-specific
  regression.

## Known limitations

- **No live CrowdIn/Weblate project.** The export script and starter config exist (see "Translation tooling"),
  but nothing is actually connected yet — a new translation is still added by hand.
- **The Swagger UI stays untranslated** — an accepted third-party-asset boundary, not planned to change.
- **`ArabicPlural`'s hand-rolled CLDR boundary arithmetic could be narrowed with `ICU4J`'s `PluralRules.select()`**
  (see "Locale-aware formatting") — a scoped, optional simplification, not a functional gap.
- **`dir="auto"` covers only the note-writing textarea, not other read-only display of a user's own free text**
  (an action name in the Actions table or day panel, a display name, a custom stat label). This was planned
  alongside the note-box work but never carried out — a user-typed name in a script opposite to the current UI
  language has no explicit bidi handling today and simply inherits the page's own `dir`, which is usually but not
  always correct (see "Right-to-left support" for the technique to apply if this is picked up).
- **Collation is applied where it was found to matter (see "Locale-aware formatting"), not audited exhaustively
  across every list in the app** — a new paginated text list should be checked against the same question rather
  than assumed to already be covered, *including* one whose text ordering is only an implicit tie-break behind a
  numeric sort (the shape the dashboard day panel had).
- **Arabic's full CLDR plural branching is applied where the count genuinely varies**, not to every message with a
  number in it. `importWrongColumnCount`/`showingFirstOfTotalProblems` count something the input decides, so they
  carry the six-category `arabicPluralCategory` chain; `passwordLength`, `atLeastCharacters`, `importTooManyEntries`
  and similar always render the same deployment constant, so their single form is correct for the only value they
  ever show. The one to watch is `noteLength`, whose bound IS per-deployment configurable (`NOTE_MAX_LENGTH`,
  range `[1, 100_000]`) — its current wording assumes a large value, so a deployment setting it to 1 or 2 would
  read ungrammatically in Arabic. Messages with no counted noun at all (`atLine`, `pageOfTotal`) need nothing
  either way.
- **A user-chosen weekday name is not translated anywhere it is stored** — `users.week_start` holds `'monday'`, an
  English-looking token that is a storage value like a theme's `'dark'`, never display text (the WORD comes from
  CLDR at render time; see "Locale-aware formatting"). Read it as a value, never render it.

## Extending this

### Adding a new offered language

1. Add a constant to the `Language` enum: value tag, autonym label, a `dir()` switch arm (compiler-enforced — a
   missing arm fails the build), and a `BASE_LANGUAGE_FALLBACK` entry. The date patterns need nothing —
   `dayMonthPattern()`/`monthYearPattern()` resolve themselves from CLDR (see "Locale-aware formatting"); add the
   new language to `LanguageTest`'s four pattern tests to pin what CLDR gave it.
2. Add the tag to `quarkus.locales` in `application.properties` (Quarkus validates every `.properties` file's
   locale against this list at build time).
3. Add `src/main/resources/messages/msg_<locale>.properties` with the full bundle key set —
   `AppMessageCoverageTest` fails loudly if any key is missing, if any is orphaned, or if any translated value drops
   a `{placeholder}` its English default uses. It picks the new language up automatically: its locale list comes
   from `Language.values()`, so there is no second list to remember to extend (there used to be, and a guard that
   quietly does not run for the new language is worse than no guard).
4. If the script isn't Latin, add a font (see "Fonts") — the `unicode-range` mechanism is generic and needs no
   gating logic. RTL needs nothing extra either; `Language.dir()` and the logical-properties convention already
   generalize to a second RTL language.
5. Pick and document the register/formality convention for the language once (see "Translation content"), and
   apply it consistently rather than per-string.

A dynamic, filesystem-scanned language list (drop a file in, no code change) was considered and rejected:
`quarkus.locales` is validated at **build time**, so an unlisted file wouldn't even compile in as a recognized
locale, and `dir()`/the date patterns/the autonym label are structural facts a translated `.properties` file has
no natural home for — keeping them as compiler-enforced exhaustive switches trades away nothing a runtime lookup
would actually gain.

### Adding a new translatable string

Add a new `@Message`-annotated method to `AppMessages` (English inline as the default value), call it from a
template as `{msg:methodName}` / `{msg:methodName(args)}`, and add the key to every `msg_<locale>.properties`
file — `AppMessageCoverageTest` will fail if a language is missing it. Two footguns worth knowing before touching
an *existing* method's signature:

- A `@Message` method's parameter type must match what's actually passed — Quarkus's generated bundle resolver
  **casts** the argument to the declared type rather than widening/narrowing it, so a `Long` reaching an
  `int`-typed parameter (or vice versa) throws `ClassCastException` **at render time**, invisible to a normal
  build (Qute's build-time validation checks the expression parses and the method exists, not argument-type
  compatibility).
- After changing a widely-referenced method's signature, run a full `mvn clean compile test-compile` rather than
  relying on an incremental build — Maven's staleness check only recompiles a file whose *own* mtime changed, and
  will silently leave an unrelated dependent test file compiled against the old shape.

For pluralisation, embed the `{#if count == 1}...{#else}...{/if}` (or, for full CLDR generality,
`{count.arabicPluralCategory}`) **inside the single `@Message` value** — never mint a singular/plural method pair.

### The template-side-switch rule

Anything that needs translated text but isn't a literal `{msg:...}` call at a template render site — an enum's
own `label()`, a `*Extensions`/`*Service` method that would otherwise call `AppMessages` directly, a sealed
result's message — **cannot** resolve it from Java, per the "Java call = always English" rule under "Message
bundles" above. The established fix is a `{#switch someValue}...{#is X}{msg:someKey}{/is}...{/switch}` written
directly in the template that already has a locale-bound `TemplateInstance`; where the resolved text needs to be
reused as *data* passed into another partial (a confirm-delete prompt, an error banner), a small shared partial
rendered via `Template.render()` from Java is the pattern instead — see `partials/text-failure-message.html`,
`partials/password-rejection.html`, `partials/timezone-option.html` for worked examples of each shape. The one
exception to the whole rule: `java.time` formatters read a `Locale` argument directly with no template involved,
so ordinary Java is fine for date/number formatting (see "Locale-aware formatting").

**The corollary is that a "third bucket" enum carries no display label at all.** A `label()` field holding English
UI text is not a harmless default that a template can override — it is the thing that renders, in every language,
until someone notices. `Theme`/`Font`/`CalendarView`/`StatField` were built this way from the start; `PageSection`
and `IpLockoutStatus` had one each and shipped English into the Settings page-size rows and the admin lockout table
respectively. Both now hold only their stable key/badge class, with the word resolved from
`AppMessages#pageSection*`/`#lockoutStatus*` at the render site. Where the same enum is also published by the API,
that surface keeps the *machine-readable* form (`IpLockoutStatus#name()`), which is correct rather than a
compromise.

**Three shapes, and which one a call site needs:**

| The template needs… | Use | Worked example |
|---|---|---|
| just to print the word | `{#switch key}{#is 'x'}{msg:…}{/switch}` | `partials/admin-ip-lockout-row.html` |
| the word as *data* (an `aria-label`, a `data-*`, a nested `{#include}`) | the caller resolves it into a `{#let}` and passes it down | `settings.html` → `partials/page-size-section-row.html`, `partials/stats-field-row.html` |
| a value that is *sometimes* user data and sometimes chrome | a `@TemplateExtension` returning `null` for the chrome case, plus `.or(msg:…)` | `StatSubjectExtensions#actionName`, `FrequencySubjectExtensions#actionName` |

That third shape is the notes stat subject: an action's name is the user's own text and is never translated, while
the notes subject's name is app chrome and always is, and only the template can tell them apart *and* resolve the
translated half. `{#let}` cannot hold a `{#switch}`, and Qute has no ternary — `.or()` over a null-returning
extension is what bridges that, and it keeps the English `StatSubject#name()` intact for the API.

**A `{#switch}` with no matching arm renders NOTHING** — it does not fail the build and does not throw, so a
constant added without its arm ships a silently blank label, which is worse than the English it replaced.
`TemplateSwitchCoverageTest` reads the template source and asserts an arm exists per constant for exactly this
reason. (A bad `msg:` name inside an arm needs no such guard: Qute validates every expression at build time.)
