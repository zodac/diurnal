Diurnal's UI is available in a choice of languages, each with real translated text, locale-aware date/number
formatting, and — for Arabic — a mirrored right-to-left layout. This file documents **how the finished feature
works**: the architecture, what is and isn't translated, the translation content itself, the test coverage, and
how to extend any of it. It is a reference doc, not a changelog — read the section you need, not the whole file.

## Language resolution

The offered languages are the constants of **`user/Language`** — a plain enum (not `PreviewOption`; the Settings
picker is an autonym-labelled dropdown, since a flag/thumbnail picker is a poor fit for a language that
spans many countries — see "The Settings language picker" below). Today: `ENGLISH_GB` (`en-GB`, the default), `ENGLISH_US` (`en-US`), `SPANISH`
(`es-ES`),
`ARABIC` (`ar-SA`), `JAPANESE` (`ja-JP`). Every offered language is **region-qualified** — never a bare `en`/`es`/
`ar`/`ja` — so `Language.locale()` carries the region needed for correct date/number formatting, and a translator
is never left guessing which regional convention applies.

Two independent negotiation paths, because a request either has a signed-in user or it doesn't:

- **Logged-out pages** (login, register, the first-run setup wizard, 403/404 error pages) re-negotiate from the
  request's **`Accept-Language`** header on **every request** — `Language.fromAcceptLanguageHeader(String)`.
  There is no cookie and nothing is persisted; this was a deliberate design decision, not an oversight. Resolution
  falls back in two stages: an exact/regional match via `Locale.lookupTag`, then `Language.BASE_LANGUAGE_FALLBACK`
  for a header naming an offered *base* language but an uncarried region (e.g. `es-MX` still resolves to
  `SPANISH`, `ar-EG` still resolves to `ARABIC`) — a header naming no offered language at all, or missing/blank/
  unparseable, falls all the way to `Language.DEFAULT` (`en-GB`).
  Because those pages are genuinely content-negotiated, every HTML response carries **`Vary: Accept-Language`**
  (`quarkus.http.filter.html-pages.header.Vary` in `application.properties`, alongside the `Cache-Control:
  no-store` that already stops any cache keeping the page) — the header that stops a shared cache handing a stored Spanish
  `/login` to an Arabic-speaking client. It is set for every HTML path rather than just the logged-out ones: a
  signed-in page ignores `Accept-Language`, so declaring the dependency there is redundant but never wrong.
- **Logged-in pages** read the persisted **`User.language`** column directly, via `Language.fromValue(String)`,
  and ignore `Accept-Language` entirely. A new account's `language` defaults to `en-GB` regardless of the
  registering request's header (the header is only consulted for the pre-registration page *render*, never
  written onto the new row); a signed-in user changes it from Settings, which round-trips through
  `PATCH /api/v1/users/me`'s `preferences.language` field like any other preference.

`quarkus.default-locale`/`quarkus.locales` in `application.properties` list the same set for Quarkus's own
build-time validation of every `.properties` file — kept in sync with the `Language` enum by convention (a new
language needs both), not derived from one automatically.

**What ONE entry per language actually costs.** `BASE_LANGUAGE_FALLBACK` sends every unmatched region of an
offered language to that language's single entry — `ar-EG` and `ar-MA` to `ar-SA`, `es-MX` to `es-ES` — on the
grounds that the wrong regional flavour beats the wrong language. That is the right trade, but it is not free, and
the cost is concentrated in NUMBERS rather than words:

- **Arabic month names have three regional systems**: `سبتمبر` (Gulf/Egypt), `أيلول` (Levant/Iraq — `ar-LB`,
  `ar-SY`, `ar-IQ`, `ar-JO`), `شتنبر` (Maghreb — `ar-MA`). Everyone routed to `ar-SA` gets the first, which is the
  internationally understood form but not the local one for roughly half the Arabic-speaking world.
- **Arabic digit glyphs differ by region too, and this is the sharper one.** CLDR's default numbering system is
  `latn` for the Maghreb and the UAE (`ar-MA`, `ar-DZ`, `ar-TN`, `ar-AE`) and `arab` for the Gulf and Levant. So a
  Moroccan user gets Arabic-Indic digits throughout — every stat tile, every date, every count — where they would
  write Latin ones. The whole `localizeDigits`/`.js-digits` machinery follows `Language#locale()`, which is
  `ar-SA`.
- **Spanish vocabulary does NOT vary** (every region says `5 de septiembre de 2026`), but the **decimal separator
  does**: `es-MX`/`es-US` use `.` where `es-ES`/`es-AR`/`es-CO` use `,`. So `SubjectStatsExtensions#formatDecimal`
  shows a Mexican reader `4,0`.
- **The first day of the week differs across all of them** — and that one is already mitigated, because
  `user/WeekStart` is a user preference defaulted from the language rather than dictated by it.

**That asymmetry is the thing to notice**: the app already lets a user override the one regional difference that is
a habit, and offers no escape hatch for the numeric conventions, which are not. If a regional variant is ever added
(`es-419`, `ar-EG`), this is what it buys — separators and digits far more than words.

## The Settings language picker

**The one Settings dropdown with a filter box.** Nothing can be placed inside a native `<select>`'s popup — the
browser owns that surface — so offering one meant owning the listbox: a button plus a `role="listbox"` panel
(`partials/combo-field.html`, the `.combo-*` block in `app.css`, `wireCombo()` at the top of `settings.js`). Every
Settings dropdown is now that same control, since a page with two kinds of dropdown is worse than a page with one;
`search=true` on this row is the only difference between them. The **field** is still an
`<input type="hidden" id="language" name="language">` carrying the same `hx-patch` the `<select>` did, so the save
path — and `settings.js`'s reload-once-saved handler, which reads `#language` and listens for its
`htmx:afterRequest` — never had to learn the control's new shape.

Each option is worded by `partials/language-option-label.html`, used for both the closed button and the list so the
two can never disagree: the **autonym** (`Language.label()` — "Español", the only name a user can find before the
UI has switched), plus, when the autonym does not already say it, the language's **English name** in brackets
(`Language.englishLabel()` — "Español (Spanish)", but plain "English (UK)"). That English name is CLDR data
(`Locale#getDisplayLanguage(Locale.ENGLISH)`), resolved once per constant exactly like the date patterns above, so a
newly-added language gets its second name for free and `LanguageTest` pins the resolved value. It is deliberately
English rather than the viewer's own language: it is the second name a language is universally listed under, and
translating every offered language's name into every other offered language would be 25 bundle entries today,
growing quadratically, for a search alias.

**The list is ordered by `Language.pickerOrder()`** — alphabetically on the English name, with the autonym
breaking the "English (UK)"/"English (US)" tie — so Arabic leads a list whose default language is English. English is
the one ordering every viewer can be given: there is no sequence that is alphabetical in five alphabets at once, and
sorting by autonym would reshuffle the list per script. Sorting rather than relying on the enum's declaration order
is deliberate — it is a rule a newly-added constant obeys on its own, and it leaves the declaration order meaning
nothing a user sees.

**The filter matches either name** (the two are one `data-search` string per option), case- and accent-insensitively
— `settings.js` folds both sides with NFD-then-strip-marks, so "espanol" reaches "Español" from a keyboard with no
`ñ`. A script the user cannot type is therefore always reachable by its English name, which is the point of the
box; it is a shortcut, never a gate, since every open starts unfiltered.

**Bidi**: each half of a label is its own `<bdi>` (`unicode-bidi: isolate` + `dir="auto"`) with its own `lang`, so a
mixed-script pair like "العربية (Arabic)" is laid out on the autonym's own terms while the line's base direction
stays the page's — verified in a real browser under both `dir`s (see `UI_PATTERNS.md` §7 on why a DOM-text dump
cannot check this). The widget's offsets are all logical properties and it contains no competing `ltr:`/`rtl:`
Tailwind pair, so it is clear of the nested-`dir` trap that `.app-tooltip-center` documents.

## Message bundles (`AppMessages`)

All translatable UI text lives in **`web/AppMessages`**, a single **unqualified** `@MessageBundle` interface —
deliberately unqualified (bundle name defaults to the literal string `"msg"`) rather than named after the
interface, which is why a translated sibling file is `msg_<locale>.properties`, not `messages_<locale>.properties`
or `AppMessages_<locale>.properties` — a real bug shipped once from assuming otherwise: a wrongly-named file
compiles, deploys and registers with CDI without error, Quarkus simply never associates it with any locale, and
the "translated" language silently renders English with no warning anywhere.

English content lives **inline**, as each method's `@Message("...")` default value — there is no separate English
`.properties` file, and `quarkus.default-locale=en-GB` means Quarkus **never even consults** a properties file for
that locale, even if one existed with different content. Every other offered language is a sibling
`src/main/resources/messages/msg_<locale>.properties`, one `methodName=translated text` line per bundle entry.

**A missing key falls back to the English default**, silently, per key (not per file) — confirmed by
`AppMessagesIT` and relied on deliberately in one place (see "Known limitations"). This is also why
`AppMessageCoverageTest` exists: it reflects over `AppMessages` and asserts each offered non-default locale's file
carries **exactly** the bundle's full key set — no missing key (an invisible English fallback) and no orphaned key
(a typo, or a stale entry for a since-removed method). **The locales it checks are derived from `Language.values()`,
not listed in the test** — a hardcoded list is a guard that silently stops watching the moment a language is added,
which is the one case it exists for.

That test additionally pins **placeholder parity**: every translated value must still reference each `{name}` its
English default uses (either bare, or as the base of a derived call like Arabic's `{count.arabicPluralCategory}`).
A *dropped* placeholder is the invisible half of this failure mode — Qute renders the sentence without it, so the
value just vanishes from that one language ("please try again in  seconds"), with no build error and no exception.
The reverse (a name the method never declared) throws at render, which `AppMessagesIT`'s every-method pass covers.

**The one rule every contributor needs: a locale is resolved per `TemplateInstance`, not implicitly, and a direct
Java call to an injected `AppMessages` bean always returns the English default**, regardless of the caller's own
`user.language`. Only a literal `{msg:...}` expression at a template render site, on a `TemplateInstance` that had
`.setAttribute(MessageBundles.ATTRIBUTE_LOCALE, someLocale)` called on it, resolves per-locale. Every page-rendering
`*WebResource` and every HTMX-fragment-rendering `*InternalResource` sets that attribute. Practically,
this means anything that isn't a literal `{msg:...}` call at a template call site — an enum's own `label()`, a
Java-computed compound string, a sealed result type's message — **cannot** resolve translated text by calling
`AppMessages` from Java; see "Adding a translatable string" below for the fix pattern this forces.

`/api/v1/*` JSON responses are **always English** — there is no `TemplateInstance` in flight for a JSON body, so
this isn't a gap to close, it's the shape of the mechanism. Where a sealed result type has both a web and an API
surface (e.g. `PasswordRejection`, `ProfileRejection`, `RegistrationError`), the API resource calls a plain static
English-producing method directly and the web resource instead resolves a translated sentence through a small
dedicated partial — both call the exact same underlying service, only the *rendering* differs. This split is
marked explicitly in each such class's own Javadoc (e.g. `PasswordChangeService.CURRENT_PASSWORD_ERROR`'s
comment), so it reads as policy, not as an inconsistency.

**A translated response body is text for a human, never a value to branch on.** The web surface returns a
*translated* sentence, so any client that reads one back — to decide which step to show, which field to highlight,
what went wrong — is really branching on English and quietly stops working in every other language. This shipped
once: `settings.js` matched the password-change 422 against `/current password/i` to decide whether to send the user
back to step 1 of the flow, which no non-English user ever hit. The fix, and the pattern for anything like it, is a
**machine-readable discriminator beside the body** — `SettingsWebResource` sends `X-Password-Error: current`,
alongside the existing `X-Lockout-Retry-After`. Same rule for a client-side *literal*: the handful of strings the
scripts compose come from `layout.html`'s `data-i18n-*` bootstrap into `window.Diurnal.i18n`, never from a quoted
string in a `.js` file. Login and register make that load-bearing rather than cosmetic — they are the two pages
whose language is negotiated per request, so a hardcoded literal there is English for every visitor who needed
otherwise (the lockout countdown banner was exactly that).

Where such a bootstrapped string has to wrap around an ELEMENT rather than a plain value — the lockout banner's live
`m:ss` clock — the message carries a `%CLOCK%`-style placeholder that the script swaps for the element, because a
`data-*` attribute can only hold text. That placeholder is not cosmetic either: the clock does not sit at the end of
the sentence in every language (Japanese puts it mid-sentence), so a "lead text plus appended element" split cannot
be worded correctly for all of them.

## Locale-aware formatting

**Dates**: `Language.locale()` feeds `DateTimeFormatter.ofLocalizedDate(FormatStyle...)` for full/long dates —
this localizes field *order* as well as vocabulary (`en-US` reorders to month-first with zero extra code, since
the `Locale` already carries the region). Two shapes no `FormatStyle` covers — `Language.dayMonthPattern()` (day +
abbreviated month, no year) and `Language.monthYearPattern()` (month + year, no day) — come from a **CLDR
skeleton** instead: `DateTimeFormatterBuilder.getLocalizedDateTimePattern("MMMd"/"yMMMM", IsoChronology.INSTANCE,
locale)`, which asks for a set of *fields* and lets CLDR choose the language's own order, separators and literals
(Japanese's `"M月d日"`/`"y年M月"`, Spanish's `"MMMM 'de' y"`, `en-US`'s `"MMM d"`). Both are resolved **once per
enum constant** in the constructor, not per call — the value is constant for a language and the lookup is ~700 ns.
This replaced an exhaustive switch of hand-written patterns, one arm per language per shape; CLDR returns exactly
what every arm said (bar `y` for the arms' `yyyy`, which renders identically for any four-digit year), so **a new
offered language needs no pattern work at all** and cannot be handed a wrong pattern by hand. The trade is that
`src/main` no longer states what any language's date shape is, so `LanguageTest` pins both the resolved pattern
and its rendered output per language — a CLDR revision arriving with a JDK upgrade fails there rather than quietly
reshaping every date on the Stats page.

> This does **not** need ICU4J — `getLocalizedDateTimePattern`'s skeleton overload is JDK (Java 19+), reading the
> same `jdk.localedata` CLDR the app already depends on and jlinks in (see "Fonts"). ICU4J was audited for this
> and the rest of the i18n surface; the only things it could remove that the JDK cannot are `ArabicPlural` and
> `Language.BASE_LANGUAGE_FALLBACK` (see "Known limitations"), which is not worth ~14 MB and a second CLDR copy
> today.

**The day a week starts on is a *user setting defaulted from the locale*, not a locale default** (`user/WeekStart`,
Settings > Preferences > "Week starts on"; stored in `users.week_start`, `NULL` = follow the language). The dashboard
calendar was fixed at Sunday-first in every language, which matched neither `en-GB`/`es-ES` convention nor the default
language's own — and the fix was deliberately **not** to make `WeekFields.of(locale).getFirstDayOfWeek()` *the* answer,
but to make it the **default** answer a user can override, because which day their week starts on is a habit a language
only predicts. All seven days are offered even though CLDR only ever returns three (Monday/Saturday/Sunday), precisely
because the override exists for the person the convention does not describe. `NULL` means there is no sentinel day to
interpret and nothing needed backfilling. `DayLabels#weekdayAbbreviations(locale, firstDay)` words the columns from the
locale and rotates them around the resolved day; the grid itself is offset by that same resolved day, handed to
`dashboard.js` as `data-week-start` in the browser's own `Date#getDay()` numbering (`WeekStart#browserIndex`), so the
header and the cells cannot drift apart. Each option's LABEL is CLDR data (`DayOfWeek#getDisplayName`), so only the
picker's `Automatic ({day})` wrapper is a bundle entry.

**Digit glyphs are a separate axis from vocabulary and field order.** `DateTimeFormatter#withLocale` alone does
*not* switch numbering systems, only weekday/month names — a date formatter must additionally chain
**`Language#localizeNumerals(DateTimeFormatter)`** (`.withDecimalStyle(DecimalStyle.of(locale()))`) to render
Arabic-Indic digits under `ar-SA`. A hand-built string that never passes through a formatter at all (e.g. the
timezone picker's `"UTC+5:30"`) instead runs through **`Language#localizeDigits(String)`**, which transcodes each
plain ASCII digit to the language's own zero-digit-relative glyph. On the client, the same job is done by the
shared **`.js-digits`** CSS marker class (paired with **`.js-phrase`**, see "Right-to-left support" below) —
applied unconditionally on every element that might ever hold a rendered number (banners, tooltips, stat tiles,
pagination, the frequency chart, the calendar). `.js-digits` transcodes whatever ASCII digits it finds in the
final rendered text regardless of whether they came from a literal or a substituted `@Message` parameter — which
matters because Qute's default `{param}` interpolation for a numeric `@Message` argument is plain
`Integer`/`Long#toString()`, with no locale awareness of its own. `HtmxResponses.conflictBanner` was the one
hand-built banner factory missing this pairing (it hardcoded `<div class="banner banner-error">` rather than
mirroring `partials/banner.html`'s markup exactly); `register.html`'s missing-fields banner is the other hand-built
copy and now carries it too (its body is a `<ul>`, so it cannot go through the partial).

**The two classes are not interchangeable, and where each goes is decided by its mechanism, not by taste.**
`.js-digits` is a JS pass that WALKS an element's descendants, so one marker on a list or a wrapper covers every row
generated inside it. `.js-phrase` is `unicode-bidi`, which is **not inherited** and governs only the inline content
of the element carrying it — so it must sit on the element that actually holds the sentence, and putting it on a
block-level ancestor whose children are block boxes does nothing at all. `partials/password-constraints.html` is the
worked example of the split (`.js-digits` on the `<ul>`, `.js-phrase` on each row's text `<span>`).

**A `#rrggbb` colour is exempt from digit localization**, in `Diurnal.localizeDigits` itself: it is a technical
token in the same category as an IANA zone id or a CSV header, and transcoding one yields `#١٦a٣٤a` — not a colour,
not copy-pasteable, and wrong in the two messages (`profileInvalidNoteColour`, `importInvalidColour`) whose whole
job is to show what a valid colour looks like. Digits elsewhere in the same sentence still localize. The guard lives
in the JS pass rather than in `Language#localizeDigits` because the JS pass is the one applied to arbitrary
translated messages; the Java one is only ever handed the timezone picker's own `"UTC+5:30"`.

**A raw `textContent =`/`innerHTML =` write bypasses every DOM pass**, because they are registered on
`htmx:afterSwap` — and `.js-digits` cannot be retro-fitted to such an element either, since `localizeDigitsIn` marks
what it has walked (`data-digits-done`) and never walks it twice. So these paths localize the STRING before writing
it: `Diurnal.bannerHtml` does, and so does `settings.js`'s `flashStatus`, which is where every Settings preference
rejection lands (several quote their own bound — "between 2 and 50 characters"). The bidi half still comes from a
class, since `.js-phrase` is CSS-only and survives the write (`partials/card-header.html`).

**Pluralisation** is expressed **inside a single `@Message` value**, as a `{#if}`/`{#else if}` chain — since a
`@Message` value is itself a small Qute template, no second grammar or bundle format is needed for CLDR-style
plural branching. English/Spanish use a plain `{#if count == 1}...{#else}...{/if}`; Japanese needs no branching at
all (nouns don't inflect) but keeps the same `{#if}` shape so every locale's file supplies what the method
declares; Arabic needs the full six-category CLDR grammar (`zero`/`one`/`two`/`few`/`many`/`other`), resolved by
**`web/ArabicPlural#arabicPluralCategory`** — a pure static `@TemplateExtension`, callable as
`{count.arabicPluralCategory}` directly inside a translated `@Message` value (Qute's expression language has no
modulo/range operators, so this can't be computed inline, and a Java-side caller can't be locale-aware per the
rule above). `ICU4J` was evaluated twice for this and rejected both times: its `MessageFormat` plural syntax uses
a second `{}` grammar that collides with Qute's own, and would need a second resource-bundle format per language.
A CLDR plural-rule LOOKUP is a different question from `MessageFormat`, and it is the standing follow-up: it would
replace just `ArabicPlural`'s hand-rolled boundary arithmetic while feeding the same `{#if}` branching. Declined for
now, with an explicit trigger and a designated 26 KB library — see step 4 of "Adding a new offered language".

**A month or weekday name that stands ALONE takes a different word from one inside a date, and CLDR carries both.**
`java.time` splits them as `TextStyle.X` (the in-date, "formatting" form) and `TextStyle.X_STANDALONE`; a bare
`Intl.DateTimeFormat(lang, {month})` gives the standalone form, while asking for the month beside a day and a year
gives the in-date one. They are the same word in English, Spanish, Arabic and Japanese, which is why getting this
wrong is invisible here — and different words in Russian, Polish, Ukrainian, Greek, Croatian and Finnish
(`сентябрь`/`сентября`, `wrzesień`/`września`, `syyskuu`/`syyskuuta`), and different punctuation in German
(`Sept.`/`Sep`, `Mo.`/`Mo`). Finnish's weekday is a whole grammatical case apart: `FULL` is the essive
`maanantaina`, "*on* Monday".

**So the style is chosen by what the string IS, not by what reads well in English.** Standing alone →
`*_STANDALONE`: `DayLabels#weekdayAbbreviations` (calendar column headers), `WeekStart#dayName` (the "Week starts
on" options), `FrequencyCharts#shortLabel` (the chart's month axis), and JS's `Diurnal.MONTHS_FULL`/`MONTHS_ABBR`
(the calendar toolbar title and the month-picker grid). Inside a rendered date → the plain style, which is what
`ofLocalizedDate` and a `MMM`/`MMMM` pattern already use on their own. **`Language#monthYearPattern()` needs
nothing either way** — the CLDR skeleton returns `LLLL y` (the standalone field) for exactly those languages by
itself, which is the skeleton approach earning its keep.

`app.js` keeps BOTH arrays for this reason. `Diurnal.shortenMonths` rewrites a name sitting inside an
already-rendered date, so it matches and replaces using the IN-DATE forms — built with `formatToParts` on a full
date, since `format` on a month-only request gives the other form. Matching on the standalone form found nothing
in `"15 сентября 2026"`, so the month step of the abbreviation ladder silently did nothing in every inflecting
language: no error, no wrong text, just a tile that skipped to shortening its year. It also skips any month whose
CLDR abbreviation is NUMERIC rather than a shorter name — Finnish abbreviates `syyskuuta` to `9`, and rewriting it
produced `"15. 9 2026"`, shorter but not a well-formed date in any language, because the separators around it
belong to the spelled-out form.

**A compact figure is CLDR's, never a suffix bolted onto a formatted number.** `app.js`'s `compactNumber` (used by
`fitFigures`' abbreviation ladder for any count of 10,000 or more) is an `Intl.NumberFormat(lang, {notation:
'compact'})`, because "10.0k" is only right for a language that abbreviates in thousands with a Latin letter:
Japanese groups by 万 at exactly that threshold (`1万`), Arabic writes `١٠ آلاف`, and under `dir="rtl"` a trailing
`k` is a stray LTR character sitting in an Arabic-Indic figure. The 10,000 threshold stays an explicit check
rather than being left to `compact` for everything — `compact` would also rewrite 1,500 as "1.5K" and move the
ladder's steps.

**The ADMIN console's timestamps are localised too, and were the last place that was not.** Both consoles used a
fixed `DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm", Locale.ROOT)`, which pinned the field order, forced 24-hour
regardless of the language's own hour cycle, and emitted ASCII digits onto a page whose every other number was in
the language's own glyphs. They now use `ofLocalizedDateTime(MEDIUM, SHORT)` with the viewing administrator's
locale, chained through `Language#localizeNumerals` like every other date. **MEDIUM rather than SHORT for the date
half**, deliberately: SHORT abbreviates the year to two digits, and `"9/5/26"` is two different days in `en-GB` and
`en-US` — an operator comparing a row against a log needs it unambiguous. The zone is still shown untranslated
beside it, as an IANA id, which is the part that genuinely is a technical token.

**A date RANGE's separator is the language's** — `Language#dateRangeSeparator()`, an exhaustive switch in the same
shape as `dir()`. An en dash is not universal punctuation: Japanese writes a range with a wave dash (`〜`), which
is what every Japanese calendar UI uses. CLDR does carry interval separators, but only inside interval formats the
JDK does not expose, which is why this is a switch rather than a lookup.

**A length bound is a CODE POINT count, so it must never be published as an HTML `maxlength`.** Everything the
server measures goes through `TextFieldExtensions#length` (`codePointCount`), while the `maxlength` attribute is
defined in UTF-16 *code units* — so on a field that accepts emoji (action name, display name, stat name, and the
note body) the browser silently truncates at half the allowed length, with no message and nothing in the DOM to
explain it. No free-text input in the app carries `maxlength`; each publishes its declared bound as
`data-max-length` instead, and the server's rejection (rendered through `partials/text-failure-message.html`, in
the viewer's own language) is what enforces it. The two `inputmode="numeric"` fields — the day-panel count and the
calendar's year jump — are the exception and keep theirs: a digit is one UTF-16 unit in every numbering system the
app renders.

**Decimal formatting** (`SubjectStatsExtensions.formatDecimal`) uses `NumberFormat.getNumberInstance(locale)` with
grouping off and rounding pinned to `HALF_UP` (not `NumberFormat`'s default `HALF_EVEN`, so `2.5` at zero decimal
places always reads `"3"`, consistently across languages).

**A SEARCH term is NFC-composed before it is compared** — `TextValidation#searchTerm`, applied at every search
entry point (`ActionsInternalResource#getActions`, `LogWebResource`'s day panel, `StatsService#compareCandidates`,
`NoteService`'s two paged reads, and the two resources that hand the same term to `NoteSearch#snippet` for
highlighting). Every stored value is already NFC-composed on the way in, so a term typed or pasted in decomposed
form — which macOS's clipboard and several input methods produce routinely for accented Latin, Vietnamese and
Arabic — is a different code-point sequence from the visually identical value it is meant to find, and matches
nothing at all. The failure is silent and reads as missing data rather than as a bug, which is why the fold sits
at every entry point rather than at whichever one gets reported. Case is folded separately, at the comparison
itself (`Locale.ROOT` everywhere, or `CASE_INSENSITIVE | UNICODE_CASE` for the note search, which needs to report
WHERE a hit sits).

**Tokenising free text is done by CODE POINT, and a combining mark extends a word rather than ending it** —
`NoteSearch#collect`, which feeds the "did you mean" suggestion. `Character.isLetterOrDigit(char)` answers false
for either half of a surrogate pair and for every mark (`Mn`/`Mc`/`Me`), so a char-at-a-time scan cut a word in
two at each of them: vocalised Arabic, Devanagari or Thai with their matras, Hebrew with niqqud, and anything
holding a supplementary-plane letter were tokenised into fragments, and the fragments are what the edit distance
then measured. For the same family of reason `NoteSearch#cut` walks a snippet edge back off a combining mark or
the interior of an emoji ZWJ sequence, not just off a lone surrogate half.

**Ordering a list of user-typed names goes through `text/TextOrdering#byName(locale)`, never a bare `Collator` and
never the database.** Two rules, and the second is not any collator's default:

1. **Letters collate per locale** (`java.text.Collator`). No third-party collator is needed for this: measured
   against `ICU4J` 77.1 across sixteen locales and five scripts — Swedish `å` after `z`, Danish, German `ä` with
   `a`, Czech `ch` as one letter after `h`, Estonian `z` between `s` and `t`, Turkish dotless `ı`, Polish, Arabic,
   Japanese kana, Chinese pinyin — the two agree on **every** case, and the JDK's locale coverage is the wider of
   the two (166 against 143).
2. **Runs of digits compare as NUMBERS**, so `"Run 2"` precedes `"Run 10"`. This is the one thing no collator here
   does: `ICU4J` offers it as a switch (`setNumericCollation`) and the JDK offers nothing, so it is hand-rolled —
   worth far less than 14 MB, and worth having, because naming a series of things is what people do. It reads any
   script's digits by value, so `"نشاط ٢"` orders before `"نشاط ١٠"`, and against Latin numerals too.

**Do not order a user-visible list in SQL.** `ORDER BY name` inherits whatever collation the container was
initialised with, and the deployed `postgres:*-alpine` image is musl-based: it reports `datcollate = en_US.utf8`
and then sorts `Zebra, apple, Ähre, ábaco` — code-point order, uppercase before lowercase and every accented name
last. It is also not stable across deployments, since a glibc-based image would answer differently for the same
rows. Three Stats lists inherited exactly that before this rule was written down (the Stats cards on both the
cached and computed paths, and the frequency chart's compare picker), which additionally made the Stats page and
the `/actions` page disagree about the same two names.

**The one list deliberately left uncollated is the CSV export** (`ExportService`): it needs a deterministic,
locale-independent order so a round-trip between two accounts on different UI languages is stable — the same
reasoning as its never-translated column headers.

**Collation**: locale-dependent lists sort via `java.text.Collator.getInstance(locale)`, applied in Java over an
already-fetched list rather than as a database `ORDER BY` (which has no access to the viewing user's locale) —
`LogsApiResource`'s day-events endpoint, `ActionsInternalResource.getActions` (shared by the `/actions` page and
`GET /api/v1/actions`) and `LogWebResource`'s day panel all do this. That last one is worth knowing as a shape: it
sorts by count and only *ties* on the name, and the tie-break used to be left implicit — a stable sort over the
DB's `order by name asc`, which is code-point order, so it put every accented or non-Latin name after every
plain-ASCII one and disagreed with the `/actions` page about the same two names on the same screen. **An implicit
tie-break inherited from a database ordering is still a text ordering**; make it explicit and collate it. The
month back-fill builds one `Collator` for the whole loop rather than one per day. Not every list needs any of this:
the admin users table sorts by `createdAt` (not a text field), and `Role`'s two-value ordering deliberately stays
plain `String#compareTo` (the two values collate identically either way).

## Calendar systems

**Every date this app renders is GREGORIAN, in every language. That is a deliberate product boundary, not an
unset option** — and it is worth stating explicitly because nothing in the code says so and no language offered
today wants otherwise. CLDR itself flags the gap: ask it for a Thai long date and it returns
`5 กันยายน ค.ศ. 2026`, adding a `ค.ศ.` ("Christian Era") marker precisely because a Thai reader expects the
Buddhist-era year 2569. A Persian user would likewise see Gregorian where Solar Hijri is conventional.

Note that this is not something Java is quietly deciding for us in a way a flag could change:
`Chronology.ofLocale` answers `ISO` for `th`, `fa`, `he` and `hi` alike, because the JDK honours only an explicit
`-u-ca-` extension rather than CLDR's per-locale default calendar. The Gregorian rendering is what the code asks
for, everywhere.

### What is calendar-independent, and what only looks it

**A date is a point in time; a calendar is a rendering of it.** Most of the persistence and contract layer follows
from that and would not move:

- **The COLUMN TYPE** — `notes.note_date` / `action_logs.log_date` are SQL `DATE`, and the Gregorian↔Hebrew↔Hijri
  day mapping is a pure bijective calculation. Nothing needs a new column to *name* a stored day differently.
- **Ordering and range scans** — a day ordering is monotonic in every calendar, so `ORDER BY log_date`, the
  `(user_id, log_date)` indexes and every `BETWEEN` window keep working once their endpoints are converted.
- **The public API** — `/api/v1/logs/{date}`, the notes feed's `start`/`end`, every DTO: ISO-8601, always. Changing
  that is a MAJOR-version event (see "The namespace decides the contract" in `CLAUDE.md`), and there is no reason
  to: a client wanting a Buddhist-era date can convert one.
- **The CSV export's `date` column** — a fixed cross-language file-format contract, for the same reason its headers
  are never translated (see "What is and isn't translated").
- **Every figure counted in DAYS** — streaks, gaps, totals, `Durations#days`. A day is a day in every calendar.

**Two things that look like storage concerns and are, so do not read the above as "the database is fine":**

- **The DATABASE does Gregorian month arithmetic.** `ActionLogQueries.MONTHLY_TOTALS_JPQL` selects
  `YEAR(l.logDate), MONTH(l.logDate)` and `GROUP BY`s them — bucketing executed by PostgreSQL, which has no notion
  of a Hebrew or Hijri month and cannot be taught one. The frequency chart's YEAR window would have to read daily
  rows and bucket them in Java against the chosen chronology instead. The shape already exists
  (`DAILY_TOTALS_JPQL`, and `StatsService.assemble` already derives a month's total from its days for the Stats
  page) so it is not a large change — but that Javadoc also records the measurement that put the aggregation into
  the database in the first place, 65 ms against 4.8 ms, so moving it back has a known cost to re-measure.
- **The day BOUNDARY is midnight, and the Hebrew and Islamic days begin at SUNSET.** `AppClock#today(zone)` is
  `LocalDate.now(clock.withZone(zone))` — a civil midnight-to-midnight day — and `log_date` is part of
  `action_logs`' PRIMARY KEY while `note_date` backs `notes_unique`, so a Gregorian civil day IS the identity of an
  entry. For an observant user an action logged at 21:00 on 5 September belongs to the *next* Hebrew day, and no
  amount of relabelling fixes that: deriving a sunset boundary needs the entry's instant plus the user's
  LOCATION (latitude/longitude for a solar calculation), and the app stores an IANA timezone, which is not one.

  **So the honest position is that the app defines its day as the civil midnight day and renders every calendar on
  that basis** — which is what ICU's own `HebrewCalendar`/`IslamicCalendar` do when converting an instant, and what
  most software does. That is a defensible choice and probably the right one; it is not a free one, and it has to
  be STATED rather than assumed, because it is the difference between "we relabel days" and "we model this
  calendar". Anything more faithful is a change to what is stored, not to how it is displayed.

### What actually assumes Gregorian

The work is confined to display and navigation, but "navigation" is the expensive half:

| Where                                                                                                           | The assumption                                                                                                                              |
|-----------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| `dashboard.js` `buildGridCalendar` (`new Date(y, m, 1).getDay()`, `monthEnd`)                                   | The month grid is built from JS `Date`, which is proleptic Gregorian only. `Intl` can FORMAT another calendar but `Date` cannot ITERATE one |
| `stats/FrequencyKeys` (`MONTHS_PER_YEAR = 12`, `^\d{4}-\d{2}$`)                                                 | A year has 12 months and a 4-digit number                                                                                                   |
| `stats/FrequencyCharts` (`case YEAR -> MONTHS_PER_YEAR`, `anchor.lengthOfMonth()`)                              | 12 slots per year; ISO month lengths                                                                                                        |
| `java.time.YearMonth`, used across seven files for the "best month" stat, chart anchors and the month back-fill | `YearMonth` has no chronology at all - it is ISO by definition                                                                              |
| `log/ActionLogQueries` (`YEAR(l.logDate)`, `MONTH(l.logDate)`, `GROUP BY`)                                      | Month buckets are computed by the DATABASE, which cannot be taught another calendar                                                         |
| `time/Durations#breakdown`                                                                                      | Years/months come from ISO `Period.between`; a "month" is an ISO month                                                                      |
| `user/Language#dayMonthPattern`/`#monthYearPattern`                                                             | Both pin `IsoChronology.INSTANCE` when resolving the CLDR skeleton                                                                          |

### The support policy: tier 1 is in scope, tiers 2 and 3 are not

**Three tiers, and they differ by more than an order of magnitude.** The JDK ships `ISO`, `ThaiBuddhist`,
`Japanese`, `Minguo` and `Hijrah-umalqura`, and no Hebrew calendar at all.

1. **Year-relabelling only — Thai Buddhist, Japanese era, Minguo (ROC). → INTENDED TO BE SUPPORTED**, as and when a language wanting one is offered.
   Of these, only Thai is a CLDR DEFAULT for any locale; the other two are overrides a user might choose. **Until this tier lands, every language
   renders Gregorian** - including any whose CLDR default is not, which is a temporary state rather than a per-language decision. These share ISO's
   month boundaries and lengths exactly; only the year number and era label differ. **The month grid, every stat bucket, the month-bucketing query and
   every key format stay as they are**, and the civil-day question below does not arise, because the day boundary is midnight in all three. See "What
   tier 1 actually takes" below.

2. **Different month boundaries — Islamic (`Hijrah-umalqura`). → NOT SUPPORTED, and not planned.** Still 12
   months, but 29/30-day months that do not align with Gregorian ones, so a "month" is a different set of days.
   The calendar GRID must be rebuilt from the chosen chronology rather than from JS `Date`
   (`Temporal.PlainDate.withCalendar` is the modern answer; a library otherwise), `YearMonth` has to give way to a
   chronology-aware month type across the seven files above, and every month-bucketed statistic ("best month", the
   monthly averages, the year chart's 12 slots) changes meaning. **This is also the tier at which the database
   stops being able to help**: `MONTHLY_TOTALS_JPQL`'s `GROUP BY YEAR(...), MONTH(...)` has to become a daily read
   bucketed in Java, against the 65 ms / 4.8 ms measurement that put it there. And the civil-day decision above
   becomes load-bearing, because a Hijri day begins at sunset.
3. **Variable months per year — Hebrew. → NOT SUPPORTED, and not planned.** Everything in tier 2, plus a leap year
   has **thirteen** months (Adar I and Adar II), so `MONTHS_PER_YEAR = 12` is wrong as a constant and the year
   chart cannot have a fixed slot count. The JDK has no Hebrew chronology, so this tier additionally needs `ICU4J`
   or an equivalent — the same dependency question the plural work already carries.

> **A tier-2/3 language is NOT blocked from being offered.** The calendar is a separate axis from the language:
> Arabic is offered today and renders Gregorian dates, which is ordinary in Arabic software. Hebrew could be added
> the same way. What "not supported" means is that those languages get Gregorian dates and that is a stated
> limitation, not that the language is refused.

### What tier 1 actually takes

Measured, not estimated. `DateTimeFormatter.ofLocalizedDate(LONG).withLocale(th).withChronology(ThaiBuddhist)`
already renders `5 กันยายน 2569` — and drops the `ค.ศ.` ("Christian Era") marker that the ISO rendering is forced
to carry, because CLDR knows BE is Thai's own era. The `yMMMM` skeleton returns the same `MMMM y` pattern either
way. So on the Java side this really is "pass a chronology":

- **A CLDR LOOKUP for the default calendar, not a hand-written per-language switch.** This is the first rule of
  the checklist ("whatever CAN be derived from CLDR, is") and the calendar is derivable: CLDR carries a default
  calendar per locale in its `calendarPreferenceData`. Scanned across all 881 CLDR locales, the entire
  non-Gregorian universe is **two** entries wide:

  | CLDR default | Locales                                                                          | Tier              |
  |--------------|----------------------------------------------------------------------------------|-------------------|
  | `buddhist`   | `th`, `th-TH`                                                                    | 1 — supported     |
  | `persian`    | `fa`, `fa-IR`, `fa-AF`, `ps`, `ps-AF`, `ckb-IR`, `lrc*`, `mzn*`, `uz-Arab*` (12) | 2 — not supported |
  | `gregorian`  | the other 867                                                                    | —                 |

  So the lookup answers `gregorian` for `ja-JP`, `he-IL`, `ar-SA` and every European language on its own, with no
  arm to write and nothing to keep in step. **Japanese in particular is not a special case and must not be made
  one**: Japanese apps use 西暦 almost universally and the imperial era is an official-document convention, and
  CLDR already says exactly that — so a hand-written `ja-JP` override would be duplicating the lookup, not
  correcting it.

- **The lookup must be FILTERED by the supported tier, because CLDR can answer with a calendar we do not
  support.** Persian is Solar Hijri — 31/30/29-day months, so different month boundaries, so tier 2. The rule is
  therefore: take CLDR's answer when the app supports that calendar, else fall back to Gregorian and say so. A
  `Language` arm survives only as the OVERRIDE seam for a language whose users want something other than CLDR's
  default, not as the primary source.

  **That filter is built and running now** — `time/Calendars`, ahead of the rest of tier 1, because it is the half
  that has value while the answer is still always Gregorian. `Calendars#cldrDefault` holds the pinned CLDR table
  (the two rows above, keyed by longest matching prefix, since `ckb` is Gregorian while `ckb-IR` is Persian and
  `uz` is Gregorian while `uz-Arab` is Persian), `#isSupported` holds the supported set, and
  `#unsupportedCalendar` reports a language that is being downgraded. `AppLifecycle#verifyOfferedLanguageCalendars`
  walks `Language.values()` at startup and logs an ERROR per offending language:

  ```text
  Language 'th-TH' expects the 'buddhist' calendar, which is not supported - its dates will render in the
  'gregorian' calendar instead. See .claude/I18N.md 'Calendar systems'
  ```

  **It logs rather than throwing, unlike every other check in `AppLifecycle`**, and that asymmetry is deliberate: a
  wrong calendar is a degraded rendering, not an unusable deployment — the dates are still the right days, named
  in the wrong era — so refusing to boot would be out of proportion, and would make offering the language
  impossible rather than merely imperfect. The other startup checks guard against a deployment that cannot work at
  all. When tier 1 lands, `SUPPORTED` gains the year-relabelling calendars and the same class becomes the filter
  in front of the real chronology, with no new mechanism to build.

- **Getting CLDR's answer needs a decision of its own, because the JDK does not expose it.**
  `Chronology.ofLocale` honours only an explicit `-u-ca-` extension and returns `ISO` for a bare `th-TH` —
  verified. Three ways to close that, and the third is the one to prefer given the table above is two rows:
  ICU4J at runtime (the same dependency question the plural work carries); generating a table at dev time like
  `scripts/generate-source-messages.sh` does; or **a tiny table in `src/main` with ICU4J as a TEST-SCOPE
  dependency asserting it still matches CLDR** — zero runtime weight, and the test fails when CLDR moves rather
  than the app silently drifting. That last shape would suit the plural work too.
- **A `users.calendar` preference, `NULL` = follow the language**, mirroring `user/WeekStart` exactly and for the
  same reason: plenty of people read a Thai UI and think in Gregorian years, so the language predicts the habit
  rather than deciding it.
- **Thread the chronology through the four formatting sites** — `SubjectStatsExtensions#dateFmt`/`dateFmtNoYear`,
  `FrequencyCharts#fullLabel`, `DayLabels#spelledOut` — via `withChronology(...)`, and pass it to
  `getLocalizedDateTimePattern` in place of `IsoChronology.INSTANCE`.
- **`Diurnal.shortenYears`' regex is wrong for every tier-1 calendar** and must be re-derived: `\b(?:19|20)\d{2}\b`
  matches 2026 but not Thai 2569, Minguo 115 (three digits) or Japanese Reiwa 8 (one). Verified.
- **The front end's `Intl` calls take a `calendar` option** — `MONTHS_FULL`/`MONTHS_ABBR`, the toolbar title, the
  month-picker grid, and the year-jump input, which also PARSES a typed year and would be parsing a BE one.
- **Keys and URLs stay ISO.** `FrequencyKeys`' `^\d{4}$` / `^\d{4}-\d{2}$` window keys, `?date=`, and the
  dashboard's retained day are shared, bookmarked and posted back — they follow the timezone picker's rule
  ("submitted and stored as the raw id, only the visible label changes"), so they are converted for display only
  and their formats do not change. This is why tier 1 needs no key rework.

## Right-to-left support

`Language.dir()` is an **exhaustive switch** (not a ternary) returning `"rtl"` for `ARABIC` and `"ltr"` for
everything else — exhaustive so a future RTL language addition that forgets this method fails the **build**,
never silently defaults to `"ltr"` at runtime. Wired into `<html dir="{language:dir(language)}">` via
`LanguageExtensions` (`@TemplateExtension(namespace = "language")`).

**App chrome deliberately stays fixed-position regardless of language.** The navbar, Settings' two-column layout
and the dashboard's panel grid all pin `dir="ltr"` on their *structural* container, with `dir="{language:
dir(language)}"` re-asserted on every child region so content inside still fully localizes (RTL alignment,
mirrored in-card controls, phrase direction, digit glyphs) — a deliberate choice of positional consistency
("muscle memory" for chrome a user builds habits around) over full mirroring, asked of the user directly rather
than assumed. The calendar's own internal day-grid is explicitly excluded from this pinning and does mirror.
Calendar-toolbar navigation glyphs (the «‹›» chevrons) are a further, separate exception: by explicit request they
never mirror regardless of language, unlike the Stats page's frequency-chart prev/next glyphs, which do.

CSS Grid and Flexbox mirror for free (`grid-column-start`/flex `justify-content`/order are relative to the writing
direction's start line, not physically left-to-right) — the dashboard's outer grid, the calendar's internal grid
and the toolbar needed zero JS/template changes for this. The general convention for anything else is **logical
properties**: `ms-*`/`me-*`/`ps-*`/`pe-*`/`start-*`/`end-*` in Tailwind, `margin-inline-*`/`padding-inline-*`/
`inset-inline-*`/`text-align: start` in handwritten CSS (see `UI_PATTERNS.md` §7) — a physical-direction utility
or property anywhere in a template or `app.css` is a bug, not a style nit.

**One CSS gotcha worth knowing**: Tailwind's `ltr:`/`rtl:` variants compile to `:where(:dir(X),[dir=X],[dir=X] *)`
— the `[dir=X] *` clause matches *any* ancestor carrying that attribute, not the nearest one, unlike native
`:dir()` (which resolves nearest-ancestor, like normal inheritance). Once chrome containers pin `dir="ltr"` with
no `dir="rtl"` reassertion inside them, a competing `ltr:`/`rtl:` pair on the same element can have **both halves
match simultaneously**, with CSS source order silently picking the wrong one. The fix, used wherever this bites
(`.app-tooltip-center`, `.toggle-thumb`), is a handwritten class using the native `:dir()` pseudo-class directly.

**Bidi isolation**, four techniques depending on shape:

- `.js-digits`/`.js-num`/`.js-num-input` — `unicode-bidi: isolate`, protects a bare number from reordering
  relative to its surroundings (the same semantics as `<bdi>`).
- `.js-phrase` — `unicode-bidi: plaintext`, for a phrase mixing translated words with an embedded number/date;
  resolves the phrase's own base direction from its first *strongly*-directional character, self-adapting per
  phrase with no code change once content is translated. A phrase that is **only** a bare localized number (no
  accompanying word — e.g. a stat tile showing just `"٢٠٢٦"`) has nothing strongly-directional to find and falls
  back to LTR even on an Arabic page; `.js-phrase:dir(rtl)`/`:dir(ltr)` force `text-align` explicitly for this
  case, keyed on the ambient page language via `:dir()` rather than guessed from the element's own content.
- Literal Unicode bidi-isolate control characters (LRI `U+2066` / PDI `U+2069`), wrapped directly around a value
  inside a Java-built string, for the one case CSS can't reach: a plain-text `<option>` element, which accepts no
  markup at all (`UserSettings#offsetParen`, the timezone picker's UTC-offset parenthetical).

- **`dir="auto"` / `<bdi>`** — the read-only counterpart of the three above, and the one that fits a user's OWN
  free text: the browser derives the direction from the text itself, and the isolate stops that direction leaking
  into the line around it. **The two are the same thing** — the HTML UA stylesheet gives any element carrying a
  `dir` attribute `unicode-bidi: isolate`, which is exactly what `<bdi>` is defined as. So put `dir="auto"` on the
  element when it holds ONLY the user's value (`partials/action-row.html`, `partials/day-action-item.html` and its
  confirm-delete twin, `partials/admin-user-row.html`, `settings.html`'s display-name row,
  `partials/stats-cards.html`'s subject title, both stat-tile partials' `{label}`), and reach for the extra `<bdi>`
  node only where the value SHARES its element with something else (`partials/account-links.html`, where the name
  sits beside a tooltip; `partials/frequency-slot-tooltip.html`, where it leads a translated phrase).

  > Prefer `dir="auto"` where it fits, for a reason beyond tidiness: Playwright's `:text-is()` matches an element
  > by its own text NODE, so wrapping a value in `<bdi>` stops `h3:text-is("Notes")` finding the `<h3>` that
  > contains it. Three `stats.spec.ts` cases failed on exactly that.

**`.js-phrase` and `<bdi>` are complementary, and the tooltip is the worked example of why.** `plaintext` takes a
line's direction from its first *strong* character — so on a line shaped `{action name}: {translated "N times"}` that
character belongs to the USER's text, and a Latin action name silently chose LTR for the Arabic half that follows it.
An isolate is a neutral object to the paragraph around it, so wrapping the name removes its vote: the name still lays
out on its own terms, and the line's direction comes from the translated words. The same reasoning is why
`partials/language-option-label.html` wraps each half of "العربية (Arabic)" separately.

`dir="auto"` (browser-derived direction, not a CSS class) is the EDITABLE-control form of the same idea, and is what
every free-text input carries — the note `<textarea>` (`#note-input`), the action-name inputs, the display-name
input, the stat-rename input, and `partials/form-field.html`'s shared input. It is right there and `<bdi>` is not,
because the browser's own per-field mechanism also gets caret placement and arrow-key navigation right, which no CSS
technique can. It resolves to `ltr` for an empty field and, by specification, for a `type="password"` one.

**Directional GLYPHS are a separate question from layout, and the answer differs per glyph.** Layout mirrors for
free (grid/flex/logical properties), but a character only turns round under RTL if Unicode says it is
`Bidi_Mirrored` — `«‹›»` (U+00AB/2039/203A/00BB) are, `←`/`→` (U+2190/2192) are **not**. So the pagination arrows,
which point the way the link travels, are mirrored explicitly by `.dt-page-arrow:dir(rtl) { transform: scaleX(-1) }`
and marked `aria-hidden` (the adjacent word is the accessible name). The calendar toolbar's chevrons stay STATIC in
every direction by explicit product decision, recorded on `.cal-chevron` — do not "fix" them to match.

## Fonts

Nova/Standard/OpenDyslexic (the `Font` setting's three options) are all Latin-only. **Noto Sans Arabic** and
**Noto Sans JP** (Google Noto project, SIL Open Font Licence) are appended to the *end* of every `--font-body`/
`--font-display` CSS stack (`:root`, `.font-nova`, `.font-dyslexic`) as a script-coverage fallback — **not** a
fourth `Font` picker option, and **not** gated behind the account's UI `language`, since a day note is free text
that may be typed in any script independent of the viewer's own language preference (the same principle
`NOTES.md` states for translation). `unicode-range` already makes the browser's fetch conditional on a character
actually needing the font, so no separate gating mechanism was needed on top of it.

Both are subsetted from upstream variable fonts (not shipped whole — the raw Japanese file alone is ~9.5 MB):
Arabic to Google's own curated Arabic-script glyph set, Japanese to the JIS X 0208 "common-use kanji + kana"
cutoff — total served payload for both scripts, both weights, is ~2.3 MB, trivial against the image's own size. A
rare kanji outside that cutoff falls through to the OS's own CJK fallback. Generation is scripted and reproducible
via `scripts/generate-noto-fonts.py`; master files live in `assets/NotoSansArabic/`/`assets/NotoSansJP/` (each
with its own `OFL.txt`), served `woff2` under `src/main/resources/META-INF/resources/fonts/`.

The Dockerfile's jlink build also trims to a `--include-locales=en,es,ar,ja` custom JRE, but must keep the
**`jdk.localedata`** module — despite the name suggesting "extra," CLDR-backed `java.time`/`java.text` calls
(weekday/month names, timezone display names) silently fall back to English/Latin data without it, in the
packaged runtime only (never in `quarkus:dev`/`mvn test`, both of which run a full non-jlink-ed JDK). A permanent
regression test lives in the deployment-smoke tier (`tests/smoke/smoke.spec.ts`).

## What is and isn't translated

**Never translated, no exceptions**: brand and product names ("Diurnal", "GitHub", "Nova", "OpenDyslexic"), a
`#rrggbb` colour value, and a user's own data — action names, display names, custom stat labels, and note content
(per `NOTES.md`'s own boundary: a note is the user's own words, and translating it would need to be a deliberate,
separately-decided, user-initiated action in some future feature, never an automatic side effect of a language
setting). The complete, closed list of user-supplied fields this covers is the `text/TextFields` catalogue:
`ACTION_NAME`, `DISPLAY_NAME`, `STAT_NAME` (the catalogue's own *default* label for a stat is translated; a user's
rename of it never is), `EMAIL`, `PASSWORD`, `NOTE`.

**The one name that looks like user data and isn't** is the notes `StatSubject`'s. Every other stats subject is an
action, so its name is the user's own text; the notes subject is app chrome sitting in the same list, and its name
is translated (`AppMessages#statSubjectNotes`) at each of the five places it renders — the stats cards, the
dashboard summary, the chart legend, the chart's compare picker, and the bar tooltip. The record still carries the
English `name()` for the API. See "The template-side-switch rule" for the `.or()` shape this needs.

**"OIDC" and "API"** are spelled out phonetically in non-Latin-script languages (`ar-SA`, `ja-JP` — e.g. OIDC →
"أو آي دي سي" / "オーアイディーシー") rather than kept as bare Latin letters, matching how Arabic/Japanese
technical writing conventionally handles initialisms like USB/PDF/CD: an initialism carries meaning (spoken
letter names) genuinely inaccessible in a different script, unlike a brand name, which carries none to translate.
`es-ES` (Latin script, already directly readable) is unaffected. **"UTC" is the one exception kept as literal
Latin letters everywhere** — it's tied to a formal ISO 8601 offset notation ("UTC+03:00"), not merely spoken
jargon, matching the convention Windows/Google/Apple all follow even in fully-localized timezone pickers.

**IANA timezone ids** (`Europe/London`, `Pacific/Auckland`, …) are always **submitted and stored** as the raw id,
in every language — only the visible Settings label changes. `en-GB`/`en-US` show the bare id (it *is* the
`@Message` default text); `es-ES`/`ar-SA`/`ja-JP` show a **segment-mapped translation** — each path segment
translated independently and rejoined with the id's own `/` (e.g. `Pacific/Auckland` → `es-ES` "Pacífico/Auckland",
`ar-SA` "باسيفيك/أوكلاند") — rather than a CLDR metazone display name or a natural "City, Country" phrase, both of
which were tried and rejected (a metazone name isn't always the translated CITY, and English losing its own
readable id in an earlier design was a regression nobody wanted).

**CSV filenames and column headers** in the data export/import (`actions.csv`/`logs.csv`/`notes.csv`, `name`/
`colour`/`date`/`action`/`count`/`content`) are a fixed, never-translated cross-language file-format contract —
otherwise round-tripping an export between two accounts on different UI languages would break. A filename is
therefore set apart visually instead of being translated - **bold**, both where it LEADS an import-refusal row and
where it is named INSIDE the sentence (`importMissingMember`/`importUnknownAction` carry
`<strong>...</strong>` in the `@Message` value itself, since the name does not fall at the same point in the sentence
in every language). A **header row** (`importEmptyFile`/`importWrongHeader`) is set in `<code>` chips instead
(`.import-problems code`): it is a list rather than one word, and bold alone leaves `name` reading as more words of
the sentence rather than as an exact column name the file has to carry.

**One chip per column NAME, never one around the whole list** — the commas separating them are ordinary sentence
punctuation and stay outside the chips, so a chip marks exactly where one name starts and stops. Unlike the bolded
filename, that markup is composed in Java (`TransferInternalResource.chippedColumns`) and substituted in as a single
value, because the number of names is a property of the member rather than of the language: writing the chips into
each `@Message` value would ask every translator to keep a per-member chip count in step with `TransferFiles`. The
separator stays an **ASCII comma in every language** (not `،`/`、`) for the same reason the names themselves are never
translated — chips and commas together spell the literal header row the file has to carry.

Those four arms of `partials/import-reason.html` — and the finished reason in `partials/import-panel.html` — are
therefore rendered with `.raw`, since Qute escapes the *result* of a `{msg:...}` expression like any other value and
would otherwise print the tags. **`.raw` switches off the escaping of everything the entry rendered, its parameters
included** (a message bundle's own template has no content type, so Qute never escaped them on the way in either) —
so a raw entry may embed only fixed text, or text escaped by hand with `web/HtmlEscaping`'s `{value.escapeHtml}`
extension, as `importUnknownAction`'s uploaded action name is.

**The Swagger UI** (the admin-only `/admin/api-docs` page) is a third-party asset and stays untranslated — an
accepted scope boundary, not a gap being tracked.

**Rejection messages are one whole, atomic sentence per (field, failure-shape) pair**, never a
`{fieldLabel} {requirement}` substitution — word order isn't universal, and a substitution can reorder words but
can't fix grammatical *agreement* (e.g. a Spanish article/adjective must agree in number with its noun), which
needs the whole sentence to vary. `partials/text-failure-message.html` is the shared partial for this shape,
switching on `field.key` then `shapeKey`.

**Every rejection is therefore worded twice**, and the Java wording is marked `@NotUiFacing` (`http/NotUiFacing`) —
`TextOutcomeExtensions.message`, `TextFieldExtensions.lengthMessage`, `ImportService.message`,
`ProfileService.message`, `RegistrationService.message`/`label`, `PasswordChangeService.message` and the three
`UserSettings.*_MESSAGE` constants. That text goes to an `/api/v1` body or a log, never to a page, which is why it
is hardcoded English with a concatenated plural `"s"` and no bundle lookup: what it says is free, because the
language setting does not govern it. **A web or internal surface must never call one** — it renders the partial (or
its own `msg:` entry) instead. `NotUiFacingTest` fails if a `*WebResource`/`*InternalResource` references an
annotated member, if one is also a Qute `@TemplateExtension`, or if the marker lands on a `private` member (the
constraint is about reach from another class, and a surface often sits in the *same package* as the service it
calls, so package-private still needs marking). Before it existed, a stray English sentence in a translated page
was caught by nobody: nothing throws, and only a reader of that language would see it.

**The same rule applies to any sentence, not just a rejection**, and two places had drifted from it:

- The registration form's missing-fields banner was `{msg:missingFieldsPrefix} {msg:missingFieldWord(n)}:`, joined
  by the template. Japanese is verb-final and has no "prefix" for a bare noun to follow, so its only workable
  translation of the prefix was the *whole* sentence — after which the noun was still appended to it, rendering
  「次の項目を入力してください 項目:」. Now one `missingFieldsIntro(count)` carrying the complete sentence per plural
  branch.
- The per-section page-size controls read `{msg:fewerItemsPerPageFor(section)}`, splicing `PageSection`'s English
  label into a translated frame — half-translated in every non-English language, and unfixable for a language whose
  preposition contracts onto the following noun (Arabic's لـ). Those three entries are gone: the visible row label
  IS the input's accessible name (a plain `<label for>`, which an `aria-label` was overriding), and the ± buttons
  take their section context from a `role="group"` labelled by that same label, so they can reuse the general row's
  existing generic captions.

**A sentence wrapping an ELEMENT is the same fault**, and five more had it — the template set one entry before the
element and another after it, which fixes that element at the position English puts it in. All five now carry a
`{placeholder}` the template substitutes the whole element into, the server-side counterpart of the lockout banner's
`%CLOCK%` above, and each is rendered `.raw`:

| Was                                    | Is now                          | What the split could not express                                                                                        |
|----------------------------------------|---------------------------------|-------------------------------------------------------------------------------------------------------------------------|
| `lastSeenPrefix` + `agoSuffix`         | `lastSeenActivity(clock)`       | Arabic/Spanish put "ago" BEFORE the duration (منذ, *hace*), so both folded it into the prefix and left the suffix empty |
| `showingLabel` + `ofLabel`             | `showingOfTotal(shown, total)`  | Japanese writes the pair as a bare `3/20`; "of" is not a word every language puts between two numerals                  |
| `importHelpPrefix`/`Emphasis`/`Suffix` | `importHelp()`                  | which word carries the warning is the translation's choice, and the joins forced a space either side of it              |
| `connectedToPrefix`                    | `connectedToProvider(provider)` | the sentence's closing full stop was template markup, so no language could drop or change it                            |
| `setupIntro`                           | `setupIntro(appName)`           | the brand name was a span the template wrote FIRST, and Japanese attaches its particle straight onto it                 |

An empty entry is the tell. Arabic's and Spanish's `agoSuffix` were both correctly blank, which a translation
platform cannot store and reports as untranslated — and twice a round trip "fixed" it, once to the English `ago` and
once to `atrás`, each rendering the word twice. **An entry that some language must leave empty is a split.**

Where the element carries a value it is composed by `web/MessageMarkup` (the OIDC provider link, the two `.js-digits`
counts) rather than by the template, which cannot build markup; where it is fixed the template passes the literal.
Either way `.raw` switches escaping off for the whole entry, so `MessageMarkup` escapes what it embeds — see
`HtmlEscaping`. Markup stays OUT of a bundle value except where the tag is part of the WORDING, which is why
`importHelp` keeps its `<strong>` inline exactly as `importMissingMember` keeps its bolded file name.

**A substitution is still correct where the argument is genuinely a NAME** — `showFrequencyGraphFor(subjectName)`,
`stopComparing(subjectName)`, `duplicateActionName(name)` all interpolate the user's own action name, which has no
translated form and no agreement to satisfy.

## Translation content

Each offered language beyond English picked its own register once and applies it consistently: Spanish uses
informal **tú** throughout (matching consumer-SaaS convention over formal *usted*); Arabic uses Modern Standard
Arabic with masculine-default second-person address (matching the near-universal convention in Arabic software
UI, since Arabic has no true gender-neutral option); Japanese uses polite ***teineigo*** (です/ます) for sentences
and plain noun form for short button/label text, both coexisting by entry kind rather than one rule applied
uniformly. Domain vocabulary (streak, gap, action, dashboard, …) was picked once per language and reused
everywhere rather than translated key-by-key, so the same concept always reads the same way.

`msg_en-US.properties` is a **full duplicate** of the bundle's key set (currently ~390 keys), not a sparse
spelling-only diff — a deliberate reversal from an earlier, smaller design, made specifically so CrowdIn/Weblate
tooling (below) has a complete file to manage. It differs from the `en-GB` default only in American spelling
(`colour`→`color`, `authorised`→`authorized`, and similar) and a small number of genuinely different American
phrasings; everything else is generated by joining those overrides onto the English export.

## Translation tooling

**`scripts/generate-source-messages.sh`** (+ `scripts/GenerateSourceMessages.java`) reflects over the compiled
`AppMessages` class — not a source-text parse, which sidesteps multi-line concatenated `@Message` values — and
writes sorted `key=value` lines to **`translations/msg_en-GB.properties`**. This file is a **one-way export**,
never read by the running application; re-run the script after any English wording change, before syncing to a
translation platform.

**A live CrowdIn project is wired up**, and the work is split between three mechanisms that must not be confused:

- **The CrowdIn GitHub integration** (configured in CrowdIn's own UI, nothing in this repo) owns **downloads**. It
  raises a PR from an `l10n_master` branch carrying each updated `src/main/resources/messages/msg_<locale>.properties`.
  It also still scans `translations/msg_en-GB.properties` as the source, but is no longer the thing this repo relies
  on to get a source change *to* CrowdIn — see the next bullet.
- **`../crowdin.yml` + `.github/workflows/crowdin_upload.yml`** own the **one thing the integration cannot do**:
  push the repo's own translations back with `--import-eq-suggestions`. CrowdIn DISCARDS an imported translation
  whose text equals its source string unless that flag is set, and the flag is a per-upload option rather than a
  project setting the integration can be given. `en-US` is 392-of-404 identical to `en-GB`, so without it that
  language reports hundreds of untranslated strings, and an export set to skip untranslated strings drops those
  keys outright. Its path filter keeps it to the moments the repo is the newer side.

  **It uploads the SOURCE file as well (`upload_sources: true`), and that is load-bearing rather than tidiness.**
  Leaving the source to the integration splits one logical change across two systems that run at different times:
  the workflow fires within seconds of the push, the integration syncs the source minutes to hours later, and
  **CrowdIn drops the translations of any string whose source text changed**. So every commit that REWORDS an
  English string used to lose that string's translations — the upload landed them against the old source, the
  later source sync invalidated them, and the job had already reported success. It cost `atLeastCharacters`,
  `atMostCharacters` and `noteLength` exactly this way when they gained their `{#if count == 1}` plural branches.
  One CLI invocation uploads sources first and then the translations against them, closing the window. The two
  paths must stay identical for this to update rather than duplicate the file, which is what `preserve_hierarchy`
  in `crowdin.yml` is for; the `workflow_dispatch` dryrun input is how to re-confirm that after any layout change.

  **Do not "fix" a lost upload by putting this workflow on a schedule.** An upload REPLACES what CrowdIn holds, so
  a timed run will sooner or later fire while CrowdIn is the newer side and discard real translator work. Re-run it
  by `workflow_dispatch` once the source is known to be current instead.
- **`.github/workflows/translations.yml`** owns the **PR-side guard**, and is the repo's only `pull_request`-triggered
  workflow (and the only one watching a branch other than `master`) — deliberately, because the translated bundles
  arrive as a CrowdIn-authored PR from `l10n_master`, so running `AppMessageCoverageTest` (below) on the push
  *after* the merge reports a break that is already on `master`.
  That is not hypothetical: the escaped-`{\#if` corruption below reached a Docker build exactly that way. It carries
  **no `paths:` filter and no `head_ref == 'l10n_master'` condition**, so a hand edit to a bundle in any other PR meets
  the same guards — and, more importantly, so that it can be a **required status check** on `master`. Branch protection
  has no concept of a path filter: a required check that a filter skips never reports, so GitHub holds the PR at
  "Expected - waiting for status to be reported" and it can never merge. **Re-adding a `paths:` filter therefore means
  dropping the required-check rule first**, or every PR that does not touch a bundle blocks forever. The job is a single
  unit-test class, so running it on every PR is cheap. The required check's name is the JOB name,
  `Translation Bundle Analysis`, not the workflow's.

**Approving a translation in CrowdIn pushes nothing on its own.** The integration writes to `l10n_master` only when
it *syncs* — on its own schedule, or immediately from CrowdIn's UI at Integrations > GitHub > **Sync Now** — and if a
PR from an earlier sync is still open, the new commits land on that same branch rather than opening a second one.
Whether approving changes the exported file at all depends on Settings > Export > "export only approved
translations": with it ON, approval is what makes a string eligible, and the sync after approving is the moment the
PR appears; with it OFF, translated-but-unapproved strings were already being exported and approving alters nothing.
**That same project setting decides the correct value of the upload workflow's `auto_approve_imported`**, which is
`false` today — marking a string approved means a review happened, which an automated upload is not, so it may only
be flipped true in a project where unapproved translations never ship anyway.

**A CrowdIn-opened PR does not trigger `translations.yml` on its own, which is why that workflow also watches**
**pushes to `l10n_master`.** Measured from the API across PRs #3–#6: `opened` produced no run, and **closing and
reopening the PR produced none either** (tried twice on #5) — despite appearances, that is not the workaround it
looks like. The only two runs before the `push` trigger came from the `synchronize` after a web-UI **Update branch**
press. Since the check is REQUIRED on `master`, never reporting means the PR sits at "Expected - waiting for status
to be reported" and cannot merge, so the run has to reach the head commit some other way; a push-event run posts
against that same head SHA.

**The CAUSE is not established, and should not be written up as though it were.** Ruled out by evidence: merge
conflicts (#5's head merges cleanly into every master tip in that window; #6 reports `mergeable_state: clean`) and a
missing workflow file on the head branch (`dbdb973` carries it). The obvious suspect is the suppression that stops a
`GITHUB_TOKEN`-authored PR from getting checks, with CrowdIn raising the event through the linked account's token —
but it does not fit, because the reopens were done by a human in a browser and were equally silent. The other
candidate is the `paths:` filter this workflow carried until `3c5d78b`, which should have matched a CrowdIn PR
anyway. Two tests settle it: whether CrowdIn's next push to `l10n_master` produces a run (if not, the block follows
the token, and the fix is to raise the PR from CI with a PAT instead of via the integration), and whether a
**human-opened** PR runs on `opened` — the latter is what a future outside contributor's PR depends on, so it is
worth knowing regardless of CrowdIn.

**Merging that PR then trips `crowdin_upload.yml`'s own path filter, which is the design rather than a loop.** The two
sides are identical at that moment, so the upload is a no-op *except* for the equal-to-source strings CrowdIn discarded
on the way in — which is the entire reason the workflow exists.

**Everything CrowdIn's exporter does to a downloaded file is the repo's problem to absorb**, and two of those are
guarded rather than trusted — see `AppMessageCoverageTest` below. The others are accepted: each file comes back
alphabetised and carrying the source file's own comment header, so per-file headers and `AppMessages` declaration
order do not survive a sync and are not worth restoring.

**`web/AppMessageCoverageTest`** is the completeness guard: it reflects over `AppMessages` for the bundle's full
key set and asserts each offered non-default locale's `.properties` file carries exactly that set. It reads each
file via an explicit UTF-8 `InputStreamReader` (not the `Properties.load(InputStream)` overload, which defaults to
ISO-8859-1 and would corrupt non-Latin content) — added after a real gap (`es-ES` missing 14 timezone keys)
shipped unnoticed once, to make that class of mistake fail the build instead.

**Two of its guards exist purely to catch what a CrowdIn download does to the files**, and both read the RAW file
text rather than going through `Properties` (which would already have undone the very escaping being looked for):

- **Platform escaping.** CrowdIn's properties exporter writes `{#if` as `{\#if`, `==` as `\=\=`, `:` as `\:`, and
  doubles a single quote to `''` in any value holding a placeholder. A localized value is a **Qute template**, not
  a MessageFormat pattern, so all four are corruption: Qute reads the escaped `{#if` as literal text, leaving its
  `{/if}` unopened, and the Quarkus augmentation step fails the whole build with an `analyzeTemplates` stack trace
  naming only the first template it happened to reach. This names every affected key at once instead.

  **The two settings behind it are named, and both default ON**, so this recurs until they are explicitly off:
  `escape_special_characters` (default `1`) backslash-escapes `=`, `:`, `!` and `#`; `escape_quotes` (default `3`)
  doubles a single quote in any value holding a placeholder. Both are pinned to `0` in `../crowdin.yml`, but that
  only asserts them when something uploads the source through that config — **the EXPORT is what writes the
  bundles, and it reads the settings the project holds**, so confirm them in the CrowdIn UI too. The guard is the
  backstop, not the fix. Seen in PR #7, where `escape_special_characters` alone corrupted 104 lines across all
  four bundles (`{#if` → `{\#if`, `==` → `\=\=`, `#6366f1` → `\#6366f1`); the quotes were untouched, which is
  how you can tell the two settings are held separately rather than as one switch.

  **Confirm the fix from a PR diff that actually has content — a quiet PR proves nothing.** PR #7 looked like a
  regression of a setting turned off earlier, and was not: PR #4 a day before carries the identical escaping, and
  the two PRs between them added 1 and 0 lines, so neither could have shown it either way. Note also that the
  project holds a version BRANCH, and file settings belong to the file — a setting applied to a root copy, or to
  a different branch's copy, leaves this one on its default.
- **Section balance.** Every `{#if}` a value opens must be closed. This is the half that still matters once the
  exporter is configured correctly, since a translator can unbalance a plural entry by hand just as easily.

**That same test also pins the export itself** (keys *and* values, against the `@Message` annotations it was
generated from). Nothing in the running app reads `translations/msg_en-GB.properties`, which is exactly why it goes
stale unnoticed — it had already drifted a key behind. A key missing *there* is a string a translation platform
never offers anyone, which is how a language quietly ends up rendering English for it. If that test fails, the fix
is to re-run `scripts/generate-source-messages.sh`, not to hand-edit the file.

## Pseudolocale

**`en-XA` is English mechanically disguised, and it is the one "language" here nobody speaks.** Every letter is
replaced with an accented look-alike, every value padded by about a third, and every value wrapped in `⟦ ⟧`. That
makes three things visible at a glance which no real translation shows:

| What you see                            | What it means                                                           |
|-----------------------------------------|-------------------------------------------------------------------------|
| A string still reading as plain English | It never went through the bundle - it is HARDCODED                      |
| A layout that breaks or wraps badly     | It only ever saw English and cannot take a real translation's EXPANSION |
| A value missing its closing `⟧`         | Its container TRUNCATED it                                              |

The middle one is the reason it exists: `I18N.md`'s own test-coverage section records text-expansion QA as manual
screenshots per language, which only ever asks the question for the four languages actually translated. The
pseudolocale asks it for a translation nobody has written yet, and German and Finnish routinely run a third longer
than English.

**Reaching it is deliberate, because `Language.PSEUDO` is marked `developerOnly()` and `pickerOrder()` filters it
out.** It is still a fully valid stored value - `isValid` accepts it and `fromAcceptLanguageHeader` resolves it -
so:

```bash
# a signed-in page
curl -X PATCH .../api/v1/users/me -d '{"preferences":{"language":"en-XA"}}'
# a logged-out one (login, register, the setup wizard)
curl -H 'Accept-Language: en-XA' .../login
```

`XA` is a user-assigned region code, so CLDR carries no data for it and every date, number and digit glyph behaves
exactly as English does. That is deliberate: it keeps the disguise confined to the message bundle, so anything odd
on screen is a bundle or layout problem rather than a formatting one.

**The bundle is GENERATED - never hand-edit it.** `scripts/generate-pseudo-messages.sh` reads
`translations/msg_en-GB.properties` (so run `scripts/generate-source-messages.sh` first after any `@Message`
change) and writes `src/main/resources/messages/msg_en-XA.properties`. Output is committed, matching the pattern
`generate-source-messages.sh` and `generate-noto-fonts.py` already set.

**Why the generator is a character walk rather than a regex.** A message value is itself a small Qute template, so
it may hold an expression (`{count}`, `{#if count == 1}`, `{count.arabicPluralCategory}`) or markup (`<strong>`)
the renderer has to read back exactly. Accenting a letter inside one turns a working bundle into a render-time
failure; padding inside one corrupts a parameter name. So every `{...}` region and every `<...>` tag is copied
through untouched and only the literal text between them is disguised - which is precisely the text a translator
would have translated. `AppMessageCoverageTest` (placeholder parity) and `AppMessagesIT` (renders every method
against every locale) both cover `en-XA` automatically, so a generator that broke either would fail the build.

- **`tests/smoke/smoke.spec.ts`** carries a permanent regression test against the packaged Docker image: sets a

- **`AppMessagesIT`** renders real content per locale (including a worked pluralisation example), and includes a
  reflection-driven test that renders **every** bundle method with dummy arguments against every translated
  locale, asserting nothing throws — a stray unbalanced `{#if}` or a typo-ed parameter name in a 380+-line

  rule".
- **Text-expansion / visual QA is manual, not automated** — real Playwright screenshots (desktop and a 390px
  mobile viewport) taken across the Actions table, calendar toolbar and full Settings page per language, reviewed
  by eye rather than asserted on. Right-to-left mirroring and the preview-tile pickers held up cleanly at both
  sizes across every language checked; the one place translated captions visibly truncate (the Settings "Action
  stats" picker row, at the 390px width) already truncates in English too and is already mitigated by its own
  long-press/hover tooltip, so this is an accepted, pre-existing tradeoff rather than a translation-specific
  regression.

## Known limitations

- **The Swagger UI stays untranslated** — an accepted third-party-asset boundary, not planned to change.
- **`ArabicPlural` is the one piece of LANGUAGE-SPECIFIC Java in the i18n surface, and it is kept deliberately.**
  Everything else generalizes from a new `.properties` file; this does not, so a second language with a
  non-two-way plural system needs a generic CLDR-backed `pluralCategory` rather than a sibling class. Declined
  while Arabic is the only language needing it — the designated replacement (`net.xyzsd.plurals:cldr-plural-rules`,
  26 KB, measured identical to `ICU4J` for every language we would plausibly add), the rejected alternatives and
  the trigger to revisit are all in step 4 of "Adding a new offered language". Not a functional gap today.
- **`dir="auto"` covers only the note-writing textarea, not other read-only display of a user's own free text**
  (an action name in the Actions table or day panel, a display name, a custom stat label). This was planned
  alongside the note-box work but never carried out — a user-typed name in a script opposite to the current UI
  language has no explicit bidi handling today and simply inherits the page's own `dir`, which is usually but not
  always correct (see "Right-to-left support" for the technique to apply if this is picked up).
- **Collation is applied where it was found to matter (see "Locale-aware formatting"), not audited exhaustively
  across every list in the app** — a new paginated text list should be checked against the same question rather
  than assumed to already be covered, *including* one whose text ordering is only an implicit tie-break behind a
  numeric sort (the shape the dashboard day panel had).
- **Arabic's full CLDR plural branching is applied where the count genuinely varies**, not to every message with a
  number in it. `importWrongColumnCount`/`showingFirstOfTotalProblems` count something the input decides, so they
  carry the six-category `arabicPluralCategory` chain; `passwordLength`, `importTooManyEntries` and the five
  `*NoStackedMarks` always render the same compile-time constant, so their single form is correct for the only value they
  ever show. Messages with no counted noun at all (`atLine`, `pageOfTotal`) need nothing either way.

  > **"A single form is correct" means correct for THAT VALUE's category, which has to be checked against
  > `ArabicPlural`, not assumed.** Six entries were wrong on exactly this and have been fixed: `actionNameLength`
  > renders 100 (`other`, singular genitive) but carried the `many` form `حرفًا`; the five `*NoStackedMarks` render
  > 8 (`few`, the plural of paucity) but carried the singular `علامة`; `atMostCharacters` renders 128 (`many`) but
  > carried the `few` form `أحرف`. English is not immune either — `atLeastCharacters` renders `PASSWORD_MIN_LENGTH`,
  > which is `1`, and read "At least 1 characters" on the register card in English and Spanish alike.
  > **Changing one of these constants means re-checking every entry that renders it**, in every language with more
  > than one plural form. Where the value can vary at all, use the chain instead and the question never arises:
  > `atLeastCharacters`/`atMostCharacters` (a field's own bound, which may legitimately be 1) and `noteLength`
  > (per-deployment configurable — `NOTE_MAX_LENGTH`, range `[1, 100_000]`) now all do.
- **Every date is rendered in the GREGORIAN calendar, in every language** — a deliberate product boundary, not an
  unset option. A Thai user sees `5 กันยายน ค.ศ. 2026` rather than the Buddhist-era 2569 they expect. What is and
  is not affected, and what each of the three tiers of calendar support would actually cost, is its own section:
  "Calendar systems".
- **A user-chosen weekday name is not translated anywhere it is stored** — `users.week_start` holds `'monday'`, an
  English-looking token that is a storage value like a theme's `'dark'`, never display text (the WORD comes from
  CLDR at render time; see "Locale-aware formatting"). Read it as a value, never render it.

## Extending this

### Adding a new offered language

**This checklist is the WHOLE process, and it deliberately covers every locale-shaped axis rather than just the
strings** — direction, plurals, date patterns, digit glyphs, collation, fonts, register, and the calendar. A
language is not "a new `.properties` file"; the file is one step of eight, and the steps that are easy to forget
are the ones with no file to create. Two properties make that workable and are worth preserving in anything added
here:

- **Whatever CAN be derived from CLDR, is** — date patterns, digit glyphs, month/weekday names, collation,
  plural categories. Those need no entry at all, which is why the list is as short as it is.
- **Whatever CANNOT is a compiler-enforced arm on `Language`** — `dir()` and `dateRangeSeparator()` today. A new
  constant that forgets one fails the BUILD rather than silently taking English's answer. **Prefer that shape for
  anything new**: an exhaustive switch beats a lookup table with a default, and both beat a convention nobody
  reads.

1. Add a constant to the `Language` enum: value tag, autonym label, a `dir()` switch arm and a
   `dateRangeSeparator()` one (both compiler-enforced — a missing arm fails the build), and a
   `BASE_LANGUAGE_FALLBACK` entry. The date patterns need nothing —
   `dayMonthPattern()`/`monthYearPattern()` resolve themselves from CLDR (see "Locale-aware formatting"); add the
   new language to `LanguageTest`'s four pattern tests to pin what CLDR gave it.
2. **If the new language is distinguished by SCRIPT rather than by region, stop and read this first** — Chinese
   (`zh-Hans`/`zh-Hant`), Serbian (`sr-Latn`/`sr-Cyrl`), and any second such pair. Three things in the machinery
   assume a language is identified by its base subtag, and none of them says so:
   - **`BASE_LANGUAGE_FALLBACK` cannot express the distinction at all.** `fromBaseLanguage` keys on
     `range.getRange().split("-", 2)[0]`, so `zh-Hant-TW` and `zh-Hans-CN` both reduce to `zh` and one of them
     gets served a script it cannot read. That is right for `es-MX`→`SPANISH` (mutually intelligible regional
     flavours) and wrong here, and the map's SHAPE — one entry per base language — has no room for the answer.
     Changing it is a data-structure change, not a new entry.
   - **`englishLabel()` drops the script.** It is `locale.getDisplayLanguage(ENGLISH)`, which answers `"Chinese"`
     for both `zh-Hans` and `zh-Hant`, and `"Serbian"` for both Serbian scripts. Since `showsEnglishLabel()` is
     `!label.contains(englishLabel)` and `中文` does not contain `"Chinese"`, the picker would render **two rows
     both reading "中文 (Chinese)"**, which a user cannot tell apart. **The qualifier therefore belongs in the
     AUTONYM**, exactly as the two English entries already do it (`"English (UK)"`, not a smarter English name) —
     so `"中文（简体）"`/`"中文（繁體）"`. Nothing enforces this; it is a convention, and this is where it is written down.
   - **The bundle FILENAME for a script-qualified tag is unverified** (`msg_zh-Hans.properties` vs
     `msg_zh_Hans.properties`). Pin it before relying on it: a wrongly-named bundle compiles, deploys, registers
     with CDI and silently renders English with no warning anywhere — see "Message bundles" for the time that
     shipped.
3. Add the tag to `quarkus.locales` in `application.properties` (Quarkus validates every `.properties` file's
   locale against this list at build time).
4. Add `src/main/resources/messages/msg_<locale>.properties` with the full bundle key set —
   `AppMessageCoverageTest` fails loudly if any key is missing, if any is orphaned, or if any translated value drops
   a `{placeholder}` its English default uses. It picks the new language up automatically: its locale list comes
   from `Language.values()`, so there is no second list to remember to extend (there used to be, and a guard that
   quietly does not run for the new language is worse than no guard).
5. **Look up the new language's actual CLDR plural rule before writing a single pluralised entry.** Everything
   else on this list generalizes on its own; this one does not. The branching itself is per-file and scales fine —
   a `{#if}` chain inside each `@Message` value, which is content a translator writes, not code — but the *rule*
   deciding which branch a count falls into may need Java, and today the only Java there is `web/ArabicPlural`,
   hardcoded to CLDR's `ar` rules and nothing else.

   **Counting the categories is the WRONG test**, and it is the obvious one to reach for. Ask two questions
   instead:
   - **Does the rule use MODULO?** Qute's expression language has `==`, `!=`, `>`, `&&`, `||` and parentheses (see
     `duration`, which uses several) but no `%`. A rule without `%` is writable inline in the properties file and
     needs no Java at all, **however many categories it has** — Welsh has SIX (`zero: n=0`, `one: n=1`, `two: n=2`,
     `few: n=3`, `many: n=6`) and needs nothing; Czech and Slovak have four (`few: i = 2..4`) and need nothing;
     Irish and Hebrew likewise. A rule with `%` needs the swap below: Arabic, Polish, Russian, Ukrainian, Croatian,
     Serbian, Lithuanian, Latvian, Romanian, Maltese.
   - **Can this app's counts REACH the category?** Spanish, French, Italian and Portuguese are all technically
     three-category, but their `many` rule is `i % 1000000 = 0` — it fires only at exact multiples of a million,
     and nothing here counts that high (`ActionLog.MAX_DAILY_COUNT` is 999, `NOTE_MAX_LENGTH` caps at 100,000).
     That is *why* the existing Spanish two-way split is correct, and it is worth knowing before someone "fixes" it.

   **And do not assume a two-category language splits at 1.** Hindi, Persian and Danish put ZERO in the singular
   (`one: i = 0 or n = 1`), so a copied `{#if count == 1}` renders "0 दिन" wrongly. Write `{#if count == 0 || count == 1}`.
   The rule text for any locale is one line to check: `PluralRules.forLocale(locale).getRules("one")`.

   **Never write a second `<Language>Plural` class beside `ArabicPlural`.** If the rule needs modulo, take the
   decision below instead.

   **The decision, deliberately deferred rather than forgotten:** replace `ArabicPlural` with one generic
   `pluralCategory` that resolves the CLDR category for whatever locale is rendering, so no language is named in
   Java ever again. **The second language on the list above is what flips the trade** — raise it then, rather than
   hand-rolling a second rule set.

   **Use `net.xyzsd.plurals:cldr-plural-rules`, not `ICU4J`.** It is 26 KB, six classes, zero dependencies, no
   data files (the rules are generated Java), Apache-2.0/MIT, Java 11 target, and its API is a direct swap:
   `PluralRule.createOrDefault(locale, PluralRuleType.CARDINAL).select(count)`. It was measured head to head
   against `ICU4J` 77.1 over every language the JDK knows — 251 languages, 301,451 integer checks, **99.95%
   agreement**, and **byte-identical for all five languages offered today and for every plausible next addition**
   (`de`/`fr`/`pt`/`it`/`nl`/`pl`/`ru`/`cs`/`cy`/`tr`/`hi`/`ko`/`zh`). Its one caveat: Maven Central's newest
   release is `41` (June 2022), so three real languages have since drifted — Hebrew dropped `many`, Romanian
   widened `few`, Maltese gained `two`. Check that list against the language being added, and check whether a
   newer version has shipped (the repo carries a `cldr48` tag that was never published).

   `ICU4J` is the fallback if that library's staleness ever matters — it is Unicode Consortium-published and
   tracks CLDR — but it costs 13 MB in-jar / 31 MB unpacked / 5,746 files, of which **10.3 MB is `icudata`**
   (collation, transliteration, currencies, zone names) that nothing here would touch; `plurals.res` is 6 KB of
   it. **Do not try to shade it down.** That was attempted: a class-load trace across all 1,189 locales says only
   150 classes are reachable (292 KB), but ICU resolves classes and `.res` bundles lazily and reflectively, so the
   minimised jar failed on `LocaleFallbackData`, then `keyTypeData.res`, then `likelySubtags`, and the iterative
   closure reached 1,206 entries / 2.4 MB without converging. That keep-list would need re-deriving by hand on
   every ICU upgrade and would fail at runtime, not at build time, when it drifted.

   A third option, if a third-party dependency is unwanted at all: generate a small rules table from CLDR with a
   dev-time script and check it in beside a compact evaluator — the pattern
   `scripts/generate-source-messages.sh` and `scripts/generate-noto-fonts.py` already use here. Zero dependencies,
   at the cost of owning the generator and the evaluator.

   Two things to know going in, whichever is chosen: the generic form needs the RENDER LOCALE at a
   `@TemplateExtension`, which has no locale in scope — the design is a Qute `ValueResolver` reading
   `MessageBundles.ATTRIBUTE_LOCALE` via `EvalContext.getAttribute` (both APIs exist; that the attribute reaches a
   message-bundle sub-render is unproven, and `AppMessagesIT` settles it in one run). And the library's
   category-set accessor (`PluralRules.getKeywords()`, or its equivalent) would let `AppMessageCoverageTest` assert
   a locale covers every category it actually uses — a guard that does not exist today, and the reason six wrong
   Arabic forms once shipped unnoticed (see "Known limitations"). Note that `ICU4J`'s `MessageFormat` stays
   rejected regardless of any of this: its plural syntax uses a second `{}` grammar that collides with Qute's own.
   The plural RULES are the only thing wanted from any of these.
6. **Check whether the language wants a non-Gregorian CALENDAR** — the axis with no file to create, and so the
   one most easily missed. Today the app is Gregorian-only in every language (see "Calendar systems"), so:
   - **You do not have to work this out by hand — the app tells you.** `AppLifecycle` walks every offered language
     at startup and logs an ERROR naming any whose CLDR calendar it cannot render (`time/Calendars`), so adding a
     language with a calendar of its own is announced on the first boot rather than discovered by a reader.
   - **Most languages want nothing.** Every European language, Arabic (Gregorian dates are ordinary in Arabic
     software), Japanese (西暦 is near-universal in apps; the imperial era is an official-document convention).
     Note it and move on.
   - **A tier-1 calendar — Thai Buddhist, Minguo, Japanese era — is IN SCOPE**, and the work is scoped in
     "Calendar systems" → "What tier 1 actually takes". Once that lands the default is a CLDR LOOKUP filtered by
     the supported tier, not a per-language decision, so this step becomes "confirm CLDR's answer is one we
     support" rather than "pick one": a `users.calendar` preference defaulted from that lookup,
     `withChronology(...)` at four formatting sites, a `calendar` option on the front end's `Intl` calls, and a
     re-derived `shortenYears` regex. Keys and URLs stay ISO.
   - **A tier-2/3 calendar — Islamic, Hebrew — is NOT supported and not planned.** This does not block the
     language: offer it with Gregorian dates, exactly as Arabic is offered today, and record it as a known
     limitation rather than treating it as a blocker.
7. If the script isn't Latin, add a font (see "Fonts") — the `unicode-range` mechanism is generic and needs no
   gating logic. RTL needs nothing extra either; `Language.dir()` and the logical-properties convention already
   generalize to a second RTL language.
8. Pick and document the register/formality convention for the language once (see "Translation content"), and
   apply it consistently rather than per-string.

A dynamic, filesystem-scanned language list (drop a file in, no code change) was considered and rejected:
`quarkus.locales` is validated at **build time**, so an unlisted file wouldn't even compile in as a recognized
locale, and `dir()`/the date patterns/the autonym label are structural facts a translated `.properties` file has
no natural home for — keeping them as compiler-enforced exhaustive switches trades away nothing a runtime lookup
would actually gain.

### Adding a new translatable string

Add a new `@Message`-annotated method to `AppMessages` (English inline as the default value), call it from a
template as `{msg:methodName}` / `{msg:methodName(args)}`, and add the key to every `msg_<locale>.properties`
file — `AppMessageCoverageTest` will fail if a language is missing it. Two footguns worth knowing before touching
an *existing* method's signature:

- A `@Message` method's parameter type must match what's actually passed — Quarkus's generated bundle resolver
  **casts** the argument to the declared type rather than widening/narrowing it, so a `Long` reaching an
  `int`-typed parameter (or vice versa) throws `ClassCastException` **at render time**, invisible to a normal
  build (Qute's build-time validation checks the expression parses and the method exists, not argument-type
  compatibility).
- After changing a widely-referenced method's signature, run a full `mvn clean compile test-compile` rather than
  relying on an incremental build — Maven's staleness check only recompiles a file whose *own* mtime changed, and
  will silently leave an unrelated dependent test file compiled against the old shape.

For pluralisation, embed the `{#if count == 1}...{#else}...{/if}` (or, for full CLDR generality,
`{count.arabicPluralCategory}`) **inside the single `@Message` value** — never mint a singular/plural method pair.

### The template-side-switch rule

Anything that needs translated text but isn't a literal `{msg:...}` call at a template render site — an enum's
own `label()`, a `*Extensions`/`*Service` method that would otherwise call `AppMessages` directly, a sealed
result's message — **cannot** resolve it from Java, per the "Java call = always English" rule under "Message
bundles" above. The established fix is a `{#switch someValue}...{#is X}{msg:someKey}{/is}...{/switch}` written
directly in the template that already has a locale-bound `TemplateInstance`; where the resolved text needs to be
reused as *data* passed into another partial (a confirm-delete prompt, an error banner), a small shared partial
rendered via `Template.render()` from Java is the pattern instead — see `partials/text-failure-message.html`,
`partials/password-rejection.html`, `partials/timezone-option.html` for worked examples of each shape. The one
exception to the whole rule: `java.time` formatters read a `Locale` argument directly with no template involved,
so ordinary Java is fine for date/number formatting (see "Locale-aware formatting").

**The corollary is that a "third bucket" enum carries no display label at all.** A `label()` field holding English
UI text is not a harmless default that a template can override — it is the thing that renders, in every language,
until someone notices. `Theme`/`Font`/`CalendarView`/`StatField` were built this way from the start; `PageSection`
and `IpLockoutStatus` had one each and shipped English into the Settings page-size rows and the admin lockout table
respectively. Both now hold only their stable key/badge class, with the word resolved from
`AppMessages#pageSection*`/`#lockoutStatus*` at the render site. Where the same enum is also published by the API,
that surface keeps the *machine-readable* form (`IpLockoutStatus#name()`), which is correct rather than a
compromise.

**Three shapes, and which one a call site needs:**

| The template needs…                                                     | Use                                                                            | Worked example                                                                           |
|-------------------------------------------------------------------------|--------------------------------------------------------------------------------|------------------------------------------------------------------------------------------|
| just to print the word                                                  | `{#switch key}{#is 'x'}{msg:…}{/switch}`                                       | `partials/admin-ip-lockout-row.html`                                                     |
| the word as *data* (an `aria-label`, a `data-*`, a nested `{#include}`) | the caller resolves it into a `{#let}` and passes it down                      | `settings.html` → `partials/page-size-section-row.html`, `partials/stats-field-row.html` |
| a value that is *sometimes* user data and sometimes chrome              | a `@TemplateExtension` returning `null` for the chrome case, plus `.or(msg:…)` | `StatSubjectExtensions#actionName`, `FrequencySubjectExtensions#actionName`              |

That third shape is the notes stat subject: an action's name is the user's own text and is never translated, while
the notes subject's name is app chrome and always is, and only the template can tell them apart *and* resolve the
translated half. `{#let}` cannot hold a `{#switch}`, and Qute has no ternary — `.or()` over a null-returning
extension is what bridges that, and it keeps the English `StatSubject#name()` intact for the API.

**A `{#switch}` with no matching arm renders NOTHING** — it does not fail the build and does not throw, so a
constant added without its arm ships a silently blank label, which is worse than the English it replaced.
`TemplateSwitchCoverageTest` reads the template source and asserts an arm exists per constant for exactly this
reason. (A bad `msg:` name inside an arm needs no such guard: Qute validates every expression at build time.)
