# Internationalisation (i18n) & Localisation (l10n)

> **Status: Phase 0 done (2026-08-17). Phase 1 fully done (2026-08-18)** - including the two areas slice 5 explicitly
> deferred (the text-validation pipeline, item 3; the transfer/import row-level reasons, item 6), resolved in slice 7
> by restructuring the affected `*Result`/outcome shapes to carry a compile-checked sealed cause instead of one opaque
> pre-composed `String`. Phases 2-6 not started. This is a roadmap for introducing multi-language support (English
> now; Spanish, Arabic and Japanese planned next), broken into phases so any one of them can be picked up in a future
> session without re-deriving the scope. Read the relevant phase before starting that work; update this file's
> checkboxes/notes as phases/slices land instead of leaving it to drift from the code.
> **Not yet wired into `CLAUDE.md`'s cross-reference list** — deliberately, until the whole effort is complete.

## Why this file exists

The app currently has **zero i18n infrastructure**: `templates/layout.html` hardcodes `<html lang="en">`, there is
no `dir` attribute anywhere, no `@MessageBundle`/resource bundle exists, no `Locale` field exists on `User`, and
every user-facing string is an English literal embedded directly in Java or Qute templates. This was fine for an
English-only app; it stops being fine the moment a second language ships, so the work needs to be sequenced rather
than attempted as one change. Arabic in particular is not "translate the strings" — it needs RTL layout, which
touches CSS pervasively (see Phase 3).

## Phase 0 — Infrastructure ✅ DONE (2026-08-17)

**Goal**: make "a request has a language" a real, resolvable concept, with nothing yet translated.

**As built** (differs from the original plan in a few places — corrected here so the next phase starts from what's
actually true, not what was guessed beforehand):

- **The `language` preference**, following the exact `Theme`/`Font`/`CalendarView` precedent: Flyway
  `V31__add_language.sql` (`users.language`, originally `NOT NULL DEFAULT 'en'`),
  `V32__split_english_locale.sql` (backfills existing `'en'` rows to `'en-GB'` and updates the column default),
  `V33__region_qualify_all_languages.sql` (backfills `'es'`→`'es-419'`, `'ar'`→`'ar-SA'`, `'ja'`→`'ja-JP'` — see
  below for why every language ended up region-qualified, not just English), and
  `V34__spanish_default_is_spain.sql` (corrects V33's Spanish backfill target from `'es-419'` to `'es-ES'` — V33 is
  immutable once applied, so this landed as a new migration rather than an edit to it, per `CLAUDE.md`'s rule);
  `user/Language.java`, a **plain enum**
  (`ENGLISH_GB`/`ENGLISH_US`/`SPANISH_SPAIN`/`SPANISH_LATIN_AMERICA`/`ARABIC`/`JAPANESE`, no `PreviewOption` —
  decided in favour of a plain autonym-labelled dropdown, since a flag/thumbnail is a poor fit for a language spoken
  across many countries); `@Preference` on `User.language`; `UserDto.Preferences.language` +
  `UserResource.PreferencesUpdate.language` (both `PATCH /api/v1/users/me` and the Settings HTMX endpoint);
  `ProfileService.updateLanguage`; a plain `<select>` row in `settings.html` next to Timezone (autonym labels:
  "English (UK)", "English (US)", "Español (España)", "Español (Latinoamérica)", "العربية", "日本語").
  `UserPreferencesExposureTest` passed automatically — it's fully reflection-driven, no manual list to update.
  - **Every offered language is region-qualified** (`en-GB`/`en-US`, `es-ES`/`es-419`, `ar-SA`, `ja-JP` — none of
    them a bare `en`/`es`/`ar`/`ja`), a deliberate revision made specifically so (a) date/number formatting can be
    region-correct once Phase 2 lands — a `Locale` already bundles language + region, so
    `DateTimeFormatter.ofLocalizedDate(...).withLocale(language.locale())` gets US vs UK date conventions for free
    the moment a user's stored `Language` carries a region, no separate "region"/"date format" preference needed —
    and (b) there is never any ambiguity for a contributor writing translated content about WHICH regional
    convention they're writing in (e.g. Spain vs Latin American Spanish idiom), since every offered entry names its
    convention explicitly. `en-GB` is the default (matches this codebase's own established British spelling — see
    `Language.ENGLISH_GB`'s Javadoc). Spanish is split into two full entries (`es-ES`/`es-419`) mirroring English's
    US/UK split, since that divide is genuinely common in real products (Netflix, Google, …); Arabic/Japanese stay
    single-entry (`ar-SA`/`ja-JP`) since regional splitting isn't common practice for UI translation of those the
    way it is for English/Spanish — see each constant's Javadoc for the per-language reasoning, and re-evaluate
    per-language if that changes rather than applying one rule to all.
  - **A region with no `.properties` file of its own falls back to the bundle's default content, by design** —
    Quarkus's message-bundle fallback means every offered region can be added ahead of having its own translated
    content, costing nothing in translation work until Phase 1/5 actually adds a `messages_<locale>.properties` for
    it. Verified directly (not just assumed) by
    `AppMessagesIT.messageNamespace_fallsBackToDefaultContent_forALocaleWithNoOwnPropertiesFile`.
  - **A real correctness gap, found and fixed while making every language region-qualified**: with only specific
    regions offered (no bare-language entries left as a safety net), a browser reporting a REAL country we simply
    don't carry — `es-MX` (Mexican Spanish), `ar-EG` (Egyptian Arabic), a bare `en`/`es`/`ar`/`ja` with no region at
    all — would otherwise match NOTHING under strict RFC 4647 lookup (`Locale.lookupTag`) and silently fall all the
    way through to the unrelated global default (English), rather than merely the "wrong" regional flavour of the
    visitor's OWN language. `Language.fromAcceptLanguageHeader` now falls back in two stages: first
    `Locale.lookupTag` for an exact offered match, then (new) `Language.BASE_LANGUAGE_FALLBACK` — a small map from
    base language to a representative offered entry (`es`→`SPANISH_SPAIN`, `ar`→`ARABIC`, `ja`→`JAPANESE`,
    `en`→`ENGLISH_GB`) — so an uncarried region of an OFFERED language still resolves to THAT language, and only a
    genuinely unoffered language (e.g. French) reaches `Language.DEFAULT`. `SPANISH_SPAIN` is the Spanish entry in
    that map — **`es-ES` is the project's chosen default Spanish variant** (explicit direction, not a
    population-based inference the way the original draft of this fallback had reasoned it — that reasoning was
    corrected along with the code; see `V34` above, which fixes the one place it had already reached persisted
    data). Note this fallback is a last resort, not a quality-priority override: `Locale.lookupTag` processes
    `Accept-Language` ranges strictly in priority order and returns on the FIRST range with any exact match at all,
    so a
    lower-priority range's exact match (e.g. `ar-SA`) still wins over a higher-priority range that only has a
    base-language fallback available (e.g. `es-MX`) — verified in `LanguageTest`, alongside the base-fallback
    behaviour itself.
- **Locale resolution per request**: `Language.fromAcceptLanguageHeader(String)` (`java.util.Locale.LanguageRange`/
  `Locale.lookupTag`, quality-value-aware, falls back to English) resolves it for every logged-out page — login,
  register, `welcome` (the first-run setup wizard — it runs before any `User` row exists, same case as
  login/register), and the 403/404 error pages. Authenticated pages just read `user.language` directly. Every
  page-rendering resource (`DashboardWebResource`, `ActionsWebResource`, `NotesWebResource`, `StatsWebResource`,
  `SettingsWebResource`, `AdminWebResource`, `ErrorPages`, `AuthWebResource`) sets it.
- **`<html lang="{language}" dir="ltr">`** in `templates/layout.html` — `lang` is now dynamic, `dir` is a hardcoded
  literal with a comment pointing at Phase 3 (RTL support isn't built yet, so setting it dynamically now would be
  premature).
- **The message-bundle mechanism**: `web/AppMessages.java`, an unqualified `@MessageBundle` interface (so templates
  resolve any entry via the short `{msg:methodName}`, no per-feature prefix — the "one bundle per language"
  decision). **Correction to the original plan**: English content lives INLINE via each method's `@Message("...")`
  value, not a separate `messages_en.properties` file — that's the standard Quarkus convention (the annotation value
  IS the default-locale text) and needs no extra file. A translated language is still added as a sibling
  `messages_<locale>.properties` (`messages_en-US.properties`, `messages_es.properties`, `messages_ar.properties`,
  `messages_ja.properties`) under `src/main/resources/messages/`, one `methodName=translated text` line per entry —
  that part of the plan was right. `quarkus.default-locale=en-GB` and `quarkus.locales=en-GB,en-US,es,ar,ja` are now
  set in `application.properties` (Quarkus validates every `.properties` file's locale against this list at build
  time).
  - **Correction: there is no `io.quarkus.qute.i18n.LocaleResolver` CDI SPI** in this Quarkus version (3.38.2) — the
    original plan assumed one existed; it doesn't. The real mechanism is a per-render **template attribute**:
    `TemplateInstance.setAttribute(io.quarkus.qute.i18n.MessageBundles.ATTRIBUTE_LOCALE, someLocale)`. Every
    page-rendering resource now sets this alongside its existing `.data("language", ...)` call, using
    `Locale.forLanguageTag(user.language)` (authenticated) or the already-resolved `Language.locale()`
    (logged-out pages, reusing the one `fromAcceptLanguageHeader` call rather than computing it twice).
  - A single proof-of-mechanism entry, `AppMessages.placeholder()` ("i18n bundle mechanism online"), exists purely
    to verify the bundle resolves — it is NOT real UI copy and is not wired into any template. **Phase 1 replaces
    it with the first genuine extracted string** rather than leaving it in place. Verified end-to-end (bean
    injection AND the `{msg:...}` namespace inside an actual template render, via `Engine.parse(...)`) by
    `web/AppMessagesIT.java` — that test can also serve as the template for Phase 1's own bundle-content tests.
  - **The anticipated Qodana problem was real, and the anticipated fix was right**: Quarkus generates
    `AppMessages`'s implementation via build-time bytecode processing (Gizmo), invisible to Qodana's static
    analysis, which flagged the interface as unimplemented/unused and (with only one method) a functional-interface
    candidate. **Resolved with `@SuppressWarnings({"unused", "InterfaceMayBeAnnotatedFunctional",
    "InterfaceNeverImplemented"})`** on the interface (plus the matching `// NOPMD: ImplicitFunctionalInterface` for
    PMD's own version of the same finding) — the exact same treatment `PreviewOption`'s methods already carry for
    the identical "read by a mechanism static analysis can't trace" situation. **No submodule
    (`code-quality-config`) edit was needed** — that in-repo suppression is sufficient, so the open question in the
    original plan is resolved: don't touch the submodule for this.

**Exit criteria — met**: the `language` preference exists end-to-end and round-trips through Settings and
`PATCH /api/v1/users/me`; `<html lang>` reflects it (`dir` stays hardcoded until Phase 3); the message-bundle
mechanism is proven end-to-end; all rendered UI text is still English. Verified via
`.github/scripts/lint_and_tests.sh java` (mvn/E2E/smoke/Qodana all green) — no shortcuts taken on the gate.

**Along the way, one build-breaking mistake and fix, worth knowing before touching these files again**:
`ForbiddenExceptionMapper`'s `@ServerExceptionMapper`-annotated method cannot take an arbitrary `@HeaderParam` —
RESTEasy Reactive rejects it at build time ("Parameter ... is not allowed"). Use `RoutingContext` as the method
parameter instead (read the header off it directly) — the same pattern `NotFoundExceptionMapper` already used.
Ordinary JAX-RS resource methods (not `@ServerExceptionMapper`) don't have this restriction — `@HeaderParam` is
fine there (see `AuthWebResource`'s login/register/welcome methods).

## Phase 1 — String extraction

**Goal**: move the ~150+ scattered English strings into the Phase 0 message-bundle mechanism, keyed rather than
literal. This is the largest single chunk of mechanical effort.

Order of attack (roughly biggest-value-first):

1. Templates (60 files, ~104 literals + ~66 attribute strings) — mechanical but touches nearly every template file.
   This bucket already includes every tooltip and modal in the app: both are ordinary Qute partials
   (`templates/partials/tooltip.html`, the `stats.html` chart modal, the `settings.html` preview modal), each
   `text=`/heading literal supplied by its call site, so nothing there sits outside the count above — confirmed by
   inspection, not assumed.
2. **A third bucket, distinct from templates and the text pipeline: hardcoded English living in Java constants
   surfaced to templates via `{inject:...}` beans or enum constructors, not as template literals.** Concretely:
   - `web/AppInfo.java` — the `tagline` field (`"Make every day count"`), one Java constant feeding three separate
     places (the page `<title>`, the login wordmark's `alt` text, the navbar logo tooltip).
   - `user/Theme`, `user/Font`, `user/CalendarView` — each `implements PreviewOption` and stores its `label()`/
     `title()`/`alt()` as constructor-assigned English string state (Settings picker tiles + the preview-lightbox
     modal's title/alt text — see `settings.html:752-780`).
   - `stats/StatField` — `label()`/`description()` for the Stats-page tile catalogue and picker.
   - `user/Role` — `displayName()` for the admin role picker/table.

   These need a real design decision, not just a string move: today the label IS the enum's state. Making it
   translatable means resolving the label from the message bundle BY KEY at render time (the key already exists —
   `Theme.value()`, `StatField.key()`, `Role`'s storage value), rather than continuing to carry English text as
   enum state. **Exception, do not extract**: `StatField`'s label is only the DEFAULT caption — a user may already
   rename any stat (`StatFieldPref.label`, per `CLAUDE.md`'s pagination/stats notes), and that stored rename is the
   user's own free text in whatever language they typed it. Only the catalogue DEFAULT goes through translation;
   a user's override must never be touched by it.
3. ✅ Done — see slice 7. Slice 5 found the text-validation pipeline (`net.zodac.diurnal.text`) needed the consuming
   `*Result` shapes redesigned before it could be translated at all (`TextOutcomeExtensions.message`/
   `TextFieldExtensions.lengthMessage` composed ONE string the API and the web banner both relayed verbatim) and
   deferred it rather than attempt a redesign mid-slice. Slice 7 did that redesign: `TextOutcome.Failure` itself
   already carried everything needed (the field, the failure shape) - the fix was to stop collapsing it to English
   inside the pipeline and instead carry the `Failure` itself all the way to each surface, resolving text only at the
   edge (API: a Java composer; web: a real template render). `TEXT_INPUT.md`'s "word order isn't universal" line is
   why every message is one atomic, whole-sentence-per-(field, failure-shape) entry rather than a
   `{fieldLabel} {requirement}` substitution - Qute substitution would let a translator reorder words, but not fix
   grammatical agreement, which needs the whole sentence to vary.
4. ✅ Done — see slice 5 for exactly which of the 11 families' variants translated (independently-worded ones) vs
   needed no work (`LogResult`/`FrequencyResult`, API-only). The shared-opaque-string ones slice 5 deferred
   (`NoteResult`, `ProfileResult`, `PasswordChangeResult`, `RegistrationResult.Invalid`) are ✅ done — see slice 7.
5. ✅ Done — `auth/lockout/LockoutMessages.retryMessage` stays English (API); the web pages resolve
   `{msg:lockoutRetrySingular/Plural}` themselves from the raw seconds. The "X, Y and Z" list-joiner
   (`LockoutMessages.humanReadable`/`join`) turned out to be **server-log-only, never user-facing** (verified, not
   assumed) - nothing to translate there.
6. ✅ Done — see slice 7. Same shape as item 3, same fix shape: `transfer/ArchiveParser`'s ~14 reasons, plus
   `TransferArchive`'s 4 and `CsvParser`'s 1, were relayed verbatim by both surfaces (slice 5's deferral) until the
   new `ImportReason` sealed type gave every one of them a compile-checked, per-surface-resolvable shape.
7. ✅ Done — see slice 5. `window.Diurnal.i18n`, populated in `layout.html` from `data-i18n-*` HTML attributes (not
   interpolated directly into the inline script, to survive a translation containing an apostrophe).

### Post-slice-2 regression, found and fixed (2026-08-18)

The full gate's `FrequencyChartIT` failed 4/30 cases with `500` after slice 2 (stats-chart.html's extraction). Root
cause: `AppMessages.chartCaption(int total, String period, int peak)` declared its numeric parameters `int`, but
`FrequencyChart.total()`/`.peak()` (the record fields the template passes in, `{msg:chartCaption(chart.total, ...,
chart.peak)}`) are `long`. Qute's generated bundle resolver casts the passed argument to the DECLARED parameter
type rather than widening/narrowing it, so a `Long` hitting an `int`-typed parameter threw
`ClassCastException: class java.lang.Long cannot be cast to class java.lang.Integer` at render time (a 500, not a
compile-time error — Qute's build-time template validation checks the expression parses and the method exists, not
that argument types are assignment-compatible). Fixed by widening the message method's parameters to `long`.
**Lesson for the remaining slices**: when a `{msg:...}` call's argument is a record field (not a literal or an
already-`int` value like `List.size()` or a `PageWindow` component), check the field's actual declared type before
writing the bundle method's parameter type — `int` is not a safe default assumption. The other three `int`-parameter
bundle methods (`atLine`, `showingFirstOfTotalProblems`, `pageOfTotal`) were audited at the same time and are all
correctly typed (their arguments are genuinely `int`: `ImportProblem.line`, `List.size()`, `PageWindow` components).

**Dead end 1 — a runtime-rendered "ad hoc string" mechanism for API JSON, abandoned.** The initial plan was a

## Phase 2 — Locale-aware formatting

**Goal**: dates, durations, plurals and numbers stop being hardcoded English/`Locale.ENGLISH`.

- Replace every hardcoded `Locale.ENGLISH`/`Locale.ROOT` `DateTimeFormatter` (`time/DayLabels`,
  `stats/FrequencyKeys`, `stats/SubjectStatsExtensions`, `stats/FrequencyCharts`, `stats/StatsService`, the two
  admin-timestamp formatters) with the resolved request locale. **No extra plumbing needed for US vs UK date
  order specifically** — `Language.locale()` already carries the region (`en-GB`/`en-US`, decided in Phase 0
  specifically so this would fall out for free), so once these formatters take a real `Locale` instead of a
  hardcoded one, `DateTimeFormatter.ofLocalizedDate(...).withLocale(language.locale())` resolves US/UK date
  conventions automatically — verify it (a spot IT asserting the two render different date orders) rather than
  just assuming the plumbing carries through correctly.
- Replace `time/Durations.plural()` with CLDR plural-category logic (e.g. ICU4J `PluralRules`, or Quarkus/Qute's
  built-in `@Message` pluralisation support if it covers the needed categories) — Arabic needs six categories
  (zero/one/two/few/many/other), Japanese needs none, Spanish needs the familiar two but with different word forms
  than English's `+s`.
  This is the same `Durations.plural`/`count(n, unit)` rule `CLAUDE.md`'s "Notable invariants" section already
  requires every pluralised count to go through — extend that rule's implementation, don't bypass it.
- Rework `Durations.label(DaySpan)`'s string-concatenation-with-hardcoded-separator into a locale-composed message
  (the ordering of "1 year, 1 month, 17 days" is not universal word order).
- Replace `app.js`'s hardcoded `MONTHS_FULL`/`MONTHS_ABBR` arrays and the regex-based English abbreviation trick
  (`shortenMonths`/`shortenYears`) with `Intl.DateTimeFormat`, driven by the same resolved language as the server
  side, so the calendar and server-rendered dates agree.
- **Translating field NAMES is not enough — field ORDER must become locale-derived too.** `time/DayLabels.java:30`
  and the other formatters in `stats/` currently build a *fixed* pattern (`"EEEE, d MMMM yyyy"`) and only the
  `Locale` passed to it would change under the bullet above. That translates month/day names but keeps English
  field order for every language — wrong for Japanese, which conventionally orders year → month → day. Use
  `DateTimeFormatter.ofLocalizedDate(FormatStyle.LONG).withLocale(locale)` (or
  `DateTimeFormatterBuilder.getLocalizedDateTimePattern`) instead of a hardcoded pattern string, so the *structure*
  of the date follows the locale, not just the vocabulary.
- **Locale-aware sorting (collation).** Two user-facing name lists currently sort with plain Unicode code-point
  order: `log/LogsApiResource.java:208` (`Comparator.comparing(DayLogEntryDto::name)`, the day-panel action list)
  and `user/Role.java:83` (admin role list — small fixed set, lower priority). Ordinal order is wrong for Spanish
  (`ñ`), Arabic and Japanese (kana/kanji) — replace with `java.text.Collator.getInstance(locale)` for any
  user-facing name sort.
- **Decimal separators in stats-card averages.** The Stats page's weekly/monthly day- and count-average tiles
  (`StatField.WEEKLY_DAY_AVERAGE`/`MONTHLY_DAY_AVERAGE`/`WEEKLY_COUNT_AVERAGE`/`MONTHLY_COUNT_AVERAGE`) are rendered
  by `stats/SubjectStatsExtensions.formatDecimal(double, int)` (`SubjectStatsExtensions.java:308-314`), which calls
  `String.format(Locale.ENGLISH, "%." + decimalPlaces + "f", value)` — always a period (`"2.3"`), never the
  locale-appropriate separator (`"2,3"` in Spanish/French/German-family locales). Replace with
  `java.text.DecimalFormat`/`NumberFormat.getInstance(locale)` driven by the resolved request locale — same root
  cause (a hardcoded `Locale.ENGLISH`) and same fix shape as the `DateTimeFormatter` bullet above.
- **Related, worth checking in the same pass**: the client-side large-integer grouping
  (`Diurnal.formatNumbers()` in `app.js`, used for total-count stat tiles) calls `num.toLocaleString(undefined, …)`
  — `undefined` defers to the *browser's* locale, which may not match the language the user has explicitly picked
  in the app (e.g. a Japanese app-language preference with an English-locale browser). For full consistency, pass
  the resolved app language through explicitly (e.g. via a data attribute the layout already has, once Phase 0
  exists) rather than relying on the browser default.
- **Explicitly out of scope** (checked, not applicable to this app): decimal *input* parsing — every numeric input
  in the app is stepper/button-incremented (`ActionLog.MAX_DAILY_COUNT`, page-size settings), never typed as
  free-text decimals, so there's no locale-decimal-comma-vs-point ambiguity on the input side. Currency and
  postal-address formatting also don't apply — the app has neither concept.

**Exit criteria**: every date, duration, pluralised count and decimal average reflects the request's resolved
language — vocabulary, field order/structure, AND numeric separators — and every user-facing name list sorts by the
resolved locale's collation rather than raw code-point order.

## Phase 4 — Fonts

**Goal**: Arabic and Japanese text renders with real glyph coverage, without bloating the Docker image for
deployments that never use those languages.

**Decision (recommended): bake the fonts in by default, using the app's existing lazy-load pattern — do not
build a runtime-fetch or build-time-conditional mechanism unless real subset sizes force it.**

Rationale:
- Font *bandwidth* (the concern that actually matters for users) is already solved by a pattern this codebase uses:
  `frontend/css/app.css:21-24` notes fonts are per-user opt-in via CSS variables, and every `@font-face` already
  uses `font-display: swap`. A browser only downloads an `@font-face` resource when the page renders text matching
  that font-family — so scoping the Japanese/Arabic `@font-face` declarations behind the same `--font-body`/
  `--font-display` variable mechanism (only set when the resolved language selects them) means English/Spanish
  users' browsers never fetch those files, with zero new machinery.
- Font *image size* (the Docker-image concern) is much smaller than it sounds once subsetted: a Japanese WOFF2
  subset covering common-use kanji + kana is typically 1-3MB, Arabic (far fewer glyphs) a few hundred KB — trivial
  next to a Quarkus/JVM production image that's already 200MB+.
- The alternatives are worse fits for this app specifically:
  - **Third-party font CDN** (e.g. Google Fonts) moves the bytes out of the image entirely, but conflicts with the
    self-hosted-everything posture already established here (OpenDyslexic is self-hosted rather than CDN-loaded),
    requires loosening `auth.security.CspPolicy`'s `font-src`, and breaks offline/air-gapped deployments.
  - **Build-time conditional image variants** (a Docker `ARG` gating which font files get `COPY`'d) would keep the
    default image smaller, but adds a second image to build/maintain/scan (the `docker` gate's hadolint+grype tiers,
    per `CLAUDE.md`, would need to cover both) for a payoff measured in low single-digit MB — not worth it unless
    actual subset sizes come in far larger than expected.
- Revisit this decision only if the specific font families/weights chosen for Japanese and Arabic turn out to need
  full (non-subsetted) multi-weight families — that's when the "worth an image variant" tradeoff could flip.

Concrete steps:
- Pick specific Arabic and Japanese font families (subsettable WOFF2, SIL-OFL or similarly permissive licence, to
  match `OpenDyslexic`'s precedent) and add them to `frontend/css/app.css` alongside the existing `@font-face`
  blocks, plus new options on the `Font` enum (`net.zodac.diurnal.user`) if a per-language default is wanted, or a
  language-keyed `--font-body` override in the layout template if the choice should just follow the resolved
  language automatically rather than being a separate user pick.
- Subset each font to the glyphs actually needed (common-use kanji + hiragana + katakana for Japanese; Arabic script
  block for Arabic) rather than shipping unsubsetted families.
- Confirm `unicode-range` is set per `@font-face` block so a mixed-language page (e.g. an English UI with a
  Japanese-language note) only pulls the glyphs actually rendered.

**Exit criteria**: Arabic and Japanese text renders in a real, legible typeface everywhere in the UI; measure the
actual image-size delta once real font files are chosen, and only then decide whether Phase 4's "bake it in"
decision above needs revisiting.

## Phase 5 — Translation content

**Goal**: real `es-ES`/`es-419`/`ar-SA`/`ja-JP` message-bundle content, not engineering.

- The Phase 1 bundles are the deliverable a translator (human or LLM-assisted) works against — this phase is mostly
  a translation/localisation-workflow question (who translates, how review works, whether machine-translation is an
  acceptable first pass) rather than code.
- Decide how partial-coverage languages are handled if a translation lags behind a new string (e.g. fall back to
  English for missing keys, per-key, rather than blocking the whole language).
- **Verified, not a blocker, but review the wording**: the shared text-validation pipeline
  (`text/TextRules.java:97`, `NO_INVISIBLE_CHARACTERS`) rejects Unicode `FORMAT`/`CONTROL`/`SURROGATE`/
  `PRIVATE_USE`-category code points — bidirectional *override/isolate control* characters used for spoofing — not
  Arabic/Hebrew script letters (those are category `Lo` and pass through untouched). Real Arabic input in action
  names/notes is **not** blocked by this rule. The rejection message text itself
  ("cannot contain invisible or text-direction characters") should still get translation-review attention: read
  carelessly in another language it could sound like "your script isn't supported," which is the opposite of what
  the rule does.
- **Language-picker autonyms**: whatever picker the Phase 0 `Language` preference gets, each option should be
  labelled in its OWN language/script ("Español", "العربية", "日本語"), not translated into the current UI
  language — the standard convention, and the only way a user can find their own language before the rest of the
  UI has switched.

## Phase 6 — Test coverage

**Goal**: the E2E suite doesn't silently rot once English stops being the unconditional default, and gains
non-English coverage.

- Pin the existing E2E fixtures/spec runs to `language=en-GB` explicitly (rather than relying on it being the
  unstated default), so the literal-English assertions already in `admin.spec.ts`, `cursor.spec.ts`,
  `actions.spec.ts`, `stats.spec.ts` and `data-transfer.spec.ts` keep passing on purpose, not by accident.
- Set Playwright's `locale`/`timezoneId` deliberately per test run if any spec needs to assert on locale-formatted
  output (currently only `timezoneId: 'UTC'` is pinned, per the determinism rules in [`TESTING.md`](TESTING.md)).
- Add at least a smoke-level pass per supported language (page loads, `dir` is correct, no missing-bundle-key
  fallback text leaks through) rather than full parallel suites per language.
- **Text-expansion visual regression**: translated strings are rarely the same length as English — Spanish commonly
  runs 15-30% longer, and fixed-width buttons/table columns/badges sized for English text can wrap or truncate
  badly. Not solvable in the abstract; cover it with a visual/manual pass per language during Phase 6 rather than an
  automated check, focusing on the tightest layouts (data-table headers, the Settings picker labels, calendar
  toolbar).
- Add an i18n/locale section to [`TESTING.md`](TESTING.md) once the approach is settled, alongside the existing
  timezone-determinism section — this file (`I18N.md`) is the roadmap; `TESTING.md` should end up documenting the
  steady-state testing convention the same way it does for timezones.
