## Why this file exists

The app currently has **zero i18n infrastructure**: `templates/layout.html` hardcodes `<html lang="en">`, there is
no `dir` attribute anywhere, no `@MessageBundle`/resource bundle exists, no `Locale` field exists on `User`, and
every user-facing string is an English literal embedded directly in Java or Qute templates. This was fine for an
English-only app; it stops being fine the moment a second language ships, so the work needs to be sequenced rather
than attempted as one change. Arabic in particular is not "translate the strings" — it needs RTL layout, which
touches CSS pervasively (see Phase 3).

## Phase 0 — Infrastructure ✅ DONE (2026-08-17)

**Goal**: make "a request has a language" a real, resolvable concept, with nothing yet translated.

**As built** (differs from the original plan in a few places — corrected here so the next phase starts from what's
actually true, not what was guessed beforehand):

- **The `language` preference**, following the exact `Theme`/`Font`/`CalendarView` precedent: Flyway
  `V31__add_language.sql` (`users.language`, originally `NOT NULL DEFAULT 'en'`),
  `V32__split_english_locale.sql` (backfills existing `'en'` rows to `'en-GB'` and updates the column default),
  `V33__region_qualify_all_languages.sql` (backfills `'es'`→`'es-419'`, `'ar'`→`'ar-SA'`, `'ja'`→`'ja-JP'` — see
  below for why every language ended up region-qualified, not just English), and
  `V34__spanish_default_is_spain.sql` (corrects V33's Spanish backfill target from `'es-419'` to `'es-ES'` — V33 is
  immutable once applied, so this landed as a new migration rather than an edit to it, per `CLAUDE.md`'s rule);
  `user/Language.java`, a **plain enum**
  (`ENGLISH_GB`/`ENGLISH_US`/`SPANISH_SPAIN`/`SPANISH_LATIN_AMERICA`/`ARABIC`/`JAPANESE`, no `PreviewOption` —
  decided in favour of a plain autonym-labelled dropdown, since a flag/thumbnail is a poor fit for a language spoken
  across many countries); `@Preference` on `User.language`; `UserDto.Preferences.language` +
  `UserResource.PreferencesUpdate.language` (both `PATCH /api/v1/users/me` and the Settings HTMX endpoint);
  `ProfileService.updateLanguage`; a plain `<select>` row in `settings.html` next to Timezone (autonym labels:
  "English (UK)", "English (US)", "Español (España)", "Español (Latinoamérica)", "العربية", "日本語").
  `UserPreferencesExposureTest` passed automatically — it's fully reflection-driven, no manual list to update.
  - **Every offered language is region-qualified** (`en-GB`/`en-US`, `es-ES`/`es-419`, `ar-SA`, `ja-JP` — none of
    them a bare `en`/`es`/`ar`/`ja`), a deliberate revision made specifically so (a) date/number formatting can be
    region-correct once Phase 2 lands — a `Locale` already bundles language + region, so
    `DateTimeFormatter.ofLocalizedDate(...).withLocale(language.locale())` gets US vs UK date conventions for free
    the moment a user's stored `Language` carries a region, no separate "region"/"date format" preference needed —
    and (b) there is never any ambiguity for a contributor writing translated content about WHICH regional
    convention they're writing in (e.g. Spain vs Latin American Spanish idiom), since every offered entry names its
    convention explicitly. `en-GB` is the default (matches this codebase's own established British spelling — see
    `Language.ENGLISH_GB`'s Javadoc). Spanish is split into two full entries (`es-ES`/`es-419`) mirroring English's
    US/UK split, since that divide is genuinely common in real products (Netflix, Google, …); Arabic/Japanese stay
    single-entry (`ar-SA`/`ja-JP`) since regional splitting isn't common practice for UI translation of those the
    way it is for English/Spanish — see each constant's Javadoc for the per-language reasoning, and re-evaluate
    per-language if that changes rather than applying one rule to all.
  - **A region with no `.properties` file of its own falls back to the bundle's default content, by design** —
    Quarkus's message-bundle fallback means every offered region can be added ahead of having its own translated
    content, costing nothing in translation work until Phase 1/5 actually adds a `messages_<locale>.properties` for
    it. Verified directly (not just assumed) by
    `AppMessagesIT.messageNamespace_fallsBackToDefaultContent_forALocaleWithNoOwnPropertiesFile`.
  - **A real correctness gap, found and fixed while making every language region-qualified**: with only specific
    regions offered (no bare-language entries left as a safety net), a browser reporting a REAL country we simply
    don't carry — `es-MX` (Mexican Spanish), `ar-EG` (Egyptian Arabic), a bare `en`/`es`/`ar`/`ja` with no region at
    all — would otherwise match NOTHING under strict RFC 4647 lookup (`Locale.lookupTag`) and silently fall all the
    way through to the unrelated global default (English), rather than merely the "wrong" regional flavour of the
    visitor's OWN language. `Language.fromAcceptLanguageHeader` now falls back in two stages: first
    `Locale.lookupTag` for an exact offered match, then (new) `Language.BASE_LANGUAGE_FALLBACK` — a small map from
    base language to a representative offered entry (`es`→`SPANISH_SPAIN`, `ar`→`ARABIC`, `ja`→`JAPANESE`,
    `en`→`ENGLISH_GB`) — so an uncarried region of an OFFERED language still resolves to THAT language, and only a
    genuinely unoffered language (e.g. French) reaches `Language.DEFAULT`. `SPANISH_SPAIN` is the Spanish entry in
    that map — **`es-ES` is the project's chosen default Spanish variant** (explicit direction, not a
    population-based inference the way the original draft of this fallback had reasoned it — that reasoning was
    corrected along with the code; see `V34` above, which fixes the one place it had already reached persisted
    data). Note this fallback is a last resort, not a quality-priority override: `Locale.lookupTag` processes
    `Accept-Language` ranges strictly in priority order and returns on the FIRST range with any exact match at all,
    so a
    lower-priority range's exact match (e.g. `ar-SA`) still wins over a higher-priority range that only has a
    base-language fallback available (e.g. `es-MX`) — verified in `LanguageTest`, alongside the base-fallback
    behaviour itself.
- **Locale resolution per request**: `Language.fromAcceptLanguageHeader(String)` (`java.util.Locale.LanguageRange`/
  `Locale.lookupTag`, quality-value-aware, falls back to English) resolves it for every logged-out page — login,
  register, `welcome` (the first-run setup wizard — it runs before any `User` row exists, same case as
  login/register), and the 403/404 error pages. Authenticated pages just read `user.language` directly. Every
  page-rendering resource (`DashboardWebResource`, `ActionsWebResource`, `NotesWebResource`, `StatsWebResource`,
  `SettingsWebResource`, `AdminWebResource`, `ErrorPages`, `AuthWebResource`) sets it.
- **`<html lang="{language}" dir="ltr">`** in `templates/layout.html` — `lang` is now dynamic, `dir` is a hardcoded
  literal with a comment pointing at Phase 3 (RTL support isn't built yet, so setting it dynamically now would be
  premature).
- **The message-bundle mechanism**: `web/AppMessages.java`, an unqualified `@MessageBundle` interface (so templates
  resolve any entry via the short `{msg:methodName}`, no per-feature prefix — the "one bundle per language"
  decision). **Correction to the original plan**: English content lives INLINE via each method's `@Message("...")`
  value, not a separate `messages_en.properties` file — that's the standard Quarkus convention (the annotation value
  IS the default-locale text) and needs no extra file. A translated language is still added as a sibling
  `messages_<locale>.properties` (`messages_en-US.properties`, `messages_es.properties`, `messages_ar.properties`,
  `messages_ja.properties`) under `src/main/resources/messages/`, one `methodName=translated text` line per entry —
  that part of the plan was right. `quarkus.default-locale=en-GB` and `quarkus.locales=en-GB,en-US,es,ar,ja` are now
  set in `application.properties` (Quarkus validates every `.properties` file's locale against this list at build
  time).
  - **Correction: there is no `io.quarkus.qute.i18n.LocaleResolver` CDI SPI** in this Quarkus version (3.38.2) — the
    original plan assumed one existed; it doesn't. The real mechanism is a per-render **template attribute**:
    `TemplateInstance.setAttribute(io.quarkus.qute.i18n.MessageBundles.ATTRIBUTE_LOCALE, someLocale)`. Every
    page-rendering resource now sets this alongside its existing `.data("language", ...)` call, using
    `Locale.forLanguageTag(user.language)` (authenticated) or the already-resolved `Language.locale()`
    (logged-out pages, reusing the one `fromAcceptLanguageHeader` call rather than computing it twice).
  - A single proof-of-mechanism entry, `AppMessages.placeholder()` ("i18n bundle mechanism online"), exists purely
    to verify the bundle resolves — it is NOT real UI copy and is not wired into any template. **Phase 1 replaces
    it with the first genuine extracted string** rather than leaving it in place. Verified end-to-end (bean
    injection AND the `{msg:...}` namespace inside an actual template render, via `Engine.parse(...)`) by
    `web/AppMessagesIT.java` — that test can also serve as the template for Phase 1's own bundle-content tests.
  - **The anticipated Qodana problem was real, and the anticipated fix was right**: Quarkus generates
    `AppMessages`'s implementation via build-time bytecode processing (Gizmo), invisible to Qodana's static
    analysis, which flagged the interface as unimplemented/unused and (with only one method) a functional-interface
    candidate. **Resolved with `@SuppressWarnings({"unused", "InterfaceMayBeAnnotatedFunctional",
    "InterfaceNeverImplemented"})`** on the interface (plus the matching `// NOPMD: ImplicitFunctionalInterface` for
    PMD's own version of the same finding) — the exact same treatment `PreviewOption`'s methods already carry for
    the identical "read by a mechanism static analysis can't trace" situation. **No submodule
    (`code-quality-config`) edit was needed** — that in-repo suppression is sufficient, so the open question in the
    original plan is resolved: don't touch the submodule for this.

**Exit criteria — met**: the `language` preference exists end-to-end and round-trips through Settings and
`PATCH /api/v1/users/me`; `<html lang>` reflects it (`dir` stays hardcoded until Phase 3); the message-bundle
mechanism is proven end-to-end; all rendered UI text is still English. Verified via
`.github/scripts/lint_and_tests.sh java` (mvn/E2E/smoke/Qodana all green) — no shortcuts taken on the gate.

**Along the way, one build-breaking mistake and fix, worth knowing before touching these files again**:
`ForbiddenExceptionMapper`'s `@ServerExceptionMapper`-annotated method cannot take an arbitrary `@HeaderParam` —
RESTEasy Reactive rejects it at build time ("Parameter ... is not allowed"). Use `RoutingContext` as the method
parameter instead (read the header off it directly) — the same pattern `NotFoundExceptionMapper` already used.
Ordinary JAX-RS resource methods (not `@ServerExceptionMapper`) don't have this restriction — `@HeaderParam` is
fine there (see `AuthWebResource`'s login/register/welcome methods).

## Phase 1 — String extraction

**Goal**: move the ~150+ scattered English strings into the Phase 0 message-bundle mechanism, keyed rather than
literal. This is the largest single chunk of mechanical effort.

Order of attack (roughly biggest-value-first):

1. Templates (60 files, ~104 literals + ~66 attribute strings) — mechanical but touches nearly every template file.
   This bucket already includes every tooltip and modal in the app: both are ordinary Qute partials
   (`templates/partials/tooltip.html`, the `stats.html` chart modal, the `settings.html` preview modal), each
   `text=`/heading literal supplied by its call site, so nothing there sits outside the count above — confirmed by
   inspection, not assumed.
2. **A third bucket, distinct from templates and the text pipeline: hardcoded English living in Java constants
   surfaced to templates via `{inject:...}` beans or enum constructors, not as template literals.** Concretely:
   - `web/AppInfo.java` — the `tagline` field (`"Make every day count"`), one Java constant feeding three separate
     places (the page `<title>`, the login wordmark's `alt` text, the navbar logo tooltip).
   - `user/Theme`, `user/Font`, `user/CalendarView` — each `implements PreviewOption` and stores its `label()`/
     `title()`/`alt()` as constructor-assigned English string state (Settings picker tiles + the preview-lightbox
     modal's title/alt text — see `settings.html:752-780`).
   - `stats/StatField` — `label()`/`description()` for the Stats-page tile catalogue and picker.
   - `user/Role` — `displayName()` for the admin role picker/table.

   These need a real design decision, not just a string move: today the label IS the enum's state. Making it
   translatable means resolving the label from the message bundle BY KEY at render time (the key already exists —
   `Theme.value()`, `StatField.key()`, `Role`'s storage value), rather than continuing to carry English text as
   enum state. **Exception, do not extract**: `StatField`'s label is only the DEFAULT caption — a user may already
   rename any stat (`StatFieldPref.label`, per `CLAUDE.md`'s pagination/stats notes), and that stored rename is the
   user's own free text in whatever language they typed it. Only the catalogue DEFAULT goes through translation;
   a user's override must never be touched by it.
3. ✅ Done — see slice 7. Slice 5 found the text-validation pipeline (`net.zodac.diurnal.text`) needed the consuming
   `*Result` shapes redesigned before it could be translated at all (`TextOutcomeExtensions.message`/

4. ✅ Done — see slice 5 for exactly which of the 11 families' variants translated (independently-worded ones) vs

### Post-slice-2 regression, found and fixed (2026-08-18)

The full gate's `FrequencyChartIT` failed 4/30 cases with `500` after slice 2 (stats-chart.html's extraction). Root
cause: `AppMessages.chartCaption(int total, String period, int peak)` declared its numeric parameters `int`, but
`FrequencyChart.total()`/`.peak()` (the record fields the template passes in, `{msg:chartCaption(chart.total, ...,
chart.peak)}`) are `long`. Qute's generated bundle resolver casts the passed argument to the DECLARED parameter
type rather than widening/narrowing it, so a `Long` hitting an `int`-typed parameter threw
`ClassCastException: class java.lang.Long cannot be cast to class java.lang.Integer` at render time (a 500, not a
compile-time error — Qute's build-time template validation checks the expression parses and the method exists, not
that argument types are assignment-compatible). Fixed by widening the message method's parameters to `long`.
**Lesson for the remaining slices**: when a `{msg:...}` call's argument is a record field (not a literal or an
already-`int` value like `List.size()` or a `PageWindow` component), check the field's actual declared type before
writing the bundle method's parameter type — `int` is not a safe default assumption. The other three `int`-parameter
bundle methods (`atLine`, `showingFirstOfTotalProblems`, `pageOfTotal`) were audited at the same time and are all
correctly typed (their arguments are genuinely `int`: `ImportProblem.line`, `List.size()`, `PageWindow` components).

**Dead end 1 — a runtime-rendered "ad hoc string" mechanism for API JSON, abandoned.** The initial plan was a
`LocalizedText` bean (`engine.parse("{msg:...}").instance().setAttribute(ATTRIBUTE_LOCALE, locale).render()`) so

## Phase 2 — Locale-aware formatting

**Goal**: dates, durations, plurals and numbers stop being hardcoded English/`Locale.ENGLISH`.

- Replace every hardcoded `Locale.ENGLISH`/`Locale.ROOT` `DateTimeFormatter` (`time/DayLabels`,
  `stats/FrequencyKeys`, `stats/SubjectStatsExtensions`, `stats/FrequencyCharts`, `stats/StatsService`, the two
  admin-timestamp formatters) with the resolved request locale. **No extra plumbing needed for US vs UK date
  order specifically** — `Language.locale()` already carries the region (`en-GB`/`en-US`, decided in Phase 0
  specifically so this would fall out for free), so once these formatters take a real `Locale` instead of a
  hardcoded one, `DateTimeFormatter.ofLocalizedDate(...).withLocale(language.locale())` resolves US/UK date
  conventions automatically — verify it (a spot IT asserting the two render different date orders) rather than
  just assuming the plumbing carries through correctly.
- Replace `time/Durations.plural()` with CLDR plural-category logic (e.g. ICU4J `PluralRules`, or Quarkus/Qute's
  built-in `@Message` pluralisation support if it covers the needed categories) — Arabic needs six categories
  (zero/one/two/few/many/other), Japanese needs none, Spanish needs the familiar two but with different word forms
  than English's `+s`.
  This is the same `Durations.plural`/`count(n, unit)` rule `CLAUDE.md`'s "Notable invariants" section already
  requires every pluralised count to go through — extend that rule's implementation, don't bypass it.
- Rework `Durations.label(DaySpan)`'s string-concatenation-with-hardcoded-separator into a locale-composed message
  (the ordering of "1 year, 1 month, 17 days" is not universal word order).
- Replace `app.js`'s hardcoded `MONTHS_FULL`/`MONTHS_ABBR` arrays and the regex-based English abbreviation trick
  (`shortenMonths`/`shortenYears`) with `Intl.DateTimeFormat`, driven by the same resolved language as the server
  side, so the calendar and server-rendered dates agree.
- **Translating field NAMES is not enough — field ORDER must become locale-derived too.** `time/DayLabels.java:30`
  and the other formatters in `stats/` currently build a *fixed* pattern (`"EEEE, d MMMM yyyy"`) and only the
  `Locale` passed to it would change under the bullet above. That translates month/day names but keeps English
  field order for every language — wrong for Japanese, which conventionally orders year → month → day. Use
  `DateTimeFormatter.ofLocalizedDate(FormatStyle.LONG).withLocale(locale)` (or
  `DateTimeFormatterBuilder.getLocalizedDateTimePattern`) instead of a hardcoded pattern string, so the *structure*
  of the date follows the locale, not just the vocabulary.
- **Locale-aware sorting (collation).** Two user-facing name lists currently sort with plain Unicode code-point
  order: `log/LogsApiResource.java:208` (`Comparator.comparing(DayLogEntryDto::name)`, the day-panel action list)
  and `user/Role.java:83` (admin role list — small fixed set, lower priority). Ordinal order is wrong for Spanish
  (`ñ`), Arabic and Japanese (kana/kanji) — replace with `java.text.Collator.getInstance(locale)` for any
  user-facing name sort.
- **Decimal separators in stats-card averages.** The Stats page's weekly/monthly day- and count-average tiles
  (`StatField.WEEKLY_DAY_AVERAGE`/`MONTHLY_DAY_AVERAGE`/`WEEKLY_COUNT_AVERAGE`/`MONTHLY_COUNT_AVERAGE`) are rendered
  by `stats/SubjectStatsExtensions.formatDecimal(double, int)` (`SubjectStatsExtensions.java:308-314`), which calls
  `String.format(Locale.ENGLISH, "%." + decimalPlaces + "f", value)` — always a period (`"2.3"`), never the
  locale-appropriate separator (`"2,3"` in Spanish/French/German-family locales). Replace with
  `java.text.DecimalFormat`/`NumberFormat.getInstance(locale)` driven by the resolved request locale — same root
  cause (a hardcoded `Locale.ENGLISH`) and same fix shape as the `DateTimeFormatter` bullet above.
- **Related, worth checking in the same pass**: the client-side large-integer grouping
  (`Diurnal.formatNumbers()` in `app.js`, used for total-count stat tiles) calls `num.toLocaleString(undefined, …)`
  — `undefined` defers to the *browser's* locale, which may not match the language the user has explicitly picked
  in the app (e.g. a Japanese app-language preference with an English-locale browser). For full consistency, pass
  the resolved app language through explicitly (e.g. via a data attribute the layout already has, once Phase 0
  exists) rather than relying on the browser default.
- **Explicitly out of scope** (checked, not applicable to this app): decimal *input* parsing — every numeric input
  in the app is stepper/button-incremented (`ActionLog.MAX_DAILY_COUNT`, page-size settings), never typed as
  free-text decimals, so there's no locale-decimal-comma-vs-point ambiguity on the input side. Currency and
  postal-address formatting also don't apply — the app has neither concept.

**Exit criteria**: every date, duration, pluralised count and decimal average reflects the request's resolved
language — vocabulary, field order/structure, AND numeric separators — and every user-facing name list sorts by the
resolved locale's collation rather than raw code-point order.

Two real bugs surfaced building this, both non-obvious and now memory-documented for reuse:

- **A genuine script-load-order bug, unrelated to RTL but exposed by this change**: `settings.js`'s own header
  comment claimed it runs "after the shared /js/app.js" — false. `settings.js` sits inside layout.html's
  `{#insert body}`, and app.js is deliberately the NEXT `<script>` once that insertion closes (so it sees a
  fully-parsed `<body>` — a load-bearing ordering documented in app.js's own header). settings.js therefore
  always ran BEFORE app.js; nothing in it needed an app.js helper at top-level call time until this change did
  (`window.Diurnal.localizeDigits`), which then threw `is not a function`. Fixed by deferring the numeric-pref
  wiring calls to `DOMContentLoaded` (which only fires once every parser-blocking script, including the later
  app.js, has run) and correcting the stale comment in both settings.js and settings.html.
- **htmx 2.0.10's `event.detail.parameters` is a `FormData`-backed Proxy, and its multi-valued-key sub-proxy's
  `.map()` silently returns `undefined` instead of a new array** (it's wrapped to mutate-and-resync the
  underlying `FormData` instead of returning a value). The first `htmx:configRequest` delocalizer used
  `Array.isArray(val) ? val.map(...) : ...` — `Array.isArray` passed (it sees through the Proxy to the real
  array), but `.map()`'s `undefined` return, assigned back into the proxy, deleted every one of the per-section
  page-size overrides and replaced them with a single literal `"undefined"` string, caught by
  `settings-page-sizes.spec.ts` in the very next full-gate run. Fixed by going through the real `FormData`
  methods the proxy forwards as-is (`getAll`/`delete`/`append`) instead of the array sub-proxy, which also
  turned out simpler: one code path for both a scalar field and a repeated one, no `Array.isArray` branch
  needed at all.

- **`DateTimeFormatter#withLocale` does NOT switch numbering systems, unlike `NumberFormat`** — every

- **A worded duration/count that skips `.js-num` (to avoid grouping a tiny number: "1 day", not "1,day") was
  ALSO skipping ALL digit localization**, since `.js-num` was the only mechanism that did either. `.js-digits`
  (this round's earlier follow-up) is the fix already built for exactly this - it is now applied UNCONDITIONALLY
  alongside the conditional `.js-num` on every `partials/stat-tile.html`/`stat-tile-compact.html` value/sub,
  every `partials/pagination.html` count and the "Page X of Y" text, `partials/tooltip.html` (covers the
  footer's admin-only update tooltip and any future numeric tooltip for free), and the frequency chart's axis

  increment, not by reading the code - the gap does not show up in a fresh page load, only after this exact
  fetch-and-swap path runs.
- **The day panel's per-action count field** (`partials/day-action-item.html`, an editable `type="text"` -

**Fourth follow-up (2026-08-19): a second, more serious bidi bug, found by finally checking real RENDERED
screenshots instead of trusting `.textContent`/`.innerText` extraction.** Reported as pagination showing
"٢ of ١ page" (reversed) - confirmed for real, then found to be far more widespread once checked visually
(stats cards, tooltips, the frequency chart) - `.textContent` had been hiding it throughout this whole effort,
since it reads LOGICAL DOM order, not the VISUAL rendering the Unicode Bidi Algorithm actually produces.

- **Root cause, distinct from the earlier digit-glyph and centering-transform bugs**: `.js-digits`' `unicode-
  bidi: isolate` protects a NUMBER from its surroundings, but does nothing for a PHRASE that mixes translatable
  WORDS with an embedded number ("1 day", "Page 1 of 2", "3 times"). Confirmed directly: under `dir="rtl"` with
  no direction pinned on the phrase itself, "Page 1 of 2" (still-English, Phase 5 not shipped) rendered as
  "2 of 1 Page" - each word/number is its own bidi run, and the RTL paragraph places the first LOGICAL run on
  the right and works leftward, backwards for a Latin-script phrase.
- **Fix: a new `.js-phrase` class (`unicode-bidi: plaintext`)**, distinct from `.js-digits`/`.js-num`. Unlike a
  hardcoded `dir="ltr"`, `plaintext` resolves each phrase's OWN base direction from its first STRONGLY-
  directional character (skipping digits, which are direction-neutral) - so it self-adapts per phrase: still-
  English text (first strong char is a Latin letter) resolves LTR and renders correctly today, while a
  genuinely Arabic phrase this same class also covers (a Java-formatted date embedded in an English "since
  {date}" caption) resolves RTL from its own Arabic letters, unaffected. Verified both directions with a
  controlled test page before rolling it out. **This needs no Phase 5 revisit** — once English message-bundle
  wording is replaced with real Arabic, the heuristic keeps working without a code change.
- Applied to every confirmed mixed-content surface: `partials/stat-tile.html`/`stat-tile-compact.html` (value
  AND sub, unconditionally — durations, "since" captions, "N times", trend deltas), `partials/pagination.html`
  (both the "Showing X of Y" phrase and "Page X of Y"), `partials/tooltip.html` and
  `partials/frequency-slot-tooltip.html` (covers every current and future tooltip caller), the frequency

- **One nuance worth understanding, not a bug**: a genuinely Arabic phrase (e.g. "since 20 أغسطس 2026", where

**Fifth follow-up (2026-08-19): reversed the "let it auto-mirror" default for STRUCTURAL layout, after the user

**Sixth follow-up (2026-08-19): the fifth follow-up's `dir="ltr"` pins broke a DIFFERENT thing than intended —
Tailwind's `ltr:`/`rtl:` variants — reported as tooltips (the footer's "Release notes"/"View source", the
navbar's "Stats" link) shifted noticeably to the right under Arabic.**

- **Root cause, confirmed by reading the compiled CSS directly**: Tailwind compiles `ltr:`/`rtl:` to
  `:where(:dir(X),[dir=X],[dir=X] *)` - critically, the `[dir=X] *` clause matches ANY ancestor carrying that
  literal attribute, not the nearest one, unlike the native `:dir()` pseudo-class (which resolves like
  `direction` inheritance - correctly nearest-ancestor-based). Once the fifth follow-up pinned `dir="ltr"` on
  the navbar/footer with NO `dir="rtl"` reassertion anywhere inside them, `<html dir="rtl">` was STILL an
  ancestor further up - so for a COMPETING pair (`ltr:-translate-x-1/2` AND `rtl:translate-x-1/2`, both present
  on the same element), BOTH halves of the `:where()` selector matched simultaneously, and CSS SOURCE ORDER (not
  DOM nesting, not which is nearest) silently picked the RTL rule - shifting a centered tooltip a full 100% of
  its own width to the wrong side. Confirmed directly: `.app-tooltip`'s `start-1/2` (a genuinely logical
  property, `inset-inline-start`, correctly resolved via normal CSS inheritance) was fine; only the competing
  `ltr:`/`rtl:` transform pair broke.
- **A single-direction override (no competing opposite-direction rule) is NOT affected** - `.cal-chevron`'s
  `[dir="rtl"] { transform: scaleX(-1) }` and the settings preview-modal's `rtl:scale-x-[-1]` chevrons have
  nothing for source order to arbitrate between (the un-transformed state is simply the default), so they were
  unaffected. Only a competing PAIR (one rule per direction) is vulnerable - confirmed the SAME latent bug also
  existed, unreported, in the Settings toggle-switch thumb's `peer-checked:ltr:.../peer-checked:rtl:...` pair.
- **Fix: two new hand-written CSS classes using the native `:dir()` pseudo-class directly** instead of
  Tailwind's compiled variant - `.app-tooltip-center` (replaces the tooltip centering pair across all 5 call
  sites: `partials/tooltip.html`, `frequency-slot-tooltip.html`, `admin-user-row.html` x2, `stats-field-row.html`)
  and `.toggle-thumb` (replaces the toggle-switch pair, both switches in `settings.html`). `:dir()` has no
  `[dir=X] *`-style fallback, so it is immune to the nested-conflicting-`dir` scenario entirely.
- **A genuine, verified-not-just-assumed subtlety**: `stats-field-row.html`'s tooltip additionally resets to
  `sm:start-0 sm:translate-x-0` at wider viewports (edge-anchored instead of centered) - since Tailwind utilities
  live in `@layer utilities` and the new hand-written rule lives in `@layer components`, CSS layer ordering
  (utilities always beats components, regardless of selector specificity) means the existing `sm:` reset
  correctly overrides the new rule with NO special-casing needed - verified directly via computed styles at
  both viewport widths, not assumed from the layer-ordering theory alone.
- Verified via real geometry checks (host element center vs tooltip center, before/after values, not just DOM
  presence): the nav "Stats" tooltip and the footer "Release notes" tooltip both center with 0px of drift, the
  toggle-switch thumb's `::after` translate correctly flips sign with `:checked`, and the stats-field-row
  tooltip correctly centers below `sm` and resets to `0`/edge-anchored at `sm` and above. A clean full-gate run
  followed.

## Phase 4 — Fonts — done (2026-08-20)

**Goal**: Arabic and Japanese text renders with real glyph coverage, without bloating the Docker image for
deployments that never use those languages.

**Decision, confirmed with you before implementing (two open questions, both resolved in favour of the
recommendation below)**: (1) bake the fonts in by default via the existing lazy-load pattern rather than a
runtime-fetch/CDN/build-variant mechanism, and (2) wire them in as a **unicode-range-scoped fallback appended to
every existing font stack**, not a 4th `Font` picker option and not gated behind the resolved `language` —
Nova/Standard/OpenDyslexic are all Latin-only, so *something* has to cover Arabic/Japanese glyphs regardless of
which of the three a user has picked, and gating by `language` would leave a Japanese day-NOTE unrendered for an
English-language account (notes are free text in whatever script the user typed, independent of their UI
language — the same principle `NOTES.md` already states for translation). `unicode-range` already makes the
fetch itself conditional on a character actually needing the font, so no separate gating mechanism was needed on
top of it.

Rationale for baking in by default (unchanged from the original plan, verified rather than just assumed once real
subset sizes existed — see "As-built" below):
- Font *bandwidth* (the concern that actually matters for users) is already solved by a pattern this codebase uses:
  `frontend/css/app.css:21-24` notes fonts are per-user opt-in via CSS variables, and every `@font-face` already
  uses `font-display: swap`. A browser only downloads an `@font-face` resource when the page renders text matching
  that font-family — so scoping the Japanese/Arabic `@font-face` declarations behind the same `--font-body`/
  `--font-display` variable mechanism (only set when the resolved language selects them) means English/Spanish
  users' browsers never fetch those files, with zero new machinery.
- Font *image size* (the Docker-image concern) is much smaller than it sounds once subsetted: a Japanese WOFF2
  subset covering common-use kanji + kana is typically 1-3MB, Arabic (far fewer glyphs) a few hundred KB — trivial
  next to a Quarkus/JVM production image that's already 200MB+.
- The alternatives are worse fits for this app specifically:
  - **Third-party font CDN** (e.g. Google Fonts) moves the bytes out of the image entirely, but conflicts with the
    self-hosted-everything posture already established here (OpenDyslexic is self-hosted rather than CDN-loaded),
    requires loosening `auth.security.CspPolicy`'s `font-src`, and breaks offline/air-gapped deployments.
  - **Build-time conditional image variants** (a Docker `ARG` gating which font files get `COPY`'d) would keep the
    default image smaller, but adds a second image to build/maintain/scan (the `docker` gate's hadolint+grype tiers,
    per `CLAUDE.md`, would need to cover both) for a payoff measured in low single-digit MB — not worth it unless
    actual subset sizes come in far larger than expected.
- Revisit this decision only if the specific font families/weights chosen for Japanese and Arabic turn out to need
  full (non-subsetted) multi-weight families — that's when the "worth an image variant" tradeoff could flip.

**As-built**:

- **Font families: Noto Sans Arabic + Noto Sans JP** (Google's Noto project, SIL Open Font Licence — the same
  licence family `OpenDyslexic` already established as this app's precedent; chosen specifically for broad,
  no-tofu Unicode coverage rather than a stylistic match to Nova). Sourced as the upstream **variable** fonts
  (`wght` axis, `wdth` too for Arabic) from a **pinned commit** of `google/fonts` (not `main`, for reproducibility)
  and instanced to static 400/700 weights — neither script offers a real italic in this family (confirmed: no
  `ital` axis on either source), so unlike Nova/OpenDyslexic there is no oblique/italic `@font-face` pair.
- **Subsetted, not shipped whole**: the upstream Japanese variable font alone is ~9.5 MB (Noto Sans JP covers
  >20,000 CJK glyphs across the weight axis). Arabic subsets to the same script-block repertoire Google's own
  font-analysis pipeline curates for its `fonts.googleapis.com` "arabic" CSS chunk (reused verbatim here, since it
  was already the right answer) — **~150 KB per weight (TTF master), ~49 KB woff2**. Japanese subsets to the
  JIS X 0208 "common-use kanji + kana" cutoff (derived by walking every Shift-JIS byte sequence through Python's
  own codec, rather than hand-curating a kanji list — a well-established practical boundary for "common Japanese
  text") — **~2.6 MB per weight (TTF master), ~1.1 MB woff2**, comfortably inside the 1–3 MB estimate the original
  plan guessed at. Total served payload for both languages, both weights: **~2.3 MB** — trivial next to a 200 MB+
  Quarkus image, confirming the "bake it in" decision without needing to revisit it.
  - A rare kanji outside the JIS X 0208 cutoff (there will be some — this is a "common-use" set, not exhaustive)
    falls through to the OS's own CJK fallback font if it has one, or renders as tofu if it does not — the same
    outcome as before this phase for that character, just narrower than "every Unicode kanji." Accepted per the
    plan's own size-vs-coverage tradeoff; revisit the cutoff (not the mechanism) if this proves a real problem.
- **Mechanism, per the decision above**: `'Noto Sans Arabic'` and `'Noto Sans JP'` are appended to the END of
  every `--font-body`/`--font-display` stack in `app.css` — `:root` (the system default) and both `.font-nova`/
  `.font-dyslexic` overrides — ahead of the final generic `sans-serif` keyword. **No `Font` enum change, no
  `language`-keyed conditional anywhere.** Verified in a real browser (Playwright, three screenshots — one per
  Font setting): Arabic and Japanese sample text renders with real glyphs (no tofu) under `.font-nova`,
  `.font-dyslexic`, and the unstyled default alike, while Latin text in the same block correctly keeps rendering
  in Nova Flat/OpenDyslexic/the system stack respectively — confirming the fallback triggers per-character, not
  per-element.
  - **`unicode-range` on each `@font-face` is deliberately a handful of broad script BLOCKS** (Arabic: the same
    curated list used to subset the font; Japanese: `U+3000-30FF, U+4E00-9FFF, U+FF00-FFEF`), narrower than the
    font's actual glyph repertoire rather than an exact, ~4000-run listing of every included Japanese codepoint —
    simpler to read and maintain, at the cost of occasionally having the browser consider this font for a glyph it
    turns out not to contain (which falls through to the next font in the stack exactly as if unicode-range had
    excluded it, per the CSS Fonts spec's per-character fallback — not a correctness gap, just an accepted
    imprecision in the size-optimisation hint).
- **A documented, reproducible generation script** (`scripts/generate-noto-fonts.py`, mirroring
  `generate-brand.py`'s style): fetches the two pinned upstream variable fonts, instances, subsets to the
  repertoire above, and writes both the committed master (`assets/NotoSansArabic/`, `assets/NotoSansJP/`, each
  with its own `OFL.txt`) and the committed served `woff2` (`src/main/resources/META-INF/resources/fonts/`) — the
  same "masters + served output both committed, no build-time font generation" pattern Nova/OpenDyslexic already
  use, just with an actual subsetting step in front of it since (unlike those two) the upstream source is not
  already scoped to what this app needs. Re-running it is only needed to widen the repertoire or pick up an
  upstream Noto update, not part of the normal build.
- **No CSP change needed**: `font-src 'self'` already covers any same-origin `/fonts/*.woff2`, matching every
  other font in the app — these are self-hosted exactly like Nova/OpenDyslexic, never fetched from a CDN.
- **Checked, no change needed**: `scripts/hash-static-assets.sh` already deliberately excludes all `woff2` fonts
  from content-hashing (stable `/fonts/*` URLs), so the two new families needed no entry there.

**Exit criteria — met**: Arabic and Japanese text renders in a real, legible typeface everywhere in the UI
(verified in a real browser under all three `Font` settings); the actual image-size delta (~2.3 MB served, ~5.5 MB
of committed master TTFs) is measured, not guessed, and confirms the "bake it in by default" decision needs no
revisiting.

### `es-ES` slice ✅ DONE (2026-08-20)

All 370 `AppMessages` entries translated into Spanish (Spain), landed as `src/main/resources/messages/msg_es-ES.properties`
— every key present, none skipped, verified by a script that diffed the translated key set against the interface's
own method names before writing the file (see "how it was built" below).

**A real, previously-undiscovered bug, found and fixed before any of this could work at all**: `AppMessages.java`'s
own class Javadoc (written in Phase 0/1) documented the sibling-file convention as `messages_<locale>.properties`
under `src/main/resources/messages/`, "matching this interface's simple name". This is wrong, and was wrong from
the moment it was written — it was simply never exercised, because Phase 0/1's own `AppMessagesIT` only ever proved
the FALLBACK path (a locale with no file at all resolves to English), never a locale WITH a real file. The actual
Quarkus mechanism (confirmed by fetching `io.quarkus.qute.i18n.MessageBundle`'s real source, `3.38.2` tag, after
decompiling `MessageBundleProcessor`'s bytecode to find the file-matching logic first): a message bundle's NAME —
which is what a sibling file's prefix must match — defaults to `MessageBundle.DEFAULT_NAME`, the literal string
`"msg"`, for any unqualified TOP-LEVEL bundle interface, regardless of the interface's own class name. `"msg"` is
already a familiar token (the `{msg:...}` template namespace IS the bundle name), but nothing before this pointed
out that the sibling file must use it too. The correct filename is therefore **`msg_es-ES.properties`**, not
`messages_es-ES.properties`. **This class of bug is silent everywhere except at render time**: a wrongly-named file
still gets copied into `target/classes/messages/` by the normal resource-processing step, the build stays green,
`@QuarkusTest` startup stays green, the CDI bean registers normally — Quarkus simply never associates the file with
any locale, so every render of that "translated" locale silently falls back to the bundle's English default with
no warning anywhere. Only a runtime assertion against the actual rendered TEXT for that locale — which nothing in
this codebase had, before this slice added `AppMessagesIT.messageNamespace_resolvesRealSpanishContent_forEsEs` and
two siblings covering a parameterised call and the `{#if}` plural chain — can catch it. Fixed the Javadoc alongside
the filename, with the real mechanism (and this failure mode) spelled out so the next language slice doesn't have
to re-derive it.

**How it was built**: rather than translating inline against the 3,200-line `AppMessages.java` directly, the 370
`@Message` values and their method signatures were extracted programmatically (a small Python script walking the
source, handling the handful of multi-line concatenated `@Message("..." + "...")` values) into a flat catalogue,
translated against that catalogue, then assembled into the `.properties` file by a second script that asserts the
translated key set is EXACTLY the interface's 370 method names (no missing key, no stray extra one) before writing
anything — a mechanical safety net for a translation pass at this scale, not a design decision about the file
itself.

**Translation choices worth recording** (register, terminology, and a few places where a fixed-slot template
forced a different distribution of words across keys than the English original used):

- **Register: informal *tú*, throughout** — matches the tone of a personal habit-tracker web app (the same register
  Duolingo/most consumer Spanish-language SaaS UIs use), not the formal *usted*. Consistent across every entry;
  worth stating explicitly so the `es-419` slice either matches it or deviates on purpose, not by accident (Latin
  American Spanish's *tú*/*usted* conventions differ regionally from Spain's).
  - "Ajustes" for **Settings** (not "Configuración") — the Spain-specific choice; revisit for `es-419`, where
    "Configuración" is more common.
- **Domain vocabulary, picked once and reused everywhere it recurs**: "racha" for **streak**, "pausa" for **gap**
  (a period without the action, not literally "gap"/"hueco" — reads more naturally in the stat-tile captions),
  "recuento" for a day's logged **count**, "acción" for **action**, "panel" for **dashboard**.
- **Two places where a template concatenates several separately-keyed strings in a FIXED order, and English's word
  order happened not to survive a literal per-key translation, so words were redistributed across the same keys
  instead of translated key-for-key**:
  - `register.html` renders `{missingFieldsPrefix} {singular-or-plural word}:` — English changes only the last
    word ("field"/"fields") between forms; Spanish needs the article AND adjective to agree in number too
    ("el siguiente campo" / "los siguientes campos"), which a single shared prefix can't carry. Resolved by
    shrinking `missingFieldsPrefix` to just "Rellena" and moving the full inflected noun phrase into
    `missingFieldSingular`/`missingFieldsPlural` themselves — still three keys, same template, correct Spanish.
  - `admin-user-row.html` renders `{lastSeenPrefix} <live-updating clock> {agoSuffix}` — literally
    "Visto por última vez <clock> hace" would misplace "hace" (Spanish puts the "ago" word BEFORE the duration, not
    after) with no way to reorder a live DOM element sitting between the two message calls. Resolved by moving
    "hace" into `lastSeenPrefix` itself ("Visto por última vez hace") and leaving `agoSuffix` an empty string — a
    legitimate translation choice within a fixed template, not a workaround needing a code change.
- **The invisible-character rejection wording was reviewed as the original Phase 5 draft flagged**: translated as
  "no puede contener caracteres invisibles ni de control de dirección de texto" (cannot contain invisible
  characters or text-direction CONTROL characters) — explicitly names them as control characters, so it cannot be
  misread as "this script isn't supported" the way a vaguer phrasing might.
- Proper nouns/brand names stayed untouched per Phase 1's own precedent: "Diurnal", "GitHub", "OIDC", "Nova",
  "OpenDyslexic" are not translated.

**Translation choices worth recording** (register, terminology, numerals, and the grammar applied to every
pluralised entry):

- **Register: Modern Standard Arabic (Fus'ha), masculine-default second-person address, throughout** — Arabic verb
  conjugation is gendered in the second person (an imperative addressed to a woman takes a different form than one
  addressed to a man), and the near-universal convention across Arabic software UI (Google, Facebook, Twitter) is to
  default to the masculine form since Arabic has no true gender-neutral option — the same category of "pick the
  established convention, state it explicitly" decision `es-ES` made for *tú* vs *usted*.
- **Numerals: asked, not assumed** (per this project's own standing rule on regional/dialect defaults with no
  technical tiebreaker) — you chose Eastern Arabic-Indic digits (`٠١٢٣...`) for every LITERAL digit written directly
  into the Arabic text (e.g. the `٠` in `importActionsCount`'s zero branch, or the `١`/`٢`/`١٠٠` in the validation
  messages' fixed bounds). **A known, deliberately unfixed inconsistency this creates**: a `{count}`/`{seconds}`/
  etc. PARAMETER substituted into a message (as opposed to a literal digit typed into the translation) still prints
  in Western digits, because it is Java's raw `Integer`/`Long` `.toString()` output flowing through Qute's default
  `{param}` interpolation unchanged — the same `NumberFormat`/`DecimalStyle` locale-aware formatting Phase 2 already
  gave to computed stat figures and date components was never applied to a bare `@Message` `int`/`long` parameter,
  and doing so is a real (if narrow) Phase 2/3-shaped engineering item, not a translation-content one, so it is
  flagged here rather than attempted mid-slice. Concretely: `importActionsCount(15)` in Arabic reads `"15 نشاطًا"` —
  Eastern digits nowhere, Western `15` from the raw parameter — while `importActionsCount(1)` reads `"نشاط واحد"`
  and `importActionsCount(0)` reads `"٠ أنشطة"` (the Eastern `٠` is a literal in the translation, not a substituted
  parameter). This mirrors `DateTimeFormatter`'s own pre-existing numbering-system split (`withLocale` alone
  localises names but not digit glyphs, per `time/DayLabels`) — the app already has ONE precedent for "some numbers
  are locale-aware, some aren't" and this slice adds a second, narrower one, not a new class of problem.
- **Domain vocabulary, picked once and reused everywhere it recurs**: "نشاط" (*nashat*, activity) for **action**,
  plural "أنشطة"; "سجل" (*sijill*, record/log) for a day's logged **count** entry (the "day count" concept), plural
  "سجلات"; "ملاحظة" (note) for **note**, plural "ملاحظات"; "سلسلة" (chain) for **streak** — matching the same word
  Duolingo's Arabic UI uses for exactly this concept, the same "match the established consumer-app convention"
  reasoning `es-ES` applied to its own register choice; "فجوة" for **gap**; "لوحة التحكم" (control panel) for
  **dashboard**; "الإعدادات" for **settings**. **Two words deliberately kept distinct despite being near-synonyms**,
  caught by a scripted pass comparing every pair of keys that ended up with identical Arabic text against their
  English source: "مسح" (a light "clear", e.g. the note textarea's Clear button) vs "محو" (a heavier "erase/wipe",
  the action-log Erase button/confirmation) — English already draws this same distinction ("Clear" vs "Erase"), so
  collapsing both to one Arabic word would have quietly lost it. That same pass also flagged `themeLabel`/
  `appearanceCardTitle` both landing on "المظهر" (Theme vs Appearance are genuinely different English concepts in
  this UI — the Appearance card CONTAINS a Theme picker among others) and was fixed by giving `themeLabel` its own
  word, "السمة". Every other collision the pass found (`signIn`/`signInMethodColumnHeader`,
  `statisticsCardTitle`/`statsPageTitle`, `userManagementPageTitle`/`manageUsersTooltip`) was reviewed and left
  alone — the English source itself uses near-identical wording for each of those pairs, so the shared Arabic word
  is a correct translation, not a lost distinction.
- **Full CLDR six-category grammar applied to every pluralised noun**, not just a translated copy of the English
  two-way split — worked out once per noun (the six word-forms for "نشاط"/"سجل"/"ملاحظة"/"سنة"/"شهر"/"يوم"/"ثانية"/
  "حقل", covering every pluralised entry in the interface after the method-pair collapse above) and reused via a
  small `plural6(...)` helper in the build script rather than typed out six times per entry. Two real Arabic
  numeral-noun agreement rules were applied throughout, not just approximated: the **dual** (exactly two) is its own
  word with no digit alongside it (`نشاطان`, not `٢ نشاطان`) since the dual form already carries the count; and the
  **11-99 "many" range** takes a singular noun in the indefinite accusative, conventionally marked with a trailing
  tanwin fatha even in otherwise-unvocalised text (`{count} نشاطًا`, `{count} يومًا`) — the same "case marking DOES
  survive into plain digital text for this one construction" convention real Arabic software localisation follows.
  `duration(years, months, days)`'s three independent chains (one per unit) and `importReplacedSummary`'s three
  independent chains (one per action/log/note count) each apply the full six-way grammar per component, exactly
  like the `es-ES` slice's simpler two-way version of the same entries.
- **The invisible-character rejection wording carries the same explicit "control characters" framing `es-ES`
  chose**, for the same reason (so it cannot be misread as "Arabic script isn't supported" — real Arabic letters are
  category `Lo` and are never touched by this rule, per `TEXT_INPUT.md`'s own note): "لا يمكن أن يحتوي ... على أحرف
  غير مرئية أو أحرف تحكّم في اتجاه النص" (cannot contain invisible characters or text-direction CONTROL characters).
- Proper nouns/brand names stayed untouched, same precedent as `es-ES`: "Diurnal", "GitHub", "OIDC", "Nova",

  kind of thing Phase 3's bidi/`js-phrase` handling already exists for).

### Second follow-up round (2026-08-20), same day — the real root cause

The user reported the timezone fix still showing `Auckland` (bare Latin city name) and the import-preview
error banner missing entirely (with a browser-console `413 Request Entity Too Large`), running the app via
`docker compose down && docker compose up --build` (the packaged production image, NOT `mvn quarkus:dev`) -
the detail that cracked this open, since every verification up to this point in the whole session (including
every "did not reproduce" item logged earlier today) had only ever been run against `mvn quarkus:dev`, which
boots a full, non-jlinked JDK.

**Two real, independent bugs found, both invisible to every check this project runs short of the deployment-
smoke tier - which is exactly why that tier exists (its own header comment already named "missing jlink
modules" as its reason to exist, before this investigation added a concrete instance of one):**

1. **The Dockerfile's jlink invocation omits `jdk.localedata`.** This is not an "extra" module despite the
   name: without it, `java.time`/`java.text` CLDR-backed calls (`ZoneId`/`DayOfWeek`/`Month#getDisplayName`,
   `DateTimeFormatter.ofLocalizedDate`, `NumberFormat`/`DecimalStyle`) silently fall back to the JDK's built-in
   root/English-only data, REGARDLESS of what `Locale` is passed in - so every date/weekday/timezone label in
   the app fell back to English (or a bare Latin id) in the packaged image no matter what `user.language` said,
   while the pure-Java `AppMessages` bundle content (unaffected by JDK locale data at all) translated correctly
   - explaining why the earlier-diagnosed "not translated" items and this round's Auckland report looked so
   different in kind but shared one cause. Confirmed empirically, not assumed: jlinked the EXACT module list
   from the Dockerfile, with and without `jdk.localedata`, using the same JDK version (Temurin 26.0.1) the
   Dockerfile pins, and diffed `ZoneId.of("Pacific/Auckland").getDisplayName(TextStyle.FULL, ar-SA)` -
   `"Auckland"` (bare exemplar city, Latin script, silently derived from the id) without the module,
   `"توقيت نيوزيلندا"` with it; `DayOfWeek.SUNDAY.getDisplayName(..., ar-SA)` was `"Sun"` vs `"الأحد"` -
   `"Sun"` is a literal, exact match for the ORIGINAL bug report's #9 from earlier today, strongly suggesting
   this was the real cause of every "did not reproduce" item logged in this file's first follow-up round too,
   not a stale build as guessed there. **Fixed with `--include-locales=en,es,ar,ja`** (trims the module to only
   the four offered base languages rather than the ~700-locale default) - confirmed via `du` to cost ~0.5 MB
   over the baseline (the untrimmed module would have cost ~11 MB, which is what this project's own size-
   consciousness around `java.desktop` - documented a few lines above the jlink command - would have flagged
   immediately). **Verified against the REAL built image**, not just the isolated jlink experiment: a full
   `docker build` (with `GENERATE_PREVIEWS=false` to skip the unrelated screenshot stage) plus a manual
   container run reproduced both `"توقيت نيوزيلندا (UTC+١٢)"` for the timezone picker and the full Arabic
   weekday header - then the SAME check was captured as a permanent regression test (below) and run through
   this project's own `tests/run-smoke.sh`, green.
2. **`quarkus.http.limits.max-body-size` was unset, defaulting to Quarkus's own 10 MiB (10240K) - well below
   `transfer/TransferArchive`'s own 64 MiB `MAX_ARCHIVE_BYTES` zip-bomb cap.** An upload between 10 and 64 MiB
   (a real, legitimately-sized export re-import, not just an adversarial one) was rejected by Vert.x's raw
   body-length check before the request handler - let alone `TransferArchive`'s own check - ever ran, so the
   browser got a bare, unstyled HTTP 413 with no app-rendered content at all (in every language, since nothing
   app-side renders it - this is what "no error message appears in Arabic" actually was, for THIS report;
   confirmed the exact byte boundary empirically, binary-searching against a running dev instance:
   10,485,760 bytes (exactly 10 MiB) succeeds, 10,485,761 fails). **Fixed with
   `quarkus.http.limits.max-body-size=70M`** in `application.properties` (headroom above the app's own 64 MiB
   cap, so every upload `TransferArchive` is willing to accept can actually reach it) - confirmed the boundary
   moved to ~70 MiB and that a 63 MiB non-ZIP payload now reaches `TransferArchive`'s own check and renders the
   correct translated `NotZipArchive` banner instead of a bare 413.

**A new permanent regression test, in the deployment-smoke tier** (`tests/smoke/smoke.spec.ts`, "a non-English
language renders real CLDR text, not an English/Latin fallback") - registers a user, sets `language: ar-SA` via
`PATCH /api/v1/users/me`, and asserts the dashboard's weekday header contains `"الأحد"` (never `"Sun"`) and the
Settings timezone picker's `Pacific/Auckland` option contains `"توقيت نيوزيلندا"` (never `"Auckland"`) - the
exact two symptoms this round found, permanently guarding the `jdk.localedata` module going forward. Run against
a real build via `tests/run-smoke.sh`: 5/5 passed, including this new one. The `max-body-size` fix has no
equivalent smoke coverage yet - `TransferArchive`'s own size-cap tests already cover the APPLICATION-level
behaviour (`TransferArchiveTest`), but nothing asserts the HTTP-layer ceiling sits above it; flagged as a gap
rather than added speculatively, since a smoke test uploading a real >10 MiB archive is a heavier addition than
this round's scope.

**Also worth restating for future sessions**: `mvn quarkus:dev` and `mvn test` will NEVER catch a jlink-module
gap, no matter how thorough - both boot a full, non-jlinked JDK. Anything gated on "does the PACKAGED runtime

running the Dockerfile's own image, which is slow enough that it is easy to skip informally - this round only

### Seventh follow-up round (2026-08-20), same day — "API"/"OIDC" reconsidered, review pass

A review pass surfaced three items; two were already correct by design (confirmed live, not just re-asserted -
`apiNavLink`'s tooltip was already fully translated even though the link text itself said the bare "API", and
toggle-switch mirroring under RTL matches iOS/Android/Material Design convention, unlike the calendar chevrons'
deliberate exception two rounds up) - documented for the record but not code changes. The third was a genuine,
deliberate reversal: **"API" and "OIDC" are no longer kept as bare Latin initialisms in `ar-SA`/`ja-JP`.**

The original reasoning (an initialism is "an international abbreviation, same treatment as brand names") turned
out to conflate two different things once challenged directly: a BRAND NAME ("Diurnal", "GitHub") has no meaning
to translate - it is not a translation gap to leave it as-is in any language. An INITIALISM does carry meaning
(the sounds of specific Latin letter names), and that meaning is genuinely inaccessible to a reader who doesn't
already know those letter names - which is not remotely the same class of "untranslatable." Real Arabic and
Japanese technical writing already has an established answer for exactly this: spell the initialism out

## Translation tooling (2026-08-20) — ICU4J revisited, CrowdIn/Weblate, a real translation gap, best-practice fixes

A review pass, prompted by a request to evaluate (1) ICU4J adoption, (2) CrowdIn/Weblate support, (3) general
best practices, (4) how many code references a new language touches, (5) whether any translation had been
missed, and (6) whether the Settings language dropdown could be driven purely by which `msg_*.properties`
files exist on disk. Landed as concrete fixes/tooling rather than just a written answer to each point.

**ICU4J - re-evaluated, same conclusion as Phase 2, one narrow follow-up identified but not done**: the
Phase 2 rejection (`{msg:...}` values are themselves Qute templates, so CLDR-style plural branching lives in
one bundle entry's `{#if}`/`{#else if}` chain with no second syntax/second bundle format - see that phase's
own notes) still holds and was not reversed. The one place still worth narrowing is `web/ArabicPlural`'s
hand-rolled CLDR category arithmetic (the `11`/`99`/`2` boundary checks Qodana already needed a suppression
for, per Phase 5's ninth follow-up round) - `ICU4J`'s `PluralRules.select()` could replace just that
category-selection logic while still feeding the same `{#if}` Qute branching, keeping the "one bundle, no
second syntax" property Phase 2 chose. **Not implemented this round** - flagged as a scoped, optional
follow-up, not a live gap.

**CrowdIn/Weblate - a real blocker found and worked around, not just documented.** The obvious plan
("commit `msg_en-GB.properties` alongside the others as the source-language file") does not work: verified
empirically (a real `msg_en-GB.properties` override, compiled onto the classpath, rendered through a real
`{msg:...}` template call) that **Quarkus's `@MessageBundle` mechanism never consults a properties file for
whichever locale is `quarkus.default-locale`** - the `@Message` annotation value wins unconditionally, even
when an exactly-matching file with different content exists. So `AppMessages.java`'s own class Javadoc
("English needs no separate `msg_en-GB.properties` file") is not just a style choice, it is describing a
real framework constraint. Presented to you as three options (a generated, non-runtime export file; flipping
`quarkus.default-locale` off `en-GB` so a real file becomes authoritative; or deferring CrowdIn entirely) -
you chose the first. Built:

- `scripts/GenerateSourceMessages.java` + `scripts/generate-source-messages.sh`: reflects over the compiled
  `AppMessages` class (not a source-text parse - a handful of `@Message` values are written as multi-line
  Java string concatenation, e.g. `lockoutRetry`, and reflection reads the already-folded constant, sidestepping
  every source-layout edge case) and writes sorted `key=value` lines to `translations/msg_en-GB.properties`.
  **This file is a one-way EXPORT, never read by the running application** - re-run the script after any
  `@Message` wording change, before syncing to CrowdIn/Weblate; the application's real English source stays the
  `@Message` annotations, unchanged from Phase 0/1.
- `code-quality-config-overrides/crowdin.yml`: a starter config (properties-file mapping,
  `translations/msg_en-GB.properties` as source, `src/main/resources/messages/msg_%locale%.properties` as the
  translated target, an explicit `languages_mapping` for the four offered non-default locale tags, `base_path:
  ..` so its repo-root-relative paths resolve correctly from this directory) - **not wired to a live project**
  (no `project_id`/token exist yet); a genuinely new language's translated output still lands as a real
  `src/main/resources/messages/msg_<locale>.properties`, exactly like `es-ES`/`ar-SA`/`ja-JP` today. Moved here
  (not the repo root) after this section first landed, matching the same "no linter/tool dotfiles at the repo
  root" convention `qodana.yaml`/`.grype.yaml`/`sonar.properties` already follow - see that directory's own
  README, updated alongside this move to cover a non-lint tool for the first time.

**A real, previously-unnoticed translation gap found and fixed**: `msg_es-ES.properties` was missing all 14
`timezone*` keys (`timezoneLondon`, `timezoneTokyo`, `timezoneAuckland`, …) that `msg_ar-SA.properties`/

silently fall back to English mid-Spanish UI. Found by diffing `AppMessages`'s full key set against each
locale file (not by inspection - see the new coverage test below). Fixed with the English text as an explicit,
commented placeholder (`msg_es-ES.properties`'s own inline comment marks it), per your call that the real

**`msg_en-US.properties` deliberately converted from its Phase 5 sparse spelling-only diff (12 keys) to a
full duplicate (389 keys) - a real, considered reversal, not a bugfix.** Presented to you as a genuine
tradeoff (the sparse design's one real benefit - automatically inheriting any future `en-GB` wording change
with zero edit - is lost once every key has explicit content) rather than silently applied; you chose full
duplication specifically to give CrowdIn/Weblate a complete target file to manage. The file's own header
comment was rewritten to explain the reversal and its cost, matching this project's convention of keeping a
file's rationale in sync with what it actually does (see `Language.SPANISH`'s Javadoc after the `es-419`
removal, Phase 5's eighth follow-up round, for the same pattern). Generated by joining the existing 12

Auckland-Sydney-Tokyo-... sequence) - never alphabetical, unlike the generated export file itself, which has

**A new completeness guard, closing the gap that let the `es-ES` timezone omission ship unnoticed**:
`web/AppMessageCoverageTest` reflects over `AppMessages` for the full key set and asserts each of
`en-US`/`es-ES`/`ar-SA`/`ja-JP`'s `msg_*.properties` carries **exactly** that set - no missing key (silently
